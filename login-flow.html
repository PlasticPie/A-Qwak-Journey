Password hashing, session tokens, game tokens, and an arrival phase that finally defines what "arrived" means.Hachage des mots de passe, jetons de session, jetons de jeu, et une phase d'arrivée qui définit enfin ce que veut dire « arrivé ».密碼雜湊、連線階段權杖、遊戲權杖，以及終於定義清楚「抵達」意義的抵達階段。

Passwords are stored as slow hashes

A game database will leak one day, so it must never contain passwords. It contains a salted, deliberately slow hash of each one: PBKDF2 with SHA-256, 100,000 iterations, a random 16-byte salt per account, stored as salt:hash in base64. Verifying a password means recomputing the hash with the stored salt and comparing it in constant time, so that the comparison itself does not leak how many leading bytes matched.

Les mots de passe sont stockés en hachages lents

Une base de jeu fuira un jour : elle ne doit donc jamais contenir de mots de passe. Elle contient un hachage salé et volontairement lent de chacun : PBKDF2 avec SHA-256, 100 000 itérations, un sel aléatoire de 16 octets par compte, stocké en sel:hachage en base64. Vérifier un mot de passe, c'est recalculer le hachage avec le sel stocké et comparer en temps constant, pour que la comparaison elle-même ne révèle pas combien d'octets de tête correspondaient.

密碼以緩慢的雜湊儲存

遊戲資料庫總有一天會外洩，所以它絕不能包含密碼。它包含的是每個密碼加鹽、刻意放慢的雜湊：PBKDF2 搭配 SHA-256、100,000 次迭代、每個帳號一個隨機的 16 位元組鹽值，以 base64 編碼成 salt:hash 儲存。驗證密碼，就是用儲存的鹽值重新計算雜湊，並以常數時間比對，讓比對本身不會洩漏開頭有幾個位元組相符。

Qwak.Data/Services/PasswordHasher.cs
public static string Hash(string password)
{
    var salt = new byte[16];
    RandomNumberGenerator.Fill(salt);
    var hash = Rfc2898DeriveBytes.Pbkdf2(password, salt, 100_000, HashAlgorithmName.SHA256, 32);
    return $"{Convert.ToBase64String(salt)}:{Convert.ToBase64String(hash)}";
}

public static bool Verify(string password, string stored)
{
    var parts = stored.Split(':');
    if (parts.Length != 2) return false;
    var computed = Rfc2898DeriveBytes.Pbkdf2(password, Convert.FromBase64String(parts[0]),
                                             100_000, HashAlgorithmName.SHA256, 32);
    return CryptographicOperations.FixedTimeEquals(Convert.FromBase64String(parts[1]), computed);
}

Slowness is the point of the hash and a cost for the server: each verification burns several milliseconds of CPU. That is why the protocol version is checked before it (chapter 1.6): an outdated client retrying in a loop must not be able to make the gateway compute a hundred thousand iterations per attempt.

La lenteur est tout l'intérêt du hachage, et un coût pour le serveur : chaque vérification brûle plusieurs millisecondes de CPU. C'est pour ça que la version du protocole est vérifiée avant (chapitre 1.6) : un vieux client qui réessaie en boucle ne doit pas pouvoir faire calculer cent mille itérations à la gateway à chaque tentative.

緩慢是這種雜湊的重點，也是伺服器的成本：每次驗證都會燒掉好幾毫秒的 CPU。這就是為什麼協定版本要在它之前檢查（第 1.6 章）：一個不斷重試的過時用戶端，絕不能讓閘道每次嘗試都計算十萬次迭代。

Two tokens, two scopes

A successful login creates a session token: a random identifier, kept in the gateway's memory, tied to the connection that logged in. It authorizes the character screen: listing, creating, deleting and selecting characters.

Selecting a character creates a second token, the game token, tied to that character. The gateway sends it to the client together with the address of the game server that hosts the character's map. The client opens a new connection to that server and presents the game token. The game server cannot check it (it has never seen it), so it asks the gateway, which answers with the character id and records that this session now lives on this server.

The two tokens separate two questions: "is this person logged in?" is answered by the gateway on its own connection, and "may this connection play this character here?" is answered for the game server, which never sees a password. The game token stays valid until the game server reports the session closed; consuming it on first use would be a small hardening step.

Deux jetons, deux portées

Un login réussi crée un jeton de session : un identifiant aléatoire, gardé dans la mémoire de la gateway, lié à la connexion qui s'est authentifiée. Il autorise l'écran des personnages : lister, créer, supprimer et choisir.

Choisir un personnage crée un second jeton, le jeton de jeu, lié à ce personnage. La gateway l'envoie au client avec l'adresse du serveur de jeu qui héberge la carte du personnage. Le client ouvre une nouvelle connexion vers ce serveur et présente le jeton de jeu. Le serveur de jeu ne peut pas le vérifier (il ne l'a jamais vu) : il le demande à la gateway, qui répond avec l'identifiant du personnage et note que cette session vit désormais sur ce serveur.

Les deux jetons séparent deux questions : « cette personne est-elle connectée ? » trouve sa réponse à la gateway, sur sa propre connexion, et « cette connexion peut-elle jouer ce personnage ici ? » trouve la sienne pour le serveur de jeu, qui ne voit jamais un mot de passe. Le jeton de jeu reste valable jusqu'à ce que le serveur de jeu annonce la fermeture de la session ; le consommer à la première utilisation serait un petit durcissement.

兩種權杖，兩種範圍

成功登入會建立一個連線階段權杖：一個隨機識別碼，保存在閘道的記憶體中，綁定在登入的那條連線上。它授權的是角色畫面：列出、建立、刪除與選擇角色。

選擇角色會建立第二個權杖，也就是綁定該角色的遊戲權杖。閘道把它連同託管該角色地圖的遊戲伺服器位址一起送給用戶端。用戶端開啟一條連到那台伺服器的新連線，並出示遊戲權杖。遊戲伺服器無法檢查它（它從沒看過這個權杖），所以會詢問閘道，閘道回覆角色 ID，並記下這個連線階段現在位於這台伺服器上。

兩種權杖把兩個問題分開：「這個人登入了嗎？」由閘道在自己的連線上回答，而「這條連線可以在這裡玩這個角色嗎？」則是替遊戲伺服器回答，遊戲伺服器從頭到尾不會看到密碼。遊戲權杖在遊戲伺服器回報連線階段結束之前都有效；在第一次使用時就讓它失效，會是一個小小的強化步驟。

Selecting a character

Selection does three things in order.

  1. Takeover. If this character already has a live session somewhere (a crashed client, a second PC), that session is kicked. The most recent connection always wins. Refusing with "already logged in" would lock a player out of their own character after any crash, and would let two clients fight over one ship.
  2. Where to wake up. The character wakes up on the map of their active ship, or at a station if they have no ship. The gateway and the game server must reach the same answer, so both call the same shared query instead of each writing its own version of the rule.
  3. Find a host. The gateway looks up which server hosts that map, and if none does, asks one to load it and waits for the answer (chapter 7.1). Only then does it create the game token and reply.

Choisir un personnage

Le choix fait trois choses dans l'ordre.

  1. Reprise de session. Si ce personnage a déjà une session vivante quelque part (un client planté, un second PC), cette session est éjectée. La connexion la plus récente gagne toujours. Refuser avec « déjà connecté » enfermerait un joueur hors de son propre personnage après n'importe quel plantage, et laisserait deux clients se disputer un vaisseau.
  2. Où se réveiller. Le personnage se réveille sur la carte de son vaisseau actif, ou dans une station s'il n'a pas de vaisseau. La gateway et le serveur de jeu doivent arriver à la même réponse : les deux appellent la même requête partagée au lieu d'écrire chacun sa version de la règle.
  3. Trouver un hôte. La gateway cherche quel serveur héberge cette carte, et si aucun ne le fait, demande à l'un d'eux de la charger et attend la réponse (chapitre 7.1). Alors seulement, elle crée le jeton de jeu et répond.

選擇角色

選擇角色會依序做三件事。

  1. 接管。如果這個角色在某處已經有一個活躍的連線階段（當掉的用戶端、第二台電腦），那個連線階段會被踢掉。最新的連線永遠獲勝。若以「已經登入」拒絕，任何一次當機都會把玩家鎖在自己的角色之外，還會讓兩個用戶端搶同一艘船。
  2. 在哪裡醒來。角色會在他所使用中的船艦所在的地圖上醒來；如果沒有船，就在某個太空站醒來。閘道與遊戲伺服器必須得到相同的答案，所以兩者呼叫同一個共用查詢，而不是各自寫一份自己版本的規則。
  3. 找一台主機。閘道查詢哪台伺服器託管那張地圖；如果沒有，就請一台伺服器載入它並等待回覆（第 7.1 章）。直到這時，它才建立遊戲權杖並回覆。

"Arrived" needs a definition

For a long time, arriving on a map was a scatter of independent messages: the map's gravity field here, the spawn result there, each racing the client's scene loading. Worse, the ship was added to the map at the moment the session was validated, so the first snapshots reached a client that had not finished loading. It displayed whatever it had at hand (a stale hull for one frame, a map without its field) and then corrected itself in front of the player. Each of those artefacts was chased separately. They were one bug: nothing defined what "arrived" meant.

Arrival is now a phase with a beginning and an end, owned by the server:

« Arrivé » a besoin d'une définition

Longtemps, arriver sur une carte a été une dispersion de messages indépendants : le champ de gravité de la carte ici, le résultat du spawn là, chacun en course avec le chargement de scène du client. Pire, le vaisseau était ajouté à la carte à l'instant où la session était validée : les premiers snapshots atteignaient un client qui n'avait pas fini de charger. Il affichait ce qu'il avait sous la main (une coque périmée pendant une image, une carte sans son champ) puis se corrigeait sous les yeux du joueur. Chacun de ces artefacts a été traqué séparément. C'était un seul bug : rien ne définissait ce que voulait dire « arrivé ».

L'arrivée est maintenant une phase avec un début et une fin, possédée par le serveur :

「抵達」需要一個定義

Trade-off

There is no timeout on MapReady, deliberately. A client that never sends it stays invisible, and its connection eventually dies through the normal disconnect path. A partial, silent spawn (in the map but not ready) would be worse than a visible hang, and far harder to diagnose.

Rule

When several bugs share a moment ("on arrival", "on reconnect"), give that moment a name, an owner and an explicit end.

An undefined phase produces a family of race conditions that look unrelated. A named state that handlers already respect removes the family at once.

Compromis

Il n'y a pas de délai d'expiration sur MapReady, délibérément. Un client qui ne l'envoie jamais reste invisible, et sa connexion finit par mourir par le chemin normal de déconnexion. Une apparition partielle et silencieuse (dans la carte mais pas prête) serait pire qu'un blocage visible, et bien plus dure à diagnostiquer.

Règle

Quand plusieurs bugs partagent un moment (« à l'arrivée », « à la reconnexion »), donner à ce moment un nom, un propriétaire et une fin explicite.

Une phase non définie produit une famille de courses qui ont l'air sans rapport. Un état nommé que les gestionnaires respectent déjà supprime toute la famille d'un coup.

取捨

MapReady 刻意沒有逾時。一個永遠不送出它的用戶端會一直保持隱形，它的連線最終會經由正常的斷線路徑結束。一個不完整又無聲的出生（在地圖中卻沒準備好），會比看得見的卡住更糟，也更難診斷。

規則

當好幾個 bug 共享同一個時刻（「抵達時」、「重新連線時」），就給那個時刻一個名稱、一個負責者，以及一個明確的結束。

未定義的階段會產生一整個家族、看似無關的競爭條件。一個處理常式早已遵守的具名狀態，能一次消除整個家族。

Redundancy bought on purpose

MapInit resends, every time, the list of maps this character has visited, each with the faction that controlled it at the time and the age of that information. Strictly, the client needs it once per session. Sending it on every arrival means a client that reconnects, crashes or is freshly installed converges to the truth each time, and nothing on the server has to remember what it already told whom. A few dozen bytes on a screen the player crosses anyway are not worth optimizing against correctness.

The ages are sent as hours elapsed, not as dates. The client has no clock to synchronize with the server, so nothing can drift, and the value is capped by the constructor of the message itself, which keeps it within one byte even for a map visited six months ago.

Une redondance achetée exprès

MapInit renvoie à chaque fois la liste des cartes que ce personnage a visitées, chacune avec la faction qui la contrôlait à ce moment et l'âge de ce renseignement. Strictement, le client n'en a besoin qu'une fois par session. L'envoyer à chaque arrivée fait qu'un client qui se reconnecte, qui a planté ou qui est fraîchement installé converge vers la vérité à chaque fois, et rien côté serveur n'a à se souvenir de ce qu'il a déjà dit à qui. Quelques dizaines d'octets sur un écran que le joueur traverse de toute façon ne valent pas d'être optimisés contre la justesse.

Les âges partent en heures écoulées, pas en dates. Le client n'a aucune horloge à synchroniser avec le serveur, rien ne peut dériver, et la valeur est plafonnée par le constructeur du message lui-même, ce qui la garde sur un octet même pour une carte visitée il y a six mois.

刻意買下的冗餘

MapInit 每次都會重新送出這個角色造訪過的地圖清單，每一張都附上當時控制它的陣營，以及這項資訊的新舊程度。嚴格來說，用戶端每個連線階段只需要一次。每次抵達都送，代表一個重新連線、當機或剛安裝的用戶端，每次都會收斂到真相，而伺服器上沒有任何東西需要記得自己已經告訴過誰什麼。在一個玩家反正都要經過的畫面上多花幾十個位元組，不值得犧牲正確性去最佳化。

新舊程度以經過的小時數送出，而不是日期。用戶端沒有需要與伺服器同步的時鐘，所以什麼都不會漂移，而這個值由訊息本身的建構函式設定上限，即使是六個月前造訪的地圖，也只佔一個位元組。

Rule

Send durations, not timestamps.

"Expires in 3,600 s" needs no clock agreement and lets the client count down on its own. A date forces both ends to agree on time and time zone, and the day they disagree the bug looks like a logic error.

Règle

Envoyer des durées, pas des horodatages.

« Expire dans 3 600 s » ne demande aucun accord d'horloge et laisse le client décompter seul. Une date oblige les deux bouts à s'accorder sur l'heure et le fuseau, et le jour où ils ne s'accordent pas, le bug ressemble à une erreur de logique.

規則

送時間長度，不送時間戳記。

「3,600 秒後到期」不需要時鐘一致，還能讓用戶端自己倒數。日期則強迫兩端對時間與時區達成一致，而它們不一致的那一天，bug 看起來會像是邏輯錯誤。

Loading happens outside the tick

Everything above runs on the network thread and the background threads, never inside the 40 ms world tick. Reading the character, the ship and its parts from the database takes milliseconds, sometimes far more. Only the final step, creating the ship's physics body when it enters the map, runs on the tick thread, and it is queued there rather than done immediately (chapter 3.4).

Measured

In a bench with 2,500 bots, map loading still read the database from inside the tick: seven round trips per map. Fifty maps were created in ninety seconds and the tick rate collapsed to 3.6 per second, with the CPU at 25%. It was waiting, not computing. Splitting "read the content" (off the tick, one database context) from "place the bodies" (on the tick, with a time budget) removed the stall.

Le chargement se fait hors du tick

Tout ce qui précède tourne sur le thread réseau et les threads de fond, jamais dans le tick du monde de 40 ms. Lire le personnage, le vaisseau et ses pièces en base prend des millisecondes, parfois bien plus. Seule la dernière étape, la création du corps physique du vaisseau quand il entre dans la carte, tourne sur le thread du tick, et elle y est mise en file plutôt que faite immédiatement (chapitre 3.4).

Mesuré

Dans un banc à 2 500 robots, le chargement des cartes lisait encore la base depuis le tick : sept allers-retours par carte. Cinquante cartes ont été créées en quatre-vingt-dix secondes et la cadence est tombée à 3,6 ticks par seconde, avec le CPU à 25 %. Il attendait, il ne calculait pas. Séparer « lire le contenu » (hors tick, un seul contexte de base) de « poser les corps » (sur le tick, avec un budget de temps) a supprimé le blocage.

載入發生在 tick 之外

以上一切都在網路執行緒與背景執行緒上執行，從不在 40 ms 的世界 tick 之內。從資料庫讀取角色、船艦及其零件要花好幾毫秒，有時遠不只如此。只有最後一步，也就是船艦進入地圖時建立它的物理剛體，才在 tick 執行緒上執行，而且是排入那裡的佇列，而不是立即執行（第 3.4 章）。

實測

在一個 2,500 個機器人的測試台中，地圖載入仍然在 tick 之內讀取資料庫：每張地圖七次往返。九十秒內建立了五十張地圖，tick 頻率崩落到每秒 3.6 次，而 CPU 只有 25%。它在等待，而不是在運算。把「讀取內容」（在 tick 之外，使用一個資料庫內容）與「放置剛體」（在 tick 之內，有時間預算）拆開，就消除了這次停頓。

Key takeaways

  • Store slow, salted password hashes, compare in constant time, and check cheap things (the protocol version) before the expensive hash.
  • Use a login token for the gateway and a separate game token for the game server; the game server asks the gateway instead of seeing credentials.
  • On a new login for a character that is already online, the most recent connection wins.
  • Define arrival as a phase: build, describe, wait for the client, then add to the world.
  • Prefer redundant, self-healing initialization messages and durations over dates.

À retenir

  • Stocker des hachages de mots de passe lents et salés, comparer en temps constant, et vérifier le bon marché (la version du protocole) avant le hachage coûteux.
  • Utiliser un jeton de login pour la gateway et un jeton de jeu distinct pour le serveur de jeu ; le serveur de jeu demande à la gateway au lieu de voir les identifiants.
  • Quand un personnage déjà en ligne se reconnecte, la connexion la plus récente gagne.
  • Définir l'arrivée comme une phase : construire, décrire, attendre le client, puis ajouter au monde.
  • Préférer des messages d'initialisation redondants et auto-réparateurs, et des durées plutôt que des dates.

重點整理

  • 儲存緩慢、加鹽的密碼雜湊，以常數時間比對，並在昂貴的雜湊之前先檢查便宜的東西（協定版本）。
  • 閘道使用登入權杖，遊戲伺服器使用另一個遊戲權杖；遊戲伺服器向閘道詢問，而不是看到帳密。
  • 一個已經在線的角色再次登入時，最新的連線獲勝。
  • 把抵達定義為一個階段：建立、描述、等待用戶端，然後才加入世界。
  • 偏好冗餘、能自我修復的初始化訊息，以及時間長度而非日期。

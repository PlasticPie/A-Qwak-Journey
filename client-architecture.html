The client's network layerLa couche réseau du client

Main-thread marshalling, keeping only the newest snapshot, discovering unknown objects, and loading screens that mean something.Le passage au thread principal, ne garder que le dernier snapshot, découvrir les objets inconnus, et des écrans de chargement qui veulent dire quelque chose.

Two threads that must never touch each other's things

The client shares the server's network library and protocol code (chapter 1.6), and it inherits the same threading model: packets are received and parsed on a network thread that polls the socket. The game engine, Unity, has the opposite constraint: almost its whole API may only be called from the main thread. So no packet handler may touch a game object, a transform or a user interface element directly.

The bridge is a queue. A handler running on the network thread packages what it wants done as an action and enqueues it; the main thread drains the queue once per frame. Two details make this robust instead of merely correct:

  • A time budget per frame. Draining stops after 8 ms, leaving room under a 60 fps frame for rendering. Without a budget, a queue that grows faster than one frame can drain only gets worse every frame, the classic "still too much work left" spiral, instead of spreading the excess over a few visibly slower but still presented frames.
  • At least one item per frame. The budget is checked after each action, never before dequeuing. A queue whose next action alone exceeds the budget still makes progress, slowly, instead of never draining at all.

Deux threads qui ne doivent jamais toucher aux affaires de l'autre

Le client partage la bibliothèque réseau et le code de protocole du serveur (chapitre 1.6), et il hérite du même modèle de threads : les paquets sont reçus et analysés sur un thread réseau qui interroge la socket. Le moteur de jeu, Unity, a la contrainte inverse : presque toute son API ne peut être appelée que depuis le thread principal. Aucun gestionnaire de paquet ne peut donc toucher directement à un objet de jeu, à un transform ou à un élément d'interface.

Le pont est une file. Un gestionnaire qui tourne sur le thread réseau emballe ce qu'il veut faire dans une action et la met en file ; le thread principal vide la file une fois par image. Deux détails rendent la chose robuste plutôt que simplement correcte :

  • Un budget de temps par image. La vidange s'arrête après 8 ms, pour laisser de la place au rendu sous une image à 60 fps. Sans budget, une file qui grossit plus vite qu'une image ne peut la vider empire à chaque image, la spirale classique du « encore trop de travail », au lieu d'étaler l'excédent sur quelques images visiblement plus lentes mais toujours présentées.
  • Au moins un élément par image. Le budget est vérifié après chaque action, jamais avant de retirer de la file. Une file dont l'action suivante dépasse à elle seule le budget progresse quand même, lentement, au lieu de ne jamais se vider.
QwakClient/Scripts/Core/NetworkManager.cs
private readonly ConcurrentQueue<Action> _queue = new();

public void EnqueueMainThread(Action a) => _queue.Enqueue(a);  // any thread

private void Update()                                          // main thread, once per frame
{
    _queueStopwatch.Restart();
    while (_queue.TryDequeue(out var action))
    {
        action();
        if (_queueStopwatch.Elapsed.TotalMilliseconds >= _maxQueueMsPerFrame)  // 8 ms
            break;                                             // checked AFTER: always progress
    }
}

Keep only the newest snapshot

A generic queue is fine for rare messages. Snapshots are not rare: 25 per second, and each one fully describes the world (chapter 4.2). If the client falls behind for a moment (a slow frame, a garbage collection), queuing every snapshot means it then spends several frames applying photographs of the past, each one immediately made obsolete by the next.

So snapshots bypass the queue. The network thread only stores a reference to the latest one and, if no callback is already scheduled, schedules one. The main thread's callback takes whatever the freshest snapshot is at the time it runs. If three snapshots arrive during a long frame, the first two are simply never processed: they were already stale.

Ne garder que le dernier snapshot

Une file générique convient aux messages rares. Les snapshots ne le sont pas : 25 par seconde, et chacun décrit entièrement le monde (chapitre 4.2). Si le client prend un instant de retard (une image lente, un ramasse-miettes), mettre chaque snapshot en file revient à passer ensuite plusieurs images à appliquer des photos du passé, chacune aussitôt rendue obsolète par la suivante.

Les snapshots contournent donc la file. Le thread réseau ne stocke qu'une référence vers le plus récent et, si aucun rappel n'est déjà planifié, en planifie un. Le rappel du thread principal prend le snapshot le plus frais au moment où il s'exécute. Si trois snapshots arrivent pendant une longue image, les deux premiers ne sont tout simplement jamais traités : ils étaient déjà périmés.

QwakClient/Scripts/Core/SnapshotManager.cs · simplified
// Network thread: remember the newest, schedule at most one callback.
d.Register<Snapshot>(Type.Snapshot, (id, pkt, src) =>
{
    Volatile.Write(ref _pendingSnapshot, (Snapshot)pkt);
    if (Interlocked.Exchange(ref _snapshotQueued, 1) == 0)
        nm.EnqueueMainThread(ProcessPendingSnapshot);
    return true;
});

// Main thread.
private void ProcessPendingSnapshot()
{
    var snap = Volatile.Read(ref _pendingSnapshot);  // read BEFORE clearing the flag:
    Interlocked.Exchange(ref _snapshotQueued, 0);    // one that races in now schedules a new
    if (snap != null) HandleSnapshot(snap);          // callback; worst case a redundant apply,
}                                                    // never a lost snapshot

Rule

Coalesce full-state messages; queue only events.

A message that replaces everything before it (a snapshot, a position, a health value) should overwrite a pending copy. A message that adds something (a chat line, a trade offer) must be queued. Mixing the two in one mechanism either loses events or processes the past.

Règle

Fusionner les messages d'état complet ; ne mettre en file que les événements.

Un message qui remplace tout ce qui le précède (un snapshot, une position, une valeur de vie) doit écraser une copie en attente. Un message qui ajoute quelque chose (une ligne de chat, une offre d'échange) doit être mis en file. Mélanger les deux dans un seul mécanisme perd des événements ou traite le passé.

Register the parsers before you connect

The "connected" event is itself deferred to the main thread, so anything registered in response to it lands at least one frame after the socket is live. The server, meanwhile, sends map information right after the player enters the game. The handlers registered "on connect" raced that first message and lost it, silently, sometimes.

What a build of the client can decode is a property of the protocol, not of which component happens to have started. All parsers are registered on the connection object before it connects, in one place shared by the gateway and game connections; the components only attach their behaviour later.

Enregistrer les analyseurs avant de se connecter

L'événement « connecté » est lui-même différé vers le thread principal : tout ce qui est enregistré en réponse arrive au moins une image après que la socket est vivante. Le serveur, lui, envoie les informations de carte juste après l'entrée en jeu. Les gestionnaires enregistrés « à la connexion » faisaient la course avec ce premier message et la perdaient, en silence, parfois.

Ce qu'une version du client sait décoder est une propriété du protocole, pas du composant qui a démarré le premier. Tous les analyseurs sont enregistrés sur l'objet de connexion avant la connexion, à un seul endroit partagé par les connexions gateway et jeu ; les composants n'attachent leur comportement que plus tard.

Discovering what you do not know yet

When a snapshot mentions an id the client has never seen, the client creates a placeholder and collects the id; after parsing the whole snapshot, it sends one Discover request for all the unknown ids at once. The answer carries each object's full description (chapter 4.2), and the object is built then. Types whose snapshot state already carries a catalog id (bullets, missiles, asteroids, debris) never need that round trip.

One consequence took a while to get right: "this ship is mine" is state, re-affirmed by every snapshot, but on the client it had been implemented as an edge, a promotion done once when the id changed.

Pitfall I hit

The client attached the "player ship controller" (the component that sends ship inputs) when the id of the self ship changed. Two things defeated it. Docking removes the ship from every snapshot, so after the grace period the client lowered its "I have a ship" flag, and when undocking the promotion did not happen again. And the id was recorded even when the promotion had not happened yet (the ship not created yet, its description still in flight), so on the next snapshot the ids matched and the condition could never become true again. Symptom: you undock, the ship is there, and your inputs go nowhere for a few seconds. The fix re-affirms instead of detecting: the promotion is idempotent and runs on every snapshot, and the id is only recorded once the ship really exists.

Rule

If the wire repeats a fact every tick, apply it every tick; do not turn it into a one-time transition on the client.

A transition you detect can be missed; a state you re-apply cannot. Idempotent re-application costs a lookup and removes a whole family of ordering bugs.

Découvrir ce qu'on ne connaît pas encore

Quand un snapshot mentionne un identifiant que le client n'a jamais vu, le client crée une ébauche et note l'identifiant ; après avoir analysé tout le snapshot, il envoie une seule requête Discover pour tous les identifiants inconnus. La réponse porte la description complète de chaque objet (chapitre 4.2), et l'objet est construit à ce moment-là. Les types dont l'état porte déjà un identifiant de catalogue (balles, missiles, astéroïdes, débris) n'ont jamais besoin de cet aller-retour.

Une conséquence a mis du temps à être juste : « ce vaisseau est le mien » est un état, réaffirmé par chaque snapshot, mais côté client il avait été implémenté comme un front, une promotion faite une fois quand l'identifiant changeait.

Piège rencontré

Le client attachait le « contrôleur de vaisseau joueur » (le composant qui envoie les commandes du vaisseau) quand l'identifiant du vaisseau à soi changeait. Deux choses l'ont désarmé. S'amarrer retire le vaisseau de tous les snapshots : après la grâce, le client baissait son drapeau « j'ai un vaisseau », et au désamarrage la promotion n'avait plus lieu. Et l'identifiant était noté même quand la promotion n'avait pas encore eu lieu (vaisseau pas encore créé, description encore en vol) : au snapshot suivant les identifiants étaient égaux, et la condition ne pouvait plus jamais redevenir vraie. Symptôme : on se désamarre, le vaisseau est là, et les commandes ne partent nulle part pendant quelques secondes. La correction réaffirme au lieu de détecter : la promotion est idempotente et tourne à chaque snapshot, et l'identifiant n'est noté qu'une fois le vaisseau réellement présent.

Règle

Si le fil répète un fait à chaque tick, l'appliquer à chaque tick ; ne pas en faire une transition unique côté client.

Une transition qu'on détecte peut être manquée ; un état qu'on réapplique ne le peut pas. La réapplication idempotente coûte une recherche et supprime toute une famille de bugs d'ordre.

One way out of the scene

An object leaves the client's scene for two reasons: the server said it is gone, or it has not been seen for the grace period. Both go through a single "forget" function, and that function is idempotent, because both triggers can fire for the same id (the server repeats its announcement three times, and the grace may expire in between). Everything that must happen on removal lives there: despawning the game object, clearing the "my character" and "my ship" references so the player controller never holds a destroyed object, and removing the id from every bookkeeping dictionary. Two removal paths that differed by one line would guarantee that, one day, one of them forgets to lower a flag.

Une seule sortie de scène

Un objet quitte la scène du client pour deux raisons : le serveur a dit qu'il est parti, ou il n'a pas été vu pendant la durée de grâce. Les deux passent par une seule fonction « oublier », et cette fonction est idempotente, parce que les deux déclencheurs peuvent viser le même identifiant (le serveur répète son annonce trois fois, et la grâce peut expirer entre-temps). Tout ce qui doit se passer au retrait vit là : détruire l'objet de jeu, effacer les références « mon personnage » et « mon vaisseau » pour que le contrôleur du joueur ne tienne jamais un objet détruit, et retirer l'identifiant de chaque dictionnaire de suivi. Deux chemins de retrait qui différeraient d'une ligne garantiraient qu'un jour, l'un d'eux oublie de baisser un drapeau.

Loading screens that mean something

A loading screen is a promise: when it disappears, the world is ready. MoonQwak's arrival phase (chapter 2.2) makes that promise checkable. The client keeps its loading screen until the map description has been applied, then reports "map ready" from a finally block, so the report goes out even if one piece failed to apply. Only then does the server put the player's ship in the world and start sending snapshots. A map transition on the same server replays the same phase without reconnecting (chapter 2.3).

Disconnections need the same care, because "the game server closed my connection" can mean two opposite things:

  • Expected: the client is leaving on purpose (a transition to another server, quitting). A flag is set before closing so the handler knows.
  • Unexpected: a kick (a new login elsewhere) or a dead server. The client waits two seconds before concluding: a transition whose "you are moving" message was lost looks exactly like a dry disconnect, but the gateway's separate connection will deliver the new address right after. If no new connection appeared, the client clears the world (whose objects live outside the scene and would otherwise stay on screen), shows an explanation, and returns to character selection. Never a client frozen in a dead world.

The handler also captures which connection it belongs to. A connection that was already replaced (after a transition) and dies late must not tear down the current session.

Des écrans de chargement qui veulent dire quelque chose

Un écran de chargement est une promesse : quand il disparaît, le monde est prêt. La phase d'arrivée de MoonQwak (chapitre 2.2) rend cette promesse vérifiable. Le client garde son écran de chargement jusqu'à ce que la description de la carte soit appliquée, puis annonce « carte prête » depuis un bloc finally, pour que l'annonce parte même si un morceau n'a pas pu s'appliquer. Ce n'est qu'alors que le serveur met le vaisseau du joueur dans le monde et commence à envoyer des snapshots. Une transition vers une carte du même serveur rejoue la même phase sans reconnexion (chapitre 2.3).

Les déconnexions demandent le même soin, parce que « le serveur de jeu a fermé ma connexion » peut vouloir dire deux choses opposées :

  • Attendue : le client part exprès (transition vers un autre serveur, fermeture du jeu). Un drapeau est posé avant la fermeture pour que le gestionnaire le sache.
  • Inattendue : une éjection (une nouvelle connexion ailleurs) ou un serveur mort. Le client attend deux secondes avant de conclure : une transition dont le message « tu changes de serveur » s'est perdu ressemble exactement à une coupure sèche, mais la connexion séparée de la gateway livrera la nouvelle adresse juste après. Si aucune nouvelle connexion n'est apparue, le client nettoie le monde (dont les objets vivent hors de la scène et resteraient sinon à l'écran), affiche une explication, et revient à la sélection de personnage. Jamais un client figé dans un monde mort.

Le gestionnaire retient aussi à quelle connexion il appartient. Une connexion déjà remplacée (après une transition) qui meurt en retard ne doit pas démonter la session courante.

In MoonQwak

The shared network library cannot reference Unity, so it logs through a static hook that defaults to the console. In Unity the console output goes to a log file nobody watches: a dropped packet reported there is the same as not reported. The client points the hook at Unity's warning log at startup. The messages are then written from the network thread, and Unity's warning log is one of the few Unity calls that are safe off the main thread.

Dans MoonQwak

La bibliothèque réseau partagée ne peut pas référencer Unity : elle journalise par un crochet statique qui écrit par défaut sur la console. Dans Unity, la sortie console part dans un fichier de journal que personne ne regarde : un paquet perdu signalé là, c'est un paquet non signalé. Le client branche le crochet sur le journal d'avertissements d'Unity au démarrage. Les messages sont ensuite écrits depuis le thread réseau, et le journal d'avertissements d'Unity fait partie des rares appels Unity sûrs hors du thread principal.

Key takeaways

  • Marshal network work onto the main thread through a queue drained under a per-frame budget that always makes progress.
  • Coalesce full-state messages such as snapshots into "keep the newest"; queue only events.
  • Register every parser before connecting; decoding is a property of the protocol.
  • Batch requests for unknown objects, and re-apply facts the wire repeats instead of detecting transitions.
  • Give objects a single idempotent exit, make loading screens a checkable promise, and distinguish expected from unexpected disconnects.

À retenir

  • Faire passer le travail réseau au thread principal par une file vidée sous un budget par image qui progresse toujours.
  • Fusionner les messages d'état complet comme les snapshots en « garder le plus récent » ; ne mettre en file que les événements.
  • Enregistrer chaque analyseur avant de se connecter ; le décodage est une propriété du protocole.
  • Grouper les demandes d'objets inconnus, et réappliquer les faits que le fil répète au lieu de détecter des transitions.
  • Donner aux objets une sortie unique et idempotente, faire des écrans de chargement une promesse vérifiable, et distinguer les déconnexions attendues des inattendues.

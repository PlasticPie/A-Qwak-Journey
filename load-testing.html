What a load test must load

The first stress tool of the project spawned a hundred NPCs on a map. It loaded the physics and the AI, and it taught a lot (chapter 10.4), but it touched nothing that costs per player: serializing a snapshot for each viewer, querying the interest grid for each peer, the bytes going out. A hundred NPCs are one connected peer. What decides the size of an MMO server is the second list, so the real load tool had to be made of real clients.

Each bot runs a complete session, in the same order as the game client: through the gateway, register, log in, list or create a character, select it and receive the game server's address and a token for it; then on the game server, enter the game, receive the map description, answer that it is ready, and send inputs at 20 Hz, forever. Same protocol, same encryption, same handshakes (chapters 2.2 and 2.3).

Ce qu'un test de charge doit charger

Le premier outil de stress du projet faisait apparaître une centaine de PNJ sur une carte. Il chargeait la physique et l'IA, et il a beaucoup appris (chapitre 10.4), mais il ne touchait à rien de ce qui coûte par joueur : sérialiser un snapshot pour chaque spectateur, interroger la grille d'intérêt pour chaque pair, les octets qui sortent. Cent PNJ, c'est un seul pair connecté. Ce qui décide de la taille d'un serveur de MMO, c'est la seconde liste : le vrai outil de charge devait donc être fait de vrais clients.

Chaque bot déroule une session complète, dans le même ordre que le client de jeu : par la gateway, s'inscrire, se connecter, lister ou créer un personnage, le sélectionner et recevoir l'adresse du serveur de jeu et un jeton pour s'y connecter ; puis sur le serveur de jeu, entrer en jeu, recevoir la description de la carte, répondre qu'il est prêt, et envoyer des entrées à 20 Hz, pour toujours. Même protocole, même chiffrement, mêmes poignées de main (chapitres 2.2 et 2.3).

負載測試必須加載什麼

專案的第一個壓力工具是在一張地圖上產生一百個 NPC。它加載了物理與 AI，也教會了我很多（第 10.4 章），但它完全沒碰到以每位玩家計的成本：為每位觀察者序列化一份快照、為每個端點查詢興趣網格、送出去的位元組。一百個 NPC 只是一個已連線的端點。決定一台 MMO 伺服器規模的是第二份清單，所以真正的負載工具必須由真實的用戶端組成。

每個機器人都執行一個完整的連線階段，順序與遊戲用戶端相同：經過閘道註冊、登入、列出或建立角色、選擇它，並收到遊戲伺服器的位址與一個給它用的權杖；然後在遊戲伺服器上進入遊戲、收到地圖描述、回覆已準備好，並以 20 Hz 送出輸入，永不停止。同樣的協定、同樣的加密、同樣的交握（第 2.2 與 2.3 章）。

Two decisions in how bots are built are worth borrowing:

  • Accounts are created through the gateway, not written into the database. The bench is allowed to write to the database (these are test accounts), but the password hash belongs to the gateway. Re-implementing it in the bench would create a second truth, diverging at the first change of algorithm, for the price of one registration round trip in the life of an account. What the bench does write is pure data: a combat hull, and the admin and invulnerability flags. The admin flag is never grantable from inside the game ("a privilege the game can grant is a privilege an exploit can grant itself"); it is set by hand in the database, and the load tool is that hand. Nothing on the server side gains the power to promote itself.
  • Bots do not decode snapshots. They receive them and throw them away. No world model, no state. The bench runs on the machine that hosts the servers it measures, and parsing hundreds of snapshot streams would take the CPU of the very thing being measured. A load tool must stay light enough not to become the load.

Deux décisions dans la construction des bots méritent d'être reprises :

  • Les comptes sont créés par la gateway, pas écrits en base. Le banc a le droit d'écrire en base (ce sont des comptes de test), mais le hachage du mot de passe appartient à la gateway. Le réimplémenter dans le banc créerait une seconde vérité, qui divergerait au premier changement d'algorithme, pour le prix d'un aller-retour d'inscription dans la vie d'un compte. Ce que le banc écrit vraiment, c'est de la donnée pure : une coque de combat, et les drapeaux d'administrateur et d'invulnérabilité. Le drapeau d'administrateur n'est jamais accordable depuis le jeu (« un privilège que le jeu peut accorder est un privilège qu'un exploit peut s'accorder ») ; il se pose à la main en base, et l'outil de charge est cette main. Rien côté serveur ne gagne le pouvoir de se promouvoir.
  • Les bots ne décodent pas les snapshots. Ils les reçoivent et les jettent. Aucun modèle du monde, aucun état. Le banc tourne sur la machine qui héberge les serveurs qu'il mesure, et analyser des centaines de flux de snapshots prendrait le CPU de la chose même qu'on mesure. Un outil de charge doit rester assez léger pour ne pas devenir la charge.

機器人的打造方式中，有兩個決定值得借鏡：

  • 帳號透過閘道建立，而不是直接寫進資料庫。測試台被允許寫入資料庫（這些是測試帳號），但密碼雜湊屬於閘道。在測試台中重新實作它，會產生第二個真相，在演算法第一次改變時就會分歧，而這只為了省下一個帳號一生中一次的註冊往返。測試台確實會寫入的是純資料：一個戰鬥用船體，以及管理員與無敵旗標。管理員旗標永遠不能從遊戲內部授予（「一個遊戲能授予的權限，就是一個漏洞能授予自己的權限」）；它是在資料庫中手動設定的，而負載工具就是那隻手。伺服器端沒有任何東西因此獲得提升自己權限的能力。
  • 機器人不解碼快照。它們收下快照，然後丟掉。沒有世界模型、沒有狀態。測試台在託管它所量測之伺服器的同一台機器上執行，而解析數百條快照串流，會吃掉被量測對象本身的 CPU。負載工具必須保持夠輕，才不會自己變成負載。

Measure a plateau, not an arrival storm

A number read during a load test is only meaningful if the load was steady when it was read. Several settings exist only to make that true:

  • A ramp. Bots connect one every 250 ms by default. A hundred clients at once measure the arrival storm (logins, character loads, first snapshots), not the steady state. Both are interesting, but not at the same time.
  • Invulnerable bots. Twenty armed bots crossing NPCs die within minutes, respawn docked, and never come out again: the population melts during the measurement, and the report describes a map emptying itself. By default bots cannot be damaged, so the number of peers, the interest sets and the snapshot sizes stay constant. A second mode runs the full damage path (hull loss, debris, wrecks, death), knowing the load will decay.
  • Confinement. A server switch closes the map's borders. Without it, bots fly straight ahead, cross borders within seconds, spread over neighbouring maps, and the bench measures map transitions instead of density.
  • Destinations instead of wandering. The first bots changed heading at random every few seconds, a random walk, and a random walk diffuses: that is its definition. One bench ended with 700 bots on 373 occupied maps, 1.6 players per map.

That last one changed what the bench could answer. A server pays for two things, and neither depends on how smart the bots are: maps (each live map is a full physics world, with a hard limit of about 120 per process) and neighbourhoods (a snapshot costs in proportion to what is in view; ten players who see each other are a hundred relations). A bench that disperses measures only the first: "how many empty worlds can a process hold", never "how many players can a battle hold", which is the question that sizes a server. So bots now fly towards a few hubs, linger, and leave for another: a random walk with a drift. Few hubs make crowds; many hubs make dispersion. Players per map stopped being an accident and became a dial.

Pitfall I hit

The first hub version seeded the bots on the hubs: a thousand bots on three maps. A map lives on exactly one server (chapter 7.1), so the fleet could not spread that load: two reinforcement servers started, received zero maps, and stayed empty. Bots are now seeded within a radius around the hubs, and the bench warns when fewer than ten starting maps exist, because the fleet cannot split the load into more pieces than it is given.

Mesurer un plateau, pas une tempête d'arrivée

Un chiffre lu pendant un test de charge n'a de sens que si la charge était stable au moment de la lecture. Plusieurs réglages n'existent que pour que ce soit vrai :

  • Une rampe. Les bots se connectent un toutes les 250 ms par défaut. Cent clients d'un coup mesurent la tempête d'arrivée (connexions, chargements de personnages, premiers snapshots), pas le régime établi. Les deux sont intéressants, mais pas en même temps.
  • Des bots invulnérables. Vingt bots armés qui croisent des PNJ meurent en quelques minutes, réapparaissent à quai, et n'en ressortent plus : la population fond pendant la mesure, et le rapport décrit une carte qui se vide. Par défaut, les bots ne peuvent pas subir de dégâts : le nombre de pairs, les ensembles d'intérêt et la taille des snapshots restent constants. Un second mode suit le chemin de dégâts complet (perte d'hex, débris, épaves, mort), en sachant que la charge va décroître.
  • Le confinement. Un interrupteur du serveur ferme les bords de la carte. Sans lui, les bots volent tout droit, franchissent des bords en quelques secondes, se répandent sur les cartes voisines, et le banc mesure des changements de carte au lieu de la densité.
  • Des destinations au lieu de l'errance. Les premiers bots changeaient de cap au hasard toutes les quelques secondes, une marche aléatoire, et une marche aléatoire diffuse : c'est sa définition. Un banc s'est terminé avec 700 bots sur 373 cartes occupées, 1,6 joueur par carte.

Ce dernier point a changé ce à quoi le banc pouvait répondre. Un serveur paie deux choses, et aucune ne dépend de l'intelligence des bots : les cartes (chaque carte vivante est un monde physique complet, avec une limite dure d'environ 120 par processus) et les voisinages (un snapshot coûte en proportion de ce qui est en vue ; dix joueurs qui se voient, ce sont cent relations). Un banc qui disperse ne mesure que le premier : « combien de mondes vides un processus peut-il tenir », jamais « combien de joueurs une bataille peut-elle tenir », qui est la question qui dimensionne un serveur. Les bots volent donc maintenant vers quelques pôles, s'y attardent, puis repartent vers un autre : une marche aléatoire avec dérive. Peu de pôles font des foules ; beaucoup de pôles font de la dispersion. Les joueurs par carte ont cessé d'être un accident pour devenir un cadran.

Piège rencontré

La première version des pôles semait les bots sur les pôles : mille bots sur trois cartes. Une carte vit sur exactement un serveur (chapitre 7.1) : le parc ne pouvait pas répartir cette charge. Deux serveurs de renfort ont démarré, n'ont reçu aucune carte, et sont restés vides. Les bots sont maintenant semés dans un rayon autour des pôles, et le banc prévient quand il existe moins de dix cartes de départ, parce que le parc ne peut pas découper la charge en plus de morceaux qu'on ne lui en donne.

量測平台期，而不是抵達風暴

負載測試中讀到的數字，只有在讀取時負載是穩定的情況下才有意義。有好幾項設定的存在，只是為了讓這件事成立：

  • 爬升。機器人預設每 250 ms 連線一個。一百個用戶端同時連線，量到的是抵達風暴（登入、角色載入、第一份快照），而不是穩定狀態。兩者都很有趣，但不能同時量。
  • 無敵的機器人。二十個武裝機器人遇上 NPC，幾分鐘內就會死光，在停靠狀態下重生，再也不出來：人口在量測期間融化，報告描述的是一張正在自己清空的地圖。機器人預設無法受傷，所以端點數量、興趣集合與快照大小都保持不變。第二種模式則執行完整的傷害路徑（船體損失、碎片、殘骸、死亡），並知道負載會逐漸衰退。
  • 封閉。一個伺服器開關會關閉地圖的邊界。沒有它，機器人會直直往前飛，幾秒內就越過邊界、分散到鄰近的地圖上，測試台量到的就是地圖切換，而不是密度。
  • 目的地，而不是漫遊。第一批機器人每隔幾秒就隨機改變航向，也就是隨機漫步，而隨機漫步會擴散：這就是它的定義。有一次測試台結束時，700 個機器人分布在 373 張有人的地圖上，每張地圖 1.6 位玩家。

最後這一項改變了測試台能回答的問題。伺服器要為兩件事付費，而兩者都與機器人有多聰明無關：地圖（每張存活的地圖都是一個完整的物理世界，每個程序有約 120 張的硬性上限）與鄰里（一份快照的成本與視野內的東西成正比；十位彼此看得見的玩家就是一百組關係）。一個會分散的測試台只能量到前者：「一個程序能容納多少個空世界」，而永遠量不到「一場戰鬥能容納多少位玩家」，而後者才是決定伺服器規模的問題。所以機器人現在會飛向少數幾個集結點，停留一會兒，再前往另一個：一個帶有漂移的隨機漫步。集結點少就形成人潮；集結點多就造成分散。每張地圖的玩家數不再是意外，而變成了一個旋鈕。

我踩過的坑

集結點的第一版把機器人直接產生在集結點上：一千個機器人在三張地圖上。一張地圖恰好存在於一台伺服器上（第 7.1 章），所以叢集無法分散這個負載：啟動了兩台支援伺服器，收到零張地圖，一直保持空的。現在機器人會被產生在集結點周圍一定半徑內，而當起始地圖少於十張時，測試台會發出警告，因為叢集無法把負載切成比它拿到的還多的塊。

A bench that fabricates its own failures

The hardest lesson of load testing is that the bench runs on a real machine, often the same one as the server, and it can fail in ways that look exactly like the server failing. Each of the following was, at first, reported as a server problem:

Un banc qui fabrique ses propres pannes

La leçon la plus dure des tests de charge est que le banc tourne sur une vraie machine, souvent la même que le serveur, et qu'il peut échouer de façons qui ressemblent exactement à une panne du serveur. Chacun des cas suivants a d'abord été rapporté comme un problème de serveur :

自己製造故障的測試台

負載測試最難的一課是：測試台在一台真實的機器上執行，往往就是伺服器所在的那一台，而它可能以看起來和伺服器故障一模一樣的方式失敗。以下每一項，一開始都被當成伺服器的問題回報：

  1. prioritypriorité優先權

    Bots stealing the server's CPUDes bots qui volent le CPU du serveur機器人偷走伺服器的 CPU

    400 bots are 400 to 800 network threads waking up constantly. At equal priority they take scheduler quanta from the tick thread, and the monitor headlined "worst tick 239 ms" for 28 ms of actual work. The bench now runs below normal priority by default: the server goes first, since it is what is being measured. Normal priority remains available, to measure behaviour under contention, which is a different question.400 bots, ce sont 400 à 800 threads réseau qui se réveillent sans arrêt. À priorité égale, ils prennent des quanta d'ordonnancement au thread de tick, et le moniteur titrait « pire tick 239 ms » pour 28 ms de travail réel. Le banc tourne maintenant en priorité sous la normale par défaut : le serveur passe d'abord, puisque c'est lui qu'on mesure. La priorité normale reste disponible, pour mesurer la tenue sous contention, qui est une autre question.400 個機器人就是 400 到 800 條不斷被喚醒的網路執行緒。在同等優先權下，它們會從 tick 執行緒手上搶走排程時間片，而監控器的標題寫著「最差 tick 239 ms」，實際工作卻只有 28 ms。現在測試台預設以低於一般的優先權執行：伺服器先走，因為它才是被量測的對象。一般優先權仍然可用，用來量測競爭下的行為，那是另一個問題。

  2. threadsthreads執行緒

    1,400 threads to read 700 bots1 400 threads pour lire 700 bots用 1,400 條執行緒讀 700 個機器人

    Each connection had its own polling thread, two per bot: 1,400 threads, each woken every 15 ms. The scheduler could not keep up, bots were disconnected for not being read in time, and the report said "640 × GameServer: Timeout", as if the server had given up. A few pump threads (a quarter of the cores, at least two) now read all sockets in slices, and each connection is read hundreds of times per second.Chaque connexion avait son propre thread d'écoute, deux par bot : 1 400 threads, chacun réveillé toutes les 15 ms. L'ordonnanceur ne suivait pas, les bots étaient déconnectés faute d'être lus à temps, et le rapport affichait « 640 × GameServer : Timeout », comme si le serveur avait lâché. Quelques threads de pompe (un quart des cœurs, au moins deux) lisent maintenant toutes les sockets par tranches, et chaque connexion est lue des centaines de fois par seconde.每條連線都有自己的輪詢執行緒，每個機器人兩條：1,400 條執行緒，每一條每 15 ms 被喚醒一次。排程器跟不上，機器人因為沒有及時被讀取而斷線，而報告寫著「640 × GameServer: Timeout」，彷彿是伺服器放棄了。現在由少數幾條泵執行緒（核心數的四分之一，至少兩條）分片讀取所有 socket，每條連線每秒被讀取數百次。

  3. fairnesséquité公平性

    One busy socket starving 279 othersUne socket occupée qui affame les 279 autres一個忙碌的 socket 餓死其他 279 個

    With shared pumps, the transport library's default let one poll swallow 256 packets in a row. A bot that had just changed maps received a discovery burst and a 15 KB first snapshot; its queue was the only full one, and it ate the turn of the 279 others, which fell behind in turn. Measured: 47,000 pump passes per second at rest, 318 at the first map change, zero three seconds later, without a single exception. A cap of eight packets per poll and per connection loses nothing (what is not read this turn is read on the next) and ends the cascade.Avec des pompes partagées, le défaut de la bibliothèque de transport laissait un seul relevé avaler 256 paquets d'affilée. Un bot qui venait de changer de carte recevait une rafale de découverte et un premier snapshot de 15 Ko ; sa file était la seule pleine, et elle mangeait le tour des 279 autres, qui prenaient du retard à leur tour. Mesuré : 47 000 passes de pompe par seconde au repos, 318 au premier changement de carte, zéro trois secondes plus tard, sans une seule exception. Un plafond de huit paquets par relevé et par connexion ne perd rien (ce qui n'est pas lu à ce tour l'est au suivant) et met fin à la cascade.使用共用的泵之後，傳輸函式庫的預設值允許一次輪詢連續吞下 256 個封包。一個剛換了地圖的機器人收到一波探索封包與一份 15 KB 的第一份快照；它的佇列是唯一滿的，它吃掉了其他 279 個的回合，而那些又輪流落後。實測：閒置時每秒 47,000 輪泵，第一次換地圖時 318 輪，三秒後歸零，而且沒有任何一個例外。每次輪詢、每條連線上限八個封包，不會遺失任何東西（這一輪沒讀到的，下一輪會讀），並終結了這場連鎖反應。

  4. patiencepatience耐心

    A bench more impatient than the clientUn banc plus impatient que le client一個比用戶端更沒耐心的測試台

    On a map change, the game server drops the old connection 300 ms after announcing the transition, betting that the new one is already up. The bet can lose when the destination map must first be loaded somewhere. The real client knows this and concludes nothing for two seconds; the bench concluded within a millisecond, and reported 136 desertions that never happened. It now waits the same two seconds. A bench more impatient than the client it simulates measures its own impatience.Lors d'un changement de carte, le serveur de jeu coupe l'ancienne connexion 300 ms après avoir annoncé la transition, en pariant que la nouvelle est déjà établie. Le pari peut se perdre quand la carte de destination doit d'abord être chargée quelque part. Le vrai client le sait et ne conclut rien pendant deux secondes ; le banc concluait en une milliseconde, et rapportait 136 désertions qui n'avaient jamais eu lieu. Il attend maintenant les mêmes deux secondes. Un banc plus impatient que le client qu'il simule mesure sa propre impatience.換地圖時，遊戲伺服器在宣告切換 300 ms 後就丟掉舊的連線，賭新的連線已經建立好了。當目的地地圖必須先在某處載入時，這個賭注可能會輸。真正的用戶端知道這一點，兩秒內不做任何結論；測試台卻在一毫秒內就下了結論，回報了 136 次從未發生的脫隊。現在它也等同樣的兩秒。一個比它所模擬的用戶端更沒耐心的測試台，量到的是它自己的不耐煩。

  5. accountscomptes帳號

    Two benches kicking each otherDeux bancs qui s'éjectent l'un l'autre兩個互踢的測試台

    The server ends the previous session whenever an account logs in again (chapter 2.2). Two people running the bench with the same account prefix drive the same accounts, kick each other in a loop, and the population never holds, which looks exactly like a server that cannot cope. The launcher script now asks each person for a unique prefix.Le serveur met fin à la session précédente chaque fois qu'un compte se reconnecte (chapitre 2.2). Deux personnes qui lancent le banc avec le même préfixe de comptes pilotent les mêmes comptes, s'éjectent l'une l'autre en boucle, et la population ne tient jamais, ce qui ressemble exactement à un serveur qui ne suit pas. Le script de lancement demande maintenant à chacun un préfixe unique.只要一個帳號再次登入，伺服器就會結束先前的連線階段（第 2.2 章）。兩個人用同樣的帳號前綴執行測試台，驅動的是同樣的帳號，在迴圈中互踢，人口永遠撐不住，看起來就和一台應付不了的伺服器一模一樣。現在啟動指令碼會要求每個人提供一個獨一無二的前綴。

  6. databasebase資料庫

    Setup written into the wrong databaseUne préparation écrite dans la mauvaise base設定寫進了錯誤的資料庫

    Before connecting, the bench writes to the database named in its own configuration: account flags, the combat hull, the hubs. Against a remote server, that can be a different database. The writes then succeed, in the wrong place, and the bots arrive mortal and unarmed without a line saying so. The bench cannot check that the two databases are the same, so it says so out loud when the target is remote.Avant de se connecter, le banc écrit dans la base nommée par sa propre configuration : drapeaux des comptes, coque de combat, pôles. Contre un serveur distant, ce peut être une autre base. Les écritures réussissent alors, au mauvais endroit, et les bots arrivent mortels et désarmés sans qu'une ligne le dise. Rule

Before blaming the server, prove the bench is not the bottleneck: its priority, its threads, its fairness, its patience and its setup.

Règle

Avant d'accuser le serveur, prouver que le banc n'est pas le goulot : sa priorité, ses threads, son équité, sa patience et sa préparation.

規則

在怪罪伺服器之前，先證明測試台不是瓶頸：它的優先權、它的執行緒、它的公平性、它的耐心，以及它的設定。

A bench needs its own instruments, precisely to tell its failures from the server's. The load tool prints one status line per second, deliberately short: how many bots are in the world, connecting or failed, and why; snapshots received per second; and three numbers about itself that settle the ambiguous cases:

Measured

The verdict of a load test is not in the bench's output. The numbers that matter (tick work, snapshot build, bytes out, connected peers, GC pauses) are measured on the server and read in the monitor (chapter 10.1). The bench only has to prove that the load it claims is the load the server received.

Un banc a besoin de ses propres instruments, justement pour distinguer ses pannes de celles du serveur. Mesuré

Le verdict d'un test de charge n'est pas dans la sortie du banc. Les chiffres qui comptent (travail du tick, construction des snapshots, octets sortants, pairs connectés, pauses du GC) sont mesurés sur le serveur et lus dans le moniteur (chapitre 10.1). Le banc n'a qu'à prouver que la charge qu'il annonce est bien celle que le serveur a reçue.

Map changes: a latency, not a rate

Moving a bot to another map means closing one connection and opening another: joining the transport library's internal thread, binding a socket, a handshake. Getting this right cost three benches, and the story is a good lesson about throttles.

  1. 1

    Inline on the pump

    The move ran on the pump thread that also reads 140 other bots. A wave of map changes froze 140 sockets at once, including those of bots waiting for their own reconnection message: the "connecting" counter climbed and never came down. Moves now run on one dedicated thread.

  2. 2

    A fixed gap

    Paced at 40 moves per second, one every 25 ms. Perfect with three in the queue, deadly with twenty-seven: the last one waited 675 ms, and the server drops the old connection 300 ms after announcing the move. The pacing meant to protect the server condemned half the queue.

  3. 3

    A gap that shrinks without limit

    Now the rule was a latency: the last in the queue must leave within 200 ms (the server's 300 ms, minus the cost of the move itself). At 67 pending, the gap fell to 3 ms, about 300 connection teardowns and rebuilds per second, each joining and recreating a thread. The server printed a slow tick of 1,111.8 ms, 1,108.8 of them preparing snapshots, for 0.0 ms of CPU: it was starved of threads, not busy. Worse, it looped: the storm froze the server, the freeze lengthened the queue, the queue shortened the gap, the gap fed the storm.

  4. 4

    A latency with a floor

    The gap aims at the 200 ms budget for the whole queue, but never drops below 10 ms: at most 100 moves per second, whatever happens to the queue. Below that floor, the bench would be measuring the scheduler.

Changements de carte : une latence, pas un débit

Déplacer un bot vers une autre carte, c'est fermer une connexion et en ouvrir une autre : joindre le thread interne de la bibliothèque de transport, lier une socket, une poignée de main. Le faire correctement a coûté trois bancs, et l'histoire est une bonne leçon sur les limiteurs de débit.

  1. 1

    En ligne sur la pompe

    Le déménagement tournait sur le thread de pompe qui lit aussi 140 autres bots. Une vague de changements de carte gelait 140 sockets d'un coup, y compris celles des bots qui attendaient leur propre message de reconnexion : le compteur « en cours » montait et ne redescendait jamais. Les déménagements tournent maintenant sur un thread dédié.

  2. 2

    Un intervalle fixe

    Cadencé à 40 déménagements par seconde, un toutes les 25 ms. Parfait avec trois en file, mortel avec vingt-sept : le dernier attendait 675 ms, et le serveur coupe l'ancienne connexion 300 ms après avoir annoncé le déménagement. La cadence censée protéger le serveur condamnait la moitié de la file.

  3. 3

    Un intervalle qui rétrécit sans limite

    La règle devenait une latence : le dernier de la file doit partir en moins de 200 ms (les 300 ms du serveur, moins le coût du déménagement lui-même). À 67 en attente, l'intervalle tombait à 3 ms, environ 300 fermetures et reconstructions de connexion par seconde, chacune joignant et recréant un thread. Le serveur imprimait un tick lent de 1 111,8 ms, dont 1 108,8 à préparer les snapshots, pour 0,0 ms de CPU : il manquait de threads, il n'était pas occupé. Pire, cela bouclait : la tempête gelait le serveur, le gel allongeait la file, la file raccourcissait l'intervalle, l'intervalle nourrissait la tempête.

  4. 4

    Une latence avec un plancher

    L'intervalle vise le budget de 200 ms pour toute la file, mais ne descend jamais sous 10 ms : au plus 100 déménagements par seconde, quoi qu'il arrive à la file. Sous ce plancher, le banc mesurerait l'ordonnanceur.

換地圖：是延遲，而不是頻率

把一個機器人移到另一張地圖，意味著關閉一條連線並開啟另一條：匯合傳輸函式庫的內部執行緒、繫結一個 socket、一次交握。把這件事做對花了三次測試台，而這段故事是關於節流的好教訓。

  1. 1

    直接在泵上執行

    移動在同時還要讀取另外 140 個機器人的泵執行緒上執行。一波換地圖同時凍結了 140 個 socket，包括那些正在等待自己重新連線訊息的機器人：「連線中」計數器一路攀升，再也沒有下降。現在移動在一條專屬的執行緒上執行。

  2. 2

    固定的間隔

    以每秒 40 次移動的速度進行，每 25 ms 一次。佇列裡有三個時完美，有二十七個時致命：最後一個等了 675 ms，而伺服器在宣告移動 300 ms 後就會丟掉舊的連線。本來要保護伺服器的節流，讓佇列的一半被判了死刑。

  3. 3

    無限制縮短的間隔

    現在規則變成了一個延遲：佇列中的最後一個必須在 200 ms 內離開（伺服器的 300 ms，減去移動本身的成本）。有 67 個待處理時，間隔降到 3 ms，每秒約 300 次連線拆除與重建，每一次都要匯合並重建一條執行緒。伺服器印出一個 1,111.8 ms 的慢 tick，其中 1,108.8 ms 在準備快照，而 CPU 是 0.0 ms：它被餓死了執行緒，而不是忙碌。更糟的是，它形成了迴圈：風暴讓伺服器凍結，凍結讓佇列變長，佇列讓間隔變短，間隔又餵養了風暴。

  4. 4

    有下限的延遲

    間隔以整個佇列 200 ms 的預算為目標，但絕不低於 10 ms：無論佇列發生什麼事，每秒最多 100 次移動。低於這個下限，測試台量到的就是排程器了。

Qwak.LoadTest/Program.cs · the transition gap
const int TransitionBudgetMs = 200;  // the server's 300 ms grace, minus the move itself
const int TransitionFloorMs  = 10;   // never more than 100 moves per second

// Count first: the gap is chosen for the whole queue, not recomputed per departure.
var gap = pending > 1
    ? Math.Max(TransitionFloorMs,  // the floor always wins
               Math.Min(transitionGapMs, TransitionBudgetMs / pending))
    : transitionGapMs;  // 25 ms at the default 40/s

One more observation made the whole problem smaller: 700 bots changing maps in the same second do not exist. They all start from the same spawn area and reach the borders in waves, an artifact of the bench, not a load a real population produces. Spreading them measures the right regime. The rate can still be raised on purpose to test a genuine burst (a whole fleet jumping together does exist), but that is a different experiment.

Rule

A throttle that protects a deadline must be expressed as a latency, and bounded by a floor.

A fixed rate misses the deadline under bursts; an unbounded latency target turns a burst into a storm. A fix that feeds itself is worse than the defect it replaces, because it has no point of equilibrium.

Une observation de plus a rendu tout le problème plus petit : 700 bots qui changent de carte à la même seconde, ça n'existe pas. Ils partent tous de la même zone d'apparition et atteignent les bords par vagues, un artefact du banc, pas une charge que produit une vraie population. Les étaler, c'est mesurer le bon régime. La cadence peut toujours être montée exprès pour tester une vraie rafale (une flotte entière qui saute ensemble, ça existe), mais c'est une autre expérience.

Règle

Un limiteur qui protège une échéance doit s'exprimer en latence, et être borné par un plancher.

Un débit fixe rate l'échéance sous rafale ; une cible de latence sans borne transforme une rafale en tempête. Une correction qui s'auto-alimente est pire que le défaut qu'elle remplace, parce qu'elle n'a pas de point d'équilibre.

還有一個觀察讓整個問題變小了：700 個機器人在同一秒換地圖，這種事不存在。它們全都從同一個出生區域出發，成波地抵達邊界，這是測試台的人為現象，而不是真實人口會產生的負載。把它們分散開來，才能量到正確的情況。仍然可以刻意調高頻率來測試真正的突發（整支艦隊一起跳躍確實存在），但那是另一個實驗。

規則

保護一個截止期限的節流，必須以延遲來表達，並以一個下限為界。

固定的頻率在突發時會錯過截止期限；沒有界限的延遲目標會把突發變成風暴。一個會自我餵養的修正比它所取代的缺陷更糟，因為它沒有平衡點。

Benching from somewhere else

A local bench cannot measure the network: every packet goes through the loopback interface, with no latency, no loss and no upload limit. So the bench can also run from another machine, against the public address of the servers, and the launcher is a small script meant to be handed to a friend. It is written defensively, because its user will not have the code: no accented characters in the file (a script re-saved in the wrong encoding breaks at the first accented line, with a message that does not say why), quoted assignments (a trailing space would otherwise become part of the address, and an address with an invisible space at the end does not resolve), a unique account prefix, and "start small, then climb in steps". The target is given on the command line rather than in the shared configuration file, because a one-off test against another machine should die with its window instead of lingering in a file that three other processes read.

Tester depuis ailleurs

Un banc local ne peut pas mesurer le réseau : chaque paquet passe par l'interface de bouclage, sans latence, sans perte et sans limite de débit montant. Le banc peut donc aussi tourner depuis une autre machine, contre l'adresse publique des serveurs, et le lanceur est un petit script fait pour être confié à un ami. Il est écrit de façon défensive, parce que son utilisateur n'aura pas le code : aucun caractère accentué dans le fichier (un script réenregistré dans le mauvais encodage casse à la première ligne accentuée, avec un message qui ne dit pas pourquoi), des affectations entre guillemets (sinon une espace en fin de ligne ferait partie de l'adresse, et une adresse avec une espace invisible au bout ne se résout pas), un préfixe de comptes unique, et « commencer petit, puis monter par paliers ». La cible se donne sur la ligne de commande plutôt que dans le fichier de configuration partagé, parce qu'un essai ponctuel contre une autre machine doit mourir avec sa fenêtre au lieu de traîner dans un fichier que trois autres processus lisent.

從別的地方進行測試

本機的測試台無法量測網路：每個封包都經過迴路介面，沒有延遲、沒有遺失、沒有上傳限制。所以測試台也可以從另一台機器、對著伺服器的公開位址執行，而啟動器是一個小小的指令碼，用來交給朋友。它以防禦性的方式撰寫，因為它的使用者不會有程式碼：檔案中沒有帶重音的字元（一個被以錯誤編碼重新儲存的指令碼，會在第一個帶重音的那一行壞掉，而錯誤訊息不會說明原因）、指派加上引號（否則尾隨的空格會成為位址的一部分，而一個結尾帶著看不見之空格的位址無法解析）、獨一無二的帳號前綴，以及「從小規模開始，再一步步往上加」。目標是在命令列上給定的，而不是寫在共用的設定檔中，因為一次對另一台機器的一次性測試，應該隨著它的視窗一起消失，而不是逗留在一個另外三個程序都會讀取的檔案裡。

Key takeaways

  • Load what costs per player: bots must be real clients running full sessions over the real protocol.
  • Create accounts through the real entry point; write only pure data directly, and never grant privileges from inside the game.
  • Keep bots light: receive snapshots, never decode them, or the bench becomes the load.
  • Measure plateaus: ramp connections, keep the population alive, confine or concentrate it, and make players-per-map a setting.
  • Lower the bench's priority, share a few pump threads, cap per-poll work, and watch the bench's own thread count.
  • Be exactly as patient as the real client, and use unique account prefixes per bench.
  • Express throttles as latencies with a floor; a self-feeding fix has no equilibrium.

À retenir

  • Charger ce qui coûte par joueur : les bots doivent être de vrais clients qui déroulent des sessions complètes sur le vrai protocole.
  • Créer les comptes par le vrai point d'entrée ; n'écrire directement que de la donnée pure, et ne jamais accorder de privilèges depuis le jeu.
  • Garder les bots légers : recevoir les snapshots, ne jamais les décoder, sinon le banc devient la charge.
  • Mesurer des plateaux : étaler les connexions, garder la population en vie, la confiner ou la concentrer, et faire des joueurs par carte un réglage.
  • Baisser la priorité du banc, partager quelques threads de pompe, plafonner le travail par relevé, et surveiller le nombre de threads du banc lui-même.
  • Être exactement aussi patient que le vrai client, et utiliser des préfixes de comptes uniques par banc.
  • Exprimer les limiteurs en latences avec un plancher ; une correction qui s'auto-alimente n'a pas d'équilibre.

重點整理

  • 加載以每位玩家計的成本：機器人必須是透過真實協定執行完整連線階段的真實用戶端。
  • 透過真正的進入點建立帳號；只直接寫入純資料，而且絕不從遊戲內部授予權限。
  • 讓機器人保持輕量：收下快照，從不解碼，否則測試台就會變成負載。
  • 量測平台期：爬升式連線、讓人口存活、封閉或集中它，並讓每張地圖的玩家數成為一項設定。
  • 降低測試台的優先權、共用少數幾條泵執行緒、限制每次輪詢的工作量，並注意測試台自己的執行緒數。
  • 和真實的用戶端完全一樣有耐心，並為每個測試台使用獨一無二的帳號前綴。
  • 以帶有下限的延遲來表達節流；一個會自我餵養的修正沒有平衡點。

The map

MoonQwak runs as a small number of separate programs. Each one exists because it owns something the others should not touch, or because it has to keep running while the others restart. La carte

MoonQwak tourne sous la forme d'un petit nombre de programmes séparés. Chacun existe parce qu'il possède quelque chose que les autres ne doivent pas toucher, ou parce qu'il doit continuer de tourner pendant que les autres redémarrent. Rule

Every fact has exactly one writer: the process that observes it.

The gateway writes how many servers a world needs because it alone sees both hosted maps and waiting maps. Each node agent writes the CPU and RAM of its own machine because it alone runs there. The gateway writes each server's map and player counts because it alone routes them. When two processes could both write a value, they eventually write different ones.

Règle

Chaque fait a exactement un écrivain : le processus qui l'observe.

La gateway écrit combien de serveurs un monde demande, parce qu'elle seule voit à la fois les cartes hébergées et celles qui attendent. Chaque agent écrit le CPU et la RAM de sa machine, parce qu'il est le seul à y tourner. La gateway écrit les comptes de cartes et de joueurs de chaque serveur, parce qu'elle seule les route. Quand deux processus peuvent écrire la même valeur, ils finissent par en écrire deux différentes.

Where the truth lives

A distributed system is mostly a list of decisions about which copy of a fact is the real one. These are MoonQwak's:

  • The world's current state lives in the RAM of the game server hosting the map. The database is written afterwards, in the background, and is only read back when a map loads or a player connects. (6.1)
  • What the player sees is a copy, sent after each tick and always slightly old. The client predicts only its own character's walking and corrects it against the server. (5.3)
  • Sessions and presence live in the gateway's memory. A game server knows which players it hosts; only the gateway knows where everyone is.
  • Goods that change hands are the exception to "RAM first": a trade, a market purchase or a parcel is written to the database immediately, in one transaction. (6.2)
  • The fleet is described by three tables: machines and their capacity (entered by hand), the number of servers each world needs (written by the gateway), and the servers actually running (written by the agents). (7.2)

Où vit la vérité

Un système distribué, c'est surtout une liste de décisions sur la copie d'un fait qui fait foi. Voici celles de MoonQwak :

  • L'état courant du monde vit dans la RAM du serveur de jeu qui héberge la carte. La base est écrite après coup, en fond, et n'est relue qu'au chargement d'une carte ou à la connexion d'un joueur. (6.1)
  • Ce que voit le joueur est une copie, envoyée après chaque tick et toujours un peu en retard. Le client ne prédit que la marche de son propre personnage, et la corrige contre le serveur. (5.3)
  • Les sessions et la présence vivent dans la mémoire de la gateway. Un serveur de jeu sait quels joueurs il héberge ; seule la gateway sait où est tout le monde.
  • Les biens qui changent de mains sont l'exception au « RAM d'abord » : un échange, un achat au marché ou un colis est écrit en base immédiatement, en une transaction. (6.2)
  • Le parc est décrit par trois tables : les machines et leur capacité (saisies à la main), le nombre de serveurs demandé par chaque monde (écrit par la gateway), et les serveurs qui tournent réellement (écrits par les agents). (7.2)

Code shared by both ends

Four libraries are compiled for both the server and the Unity client: the transport and encryption layer, the packet definitions with their serialization code, the game data catalogs and shared rules (including the protocol version), and the hexagonal grid math. A build script copies them into the Unity project.

Sharing is what lets the client re-compute a ship's statistics or a weapon's cooldown exactly as the server does, instead of receiving them over the network. It has a cost: the client must be rebuilt whenever the shared code changes, and a client built against old libraries is refused at login by the protocol version check. Chapter 1.6 explains how the two ends are kept in agreement.

Le code partagé par les deux bouts

Quatre bibliothèques sont compilées à la fois pour le serveur et pour le client Unity : la couche de transport et de chiffrement, les définitions de paquets avec leur code de sérialisation, les catalogues de données de jeu et les règles partagées (dont la version du protocole), et les maths de la grille hexagonale. Un script de build les copie dans le projet Unity.

Ce partage permet au client de recalculer les statistiques d'un vaisseau ou le temps de recharge d'une arme exactement comme le serveur, au lieu de les recevoir par le réseau. Il a un coût : il faut recompiler le client dès que le code partagé change, et un client compilé avec de vieilles bibliothèques est refusé au login par la vérification de version. Le chapitre 1.6 explique comment les deux bouts restent d'accord.

Key takeaways

  • A player holds two connections: one to the gateway for identity and social, one to the game server that hosts their map.
  • Game servers never talk to each other. Cross-map concerns go through the gateway or the database.
  • Each process owns a clear set of facts, and each fact has one writer.
  • Inside a game server, the world tick is the most protected thread: it never waits for anything slower than itself.

À retenir

  • Un joueur tient deux connexions : une vers la gateway pour l'identité et le social, une vers le serveur de jeu qui héberge sa carte.
  • Les serveurs de jeu ne se parlent jamais. Ce qui traverse les cartes passe par la gateway ou par la base.
  • Chaque processus possède un ensemble clair de faits, et chaque fait a un seul écrivain.
  • Dans un serveur de jeu, le tick monde est le thread le plus protégé : il n'attend jamais rien de plus lent que lui.

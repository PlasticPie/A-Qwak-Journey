A reconciler, not a queue of orders

Each machine that can host game servers runs one small process, the node agent. It receives no instructions. Every two seconds it compares what runs on its machine with what the worlds demand (the Desired numbers of chapter 7.2), and closes the gap if it has room. An order can be lost, arrive twice, or arrive at a machine that just died; a desired state re-read in a loop always ends up being reached. An agent restarted in the middle of a launch resumes without knowing anything about what came before.

The data model changed along the way, and the change is worth copying. The first version read slots typed in advance, one row per possible server with its identity and ports, and kept N of them alive according to a hand-tuned number: it described the result instead of the resource. Now there is one row per machine (its capacity), one number per world (its demand, computed by the gateway), and instances are born on the first machine with room. Nothing about an instance is typed anywhere: its index, its ports (base port + index) and its identity (MACHINE#index) are derived.

Un réconciliateur, pas une file d'ordres

Chaque machine capable d'héberger des serveurs de jeu fait tourner un petit processus, l'agent de machine. Il ne reçoit aucune instruction. Toutes les deux secondes, il compare ce qui tourne sur sa machine à ce que demandent les mondes (les nombres Desired du chapitre 7.2), et comble l'écart s'il a de la place. Un ordre peut se perdre, arriver deux fois, ou arriver à une machine qui vient de tomber ; un état désiré relu en boucle finit toujours par être atteint. Un agent redémarré au milieu d'un lancement reprend sans rien savoir de ce qui précède.

Le modèle de données a changé en route, et le changement mérite d'être copié. La première version lisait des emplacements saisis d'avance, une ligne par serveur possible avec son identité et ses ports, et en tenait N vivants selon un nombre réglé à la main : elle décrivait le résultat au lieu de décrire la ressource. Il y a maintenant une ligne par machine (sa capacité), un nombre par monde (sa demande, calculée par la gateway), et les instances naissent sur la première machine qui a de la place. Rien d'une instance n'est saisi nulle part : son index, ses ports (port de base + index) et son identité (MACHINE#index) sont dérivés.

一個調和器，而不是一列命令佇列

每台可以託管遊戲伺服器的機器都執行一個小程序：節點代理程式。它不接收任何指示。每兩秒，它比較自己機器上執行的東西與各個世界的需求（第 7.2 章的 Desired 數字），如果它有空間，就補上差距。一道命令可能遺失、到達兩次，或到達一台剛死掉的機器；而在迴圈中反覆讀取的期望狀態，最終總會被達成。一個在啟動途中重新啟動的代理程式，不需要知道之前發生過什麼就能繼續。

資料模型在這一路上改變了，而這個改變值得照抄。第一版讀取的是預先輸入好的槽位，每個可能的伺服器一列，帶著它的身分與埠，並依一個手動調整的數字保持其中 N 個存活：它描述的是結果，而不是資源。現在每台機器一列（它的容量），每個世界一個數字（它的需求，由閘道計算），實例誕生在第一台有空間的機器上。實例的任何東西都不需要事先輸入：它的索引、它的埠（基準埠 + 索引）與它的身分（MACHINE#index）都是推導出來的。

Claiming work through the database

Two machines see "one server missing" at the same moment and both launch: now there is one too many, and nothing will ever stop it, since an instance that hosts maps is never killed. That is not an acceptable imprecision, it is a leak. The decision is serialized by the only arbiter two processes that never talk to each other share: the database.

Prendre du travail via la base

Deux machines voient « il manque un serveur » au même moment et lancent toutes les deux : il y en a maintenant un de trop, et rien ne l'arrêtera jamais, puisqu'une instance qui héberge des cartes n'est jamais tuée. Ce n'est pas une imprécision acceptable, c'est une fuite. La décision est sérialisée par le seul arbitre que partagent deux processus qui ne se parlent jamais : la base.

透過資料庫認領工作

兩台機器在同一時刻看到「少了一台伺服器」，於是都啟動了：現在多了一台，而且永遠沒有東西會停止它，因為託管著地圖的實例從不被砍掉。這不是可接受的不精確，而是一個漏洞。這個決定由兩個從不交談的程序唯一共享的仲裁者來依序處理：資料庫。

Qwak.NodeAgent/NodeLoop.cs · TryClaim, simplified
using var db = _db();
using var tx = db.Database.BeginTransaction();

// Lock the world's row until commit: other agents wanting this world wait HERE,
// and will count again once we are done.
var world = db.WorldCapacities
              .FromSqlRaw("SELECT * FROM WorldCapacities WHERE WorldId = {0} FOR UPDATE", worldId)
              .AsEnumerable().FirstOrDefault();

var target  = Math.Clamp(world.Desired, world.Min, world.Max);
var running = db.GameServerInstances.Count(i => i.WorldId == worldId && i.LastSeenUtc > staleBefore);
if (running >= target) return false;  // someone else already filled it
if (!IsBestCandidate(db, host, worldId)) return false;  // a better machine will take it

if (!PortGuard.CanBind(gamePort, debugPort, PortGuard.BusyUdpPorts(), out _)) return false;

var row = NewInstanceRow(host, worldId, index);         // index, ports, identity: derived
db.GameServerInstances.Add(row);                        // the ROW first, under the lock...
db.SaveChanges();
var pid = _launcher.Start(slot);                        // ...then the process
if (pid <= 0)                                           // failed or cooling down:
{                                                       // give the index back at once
    db.GameServerInstances.Remove(row); db.SaveChanges(); tx.Commit();
    return false;
}
row.Pid = pid;
db.SaveChanges();
tx.Commit();

The order lock, count, insert, commit is the whole point: counting before locking would decide on a stale photograph, which is exactly the race to close. And the instance row is written before the process starts, so a server that is still booting is already counted by every other agent. Stale rows cannot hold a place forever either: rows whose agent stopped writing a heartbeat for 120 seconds are ignored when counting, and any agent may delete them. That is the only release mechanism that survives the death of the supervisor itself, which is why it lives in the database.

L'ordre verrouiller, compter, insérer, valider est tout l'enjeu : compter avant de verrouiller reviendrait à décider sur une photo périmée, c'est-à-dire exactement la course à fermer. Et la ligne de l'instance est écrite avant que le processus démarre : un serveur encore en démarrage est déjà compté par tous les autres agents. Les lignes périmées ne peuvent pas non plus garder une place pour toujours : les lignes dont l'agent a cessé d'écrire un battement depuis 120 secondes sont ignorées au comptage, et n'importe quel agent peut les effacer. C'est le seul mécanisme de libération qui survive à la mort du superviseur lui-même, et c'est pourquoi il vit en base.

上鎖、計數、插入、提交這個順序就是全部的重點：在上鎖之前計數，會根據一張過時的照片做決定，而那恰恰是要封住的競爭條件。而且實例的資料列在程序啟動之前就寫入，所以一台還在開機的伺服器，已經被其他每個代理程式計入了。過時的資料列也無法永遠佔住位置：代理程式已經 120 秒沒寫入心跳的資料列，在計數時會被忽略，而且任何代理程式都可以刪除它們。這是唯一一個在監督者本身死掉後仍然有效的釋放機制，所以它放在資料庫中。

"Am I the best host?"

Without that question, the first agent to get the lock wins: an arbitrary order, which places a server on a machine already on its knees as readily as on an idle one. So each agent, holding the lock, looks at the same table as everyone else and asks whether it is the best machine for one more server. Nobody decides for the others, which keeps the system without a leader.

  • The score. Maps hosted on the machine relative to its capacity (weight 1.0, since maps are the resource with a hard wall), plus RAM usage (0.6) and CPU usage (0.4), the last two only if the machine's metrics are fresh (under two minutes old); otherwise nothing is invented and the score rests on maps alone.
  • Exclusions. A machine that is full, or outside its RAM limits, or whose agent has not written a heartbeat recently, is not a candidate. That last rule is the whole failover: if the best machine dies, its row goes stale and the next one becomes the best, without a single line of failover code.
  • Ties broken by name. Two identical machines at startup have exactly the same score. Without a stable tie-break, each would believe itself the best at the same instant and both would launch. The machine name is arbitrary, but identical for every observer, which is the only property needed.

« Suis-je le meilleur hôte ? »

Sans cette question, le premier agent à obtenir le verrou gagne : un ordre arbitraire, qui place un serveur sur une machine déjà à genoux aussi volontiers que sur une machine inactive. Chaque agent, verrou en main, regarde donc la même table que tous les autres et se demande s'il est la meilleure machine pour un serveur de plus. Personne ne décide pour les autres, ce qui garde le système sans chef.

  • Le score. Les cartes hébergées sur la machine rapportées à sa capacité (poids 1,0, car les cartes sont la ressource au mur dur), plus l'usage de la RAM (0,6) et du CPU (0,4), ces deux derniers seulement si les mesures de la machine sont fraîches (moins de deux minutes) ; sinon on n'invente rien et le score ne repose que sur les cartes.
  • Les exclusions. Une machine pleine, hors de ses limites de RAM, ou dont l'agent n'a pas écrit de battement récemment, n'est pas candidate. Cette dernière règle est toute la bascule : si la meilleure machine meurt, sa ligne se périme et la suivante devient la meilleure, sans une seule ligne de code de bascule.
  • Égalités tranchées par le nom. Deux machines identiques au démarrage ont exactement le même score. Sans départage stable, chacune se croirait la meilleure au même instant et les deux lanceraient. Le nom de la machine est arbitraire, mais identique pour tous les observateurs, ce qui est la seule propriété demandée.

「我是最好的主機嗎？」

沒有這個問題，第一個拿到鎖的代理程式就贏了：一個任意的順序，它會把伺服器放到一台已經撐不住的機器上，就像放到一台閒置的機器上一樣輕易。所以每個代理程式在持有鎖時，看著與其他人相同的資料表，問自己是不是多放一台伺服器的最佳機器。沒有人替別人做決定，這讓系統不需要領導者。

  • 分數。機器上託管的地圖數相對於它的容量（權重 1.0，因為地圖是有硬牆的資源），加上 RAM 使用率（0.6）與 CPU 使用率（0.4），後兩者只有在機器的指標夠新（兩分鐘以內）時才計入；否則不捏造任何東西，分數只依地圖而定。
  • 排除條件。已滿的機器、超出 RAM 限制的機器，或代理程式最近沒有寫入心跳的機器，都不是候選者。最後這條規則就是全部的容錯移轉：如果最好的機器死了，它的資料列會變得過時，下一台就成了最好的，不需要任何一行容錯移轉的程式碼。
  • 平手時依名稱決定。兩台相同的機器在啟動時分數完全相同。沒有穩定的平手決定方式，兩台都會在同一瞬間認為自己是最好的，然後都啟動。機器名稱是任意的，但對每個觀察者都相同，而這正是唯一需要的特性。

Sizing to the hardware

Three numbers used to be kept consistent by hand: the machine's maximum instance count, the world's maximum, and the tick-worker count in each server's configuration. Three coupled numbers maintained by hand are three chances to be wrong and none to notice. A configuration with one worker "fixed" ten instances per machine and switched off parallelism everywhere else. Now there is one knob, the number of tick workers wanted per instance, and the rest is computed by the agent, which runs on the hardware it is sizing:

Se dimensionner sur le matériel

Trois nombres étaient autrefois tenus cohérents à la main : le nombre maximal d'instances de la machine, le maximum du monde, et le nombre d'ouvriers de tick dans la configuration de chaque serveur. Trois nombres couplés tenus à la main, ce sont trois occasions de se tromper et aucune de s'en apercevoir. Une configuration à un ouvrier « réglait » dix instances par machine et éteignait le parallélisme partout ailleurs. Il n'y a maintenant qu'un bouton, le nombre d'ouvriers de tick voulus par instance, et le reste est calculé par l'agent, qui tourne sur le matériel qu'il dimensionne :

依硬體調整規模

過去有三個數字要手動保持一致：機器的最大實例數、世界的最大值，以及每台伺服器設定中的 tick 工作執行緒數。三個手動維護的耦合數字，就是三個出錯的機會，卻沒有一個能察覺的機會。一份只有一個工作執行緒的設定，「修好了」每台機器十個實例，卻把其他所有地方的平行化都關掉了。現在只有一個旋鈕，也就是每個實例想要的 tick 工作執行緒數，其餘的由代理程式計算，因為它就在它所要調整規模的硬體上執行：

sizing, agent side
capacity = min( MaxInstances , processors / (workers wanted + 2) )
           ↓ passed to each child as the number of instances on this machine
server   : workers = processors / instances − 2

The "+ 2" reserves each instance's world and snapshot threads (chapter 3.3). The typed maximum keeps its meaning as a ceiling: the agent may decide fewer, never more. RAM is deliberately left out of the formula: CPU can be counted exactly, while an instance's memory depends on how many maps it will end up carrying, which nobody knows at launch. Inventing "megabytes per instance" would give a false number that looks measured. Memory has its own guard, and a better one because it looks at the real state: the agent refuses to launch when free RAM falls below a configured minimum, at the moment it matters.

Le « + 2 » réserve les threads du monde et des snapshots de chaque instance (chapitre 3.3). Le maximum saisi garde son sens de plafond : l'agent peut décider moins, jamais plus. La RAM est délibérément absente de la formule : le CPU se compte exactement, alors que la mémoire d'une instance dépend du nombre de cartes qu'elle finira par porter, ce que personne ne sait au lancement. Inventer des « mégaoctets par instance » donnerait un chiffre faux qui a l'air mesuré. La mémoire a son propre garde-fou, et il est meilleur parce qu'il regarde l'état réel : l'agent refuse de lancer quand la RAM libre passe sous un minimum configuré, au moment où ça compte.

「+ 2」保留給每個實例的世界執行緒與快照執行緒（第 3.3 章）。輸入的最大值保留它作為天花板的意義：代理程式可以決定更少，但絕不能更多。RAM 被刻意排除在公式之外：CPU 可以精確計算，而一個實例的記憶體取決於它最終會承載多少張地圖，這在啟動時沒有人知道。捏造一個「每個實例多少 MB」，會得到一個看起來像是量測出來的錯誤數字。記憶體有自己的防護，而且更好，因為它看的是真實的狀態：當可用 RAM 低於設定的最低值時，代理程式會拒絕啟動，就在真正重要的時刻。

Two cooldowns for two situations

A game server takes several seconds to announce itself. Without a pause between launches, the reconciler would see "still zero servers" during that time and launch one per round: the classic reconciler bug of confusing not ready yet with not there. Hence a 20-second cooldown between launches, the same duration after which a booting instance stops counting as "starting". Two constants that must agree are one constant.

That pause guards against uncertainty: when a threshold calls for a reinforcement, nobody knows yet whether one will be enough. Below the world's minimum there is no uncertainty: "eight are needed, two are running", and none of the six missing ones will make the others useless. Waiting 20 seconds between each protected nothing and cost two and a half minutes of cold start on a bench. The runaway it seemed to prevent is already closed by the write order (the row is counted before the process exists), so the cooldown below the floor is 3 seconds: just enough to spread the load of eight processes opening their catalogs and database connections at once. Filling a floor of eight went from about 160 seconds to about thirty.

Pitfall I hit

Each machine can also keep a preloaded reserve: servers started in advance, warm, for the next peak. The preload was bounded by the world's maximum, not by its desired count. So the gateway condemned a server, its agent killed it after a minute, and the next round launched a fresh one "to keep warm" in its place. Two correct mechanisms fought in a loop, each undoing the other's work, and the only trace was a fleet running at its maximum for no visible reason. A world that is shedding load no longer preloads: when the two disagree, retirement wins, because it speaks about a measured load and preloading about a supposed one.

Deux temporisations pour deux situations

Un serveur de jeu met plusieurs secondes à s'annoncer. Sans pause entre deux lancements, le réconciliateur verrait « toujours zéro serveur » pendant ce temps et en lancerait un par tour : le bug classique du réconciliateur, confondre pas encore prêt et pas là. D'où une temporisation de 20 secondes entre deux lancements, la même durée au bout de laquelle une instance qui démarre cesse de compter comme « en démarrage ». Deux constantes qui doivent s'accorder sont une seule constante.

Cette pause protège d'une incertitude : quand un seuil réclame un renfort, personne ne sait encore si un seul suffira. Sous le minimum du monde, il n'y a aucune incertitude : « il en faut huit, deux tournent », et aucun des six manquants ne rendra les autres inutiles. Attendre 20 secondes entre chacun ne protégeait de rien et coûtait deux minutes et demie de démarrage à froid au banc. L'emballement qu'elle semblait empêcher est déjà fermé par l'ordre d'écriture (la ligne est comptée avant que le processus n'existe) : sous le plancher, la temporisation est donc de 3 secondes, juste assez pour étaler la charge de huit processus qui ouvrent leurs catalogues et leurs connexions à la base en même temps. Remplir un plancher de huit est passé d'environ 160 secondes à une trentaine.

Piège rencontré

Chaque machine peut aussi garder une réserve préchargée : des serveurs démarrés d'avance, au chaud, pour la prochaine pointe. Le préchargement était borné par le maximum du monde, pas par son nombre désiré. La gateway condamnait donc un serveur, son agent le tuait au bout d'une minute, et le tour suivant en lançait un neuf « au chaud » à sa place. Deux mécanismes justes se battaient en boucle, chacun défaisant le travail de l'autre, et la seule trace était un parc qui tournait à son maximum sans raison visible. Un monde qui se déleste ne précharge plus : quand les deux se contredisent, le retrait l'emporte, parce qu'il parle d'une charge mesurée et le préchargement d'une charge supposée.

兩種情況，兩種冷卻時間

一台遊戲伺服器要花好幾秒才能宣告自己。如果兩次啟動之間沒有停頓，調和器在這段期間會看到「仍然是零台伺服器」，然後每一輪都啟動一台：這是調和器的經典 bug，把還沒準備好和不存在搞混了。因此兩次啟動之間有 20 秒的冷卻時間，與一個開機中的實例不再被算為「啟動中」的時間相同。兩個必須一致的常數，就是一個常數。

這個停頓防的是不確定性：當某個門檻要求支援時，沒有人知道一台是否就夠了。低於世界的最小值時則沒有不確定性：「需要八台，正在執行兩台」，而缺少的六台中沒有任何一台會讓其他的變得無用。每台之間等 20 秒什麼都沒保護到，卻讓一次測試台多花了兩分半的冷啟動。它看似防止的失控，已經被寫入順序封住了（資料列在程序存在之前就被計入），所以低於下限時的冷卻時間是 3 秒：剛好足以分散八個程序同時開啟目錄與資料庫連線的負載。補滿八台的下限，從約 160 秒縮短到約三十秒。

我踩過的坑

每台機器也可以保留一份預載的儲備：預先啟動、保持溫熱、為下一次峰值準備的伺服器。預載的上限是世界的最大值，而不是它的期望值。於是閘道判定一台伺服器退役，它的代理程式在一分鐘後砍掉它，而下一輪又啟動一台新的「保持溫熱」來取代它。兩個正確的機制在迴圈中互相打架，各自抵銷對方的工作，唯一的痕跡是一個毫無可見理由就以最大值運作的叢集。一個正在卸除負載的世界不再預載：兩者意見不一時，退役獲勝，因為它說的是量測到的負載，而預載說的是假設的負載。

Retiring empty servers: observe, never decide

The gateway condemns (chapter 7.2); the agent only observes and executes. For a condemned server of its own machine, it checks three things: the gateway's report is fresh, the server carries zero maps, and it has done so for long enough. Three readings, no judgement. Because no agent chooses anything, no two agents can choose the same thing, and there is no lock to take.

  • Sixty seconds of emptiness, which is twelve consecutive reports from the gateway. The risk bought with that delay is precise: a map can be assigned to the server without being counted yet (the "load this map" message left, the answer has not come back), and killing it in that window would refuse the waiting player.
  • A fresh observation. The map and player counts are written by the gateway. If the gateway goes down, they freeze, and if they freeze at zero, an agent that only read their values would kill, a minute later, a server nobody can tell is empty. Silence from the observer must never be read as "nothing changed": beyond twenty seconds without a report, nothing is killed.
  • Phantom players. The first version required zero maps and zero players, and an hour-long bench showed a server "0 maps, 1 player, draining for 39 minutes", held hostage by one ghost. That state is impossible: a player is always on a map, and an occupied map never unloads. It is a session the gateway kept after its player left. The agent now waits five minutes in that case (enough for a momentarily wrong count to fix itself), then stops the server anyway, and says loudly that the real bug is upstream.
  • Kill, then delete the row, never the reverse. Deleting first and failing the kill would leave a live process with no row: its index becomes available, and the next server would be born on its ports. In the other order, a successful kill followed by an unreachable database leaves a row without a process, which the next round already knows how to clean.

The "empty since" timer lives in memory, on purpose. An agent that restarts forgets it and waits one more minute before killing: it delays a retirement, which costs one process for sixty seconds. The symmetric failure, a persisted timer believed to be current after a restart, would kill on an observation nobody made. Forgetting is the right failure.

Retirer les serveurs vides : constater, jamais décider

La gateway condamne (chapitre 7.2) ; l'agent ne fait que constater et exécuter. Pour un serveur condamné de sa propre machine, il vérifie trois choses : le relevé de la gateway est frais, le serveur porte zéro carte, et il le fait depuis assez longtemps. Trois lectures, aucun jugement. Comme aucun agent ne choisit rien, deux agents ne peuvent pas choisir la même chose, et il n'y a aucun verrou à prendre.

  • Soixante secondes de vide, c'est-à-dire douze relevés consécutifs de la gateway. Le risque qu'achète ce délai est précis : une carte peut être assignée au serveur sans être encore comptée (le message « charge cette carte » est parti, la réponse n'est pas revenue), et le tuer dans cette fenêtre refuserait le joueur qui attendait.
  • Un relevé frais. Les comptes de cartes et de joueurs sont écrits par la gateway. Si elle tombe, ils se figent, et s'ils se figent à zéro, un agent qui ne regarderait que leur valeur tuerait, une minute plus tard, un serveur dont personne ne peut dire s'il est vide. Le silence de l'observateur ne doit jamais se lire comme « rien n'a changé » : au-delà de vingt secondes sans relevé, rien n'est tué.
  • Les joueurs fantômes. La première version exigeait zéro carte et zéro joueur, et un banc d'une heure a montré un serveur « 0 carte, 1 joueur, en retrait depuis 39 minutes », tenu en otage par un fantôme. Cet état est impossible : un joueur est toujours sur une carte, et une carte occupée ne se décharge jamais. C'est une session que la gateway a gardée après le départ de son joueur. L'agent attend maintenant cinq minutes dans ce cas (assez pour qu'un compte momentanément faux se corrige tout seul), puis arrête quand même le serveur, et dit fort que le vrai bug est en amont.
  • Tuer, puis effacer la ligne, jamais l'inverse. Effacer d'abord et rater l'arrêt laisserait un processus vivant sans ligne : son index redeviendrait disponible, et le serveur suivant naîtrait sur ses ports. Dans l'autre ordre, un arrêt réussi suivi d'une base injoignable laisse une ligne sans processus, que le tour suivant sait déjà nettoyer.

Le chronomètre « vide depuis » vit en mémoire, exprès. Un agent qui redémarre l'oublie et attend une minute de plus avant de tuer : il retarde un retrait, ce qui coûte un processus pendant soixante secondes. La panne symétrique, un chronomètre persistant qu'on croit à jour après un redémarrage, tuerait sur une observation que personne n'a faite. Oublier est la bonne panne.

讓空伺服器退役：觀察，絕不決定

閘道負責判定退役（第 7.2 章）；代理程式只負責觀察與執行。對自己機器上一台被判定退役的伺服器，它檢查三件事：閘道的報告是新的、伺服器承載零張地圖，而且已經維持夠久。三個讀數，沒有任何判斷。因為沒有任何代理程式在選擇任何東西，就不可能有兩個代理程式選中同一個東西，也沒有任何鎖需要取得。

  • 六十秒的空無，也就是閘道連續十二次的報告。這個延遲所買到的風險是明確的：一張地圖可能已經被指派給這台伺服器，卻還沒被計入（「載入這張地圖」的訊息已經送出，回覆還沒回來），而在這個時間窗中砍掉它，就會拒絕那位等待中的玩家。
  • 新鮮的觀察。地圖數與玩家數由閘道寫入。如果閘道掛了，它們就會凍結，而如果它們凍結在零，一個只讀取數值的代理程式，就會在一分鐘後砍掉一台沒有人能判斷是否為空的伺服器。觀察者的沉默絕不能被解讀為「什麼都沒變」：超過二十秒沒有報告，就什麼都不砍。
  • 幽靈玩家。第一版要求零張地圖而且零位玩家，而一次一小時的測試台顯示一台伺服器「0 張地圖、1 位玩家、排空中 39 分鐘」，被一個幽靈挾持。這個狀態是不可能的：玩家永遠在某張地圖上，而有人的地圖從不卸載。那是一個玩家離開後仍被閘道保留的連線階段。現在代理程式在這種情況下會等五分鐘（足以讓暫時錯誤的計數自行修正），然後仍然停止伺服器，並大聲地說真正的 bug 在上游。
  • 先砍程序，再刪資料列，絕不反過來。先刪除、而砍程序失敗，會留下一個沒有資料列的存活程序：它的索引變成可用，下一台伺服器就會在它的埠上誕生。照另一個順序，砍掉成功之後資料庫卻連不上，會留下一個沒有程序的資料列，而下一輪早就知道該如何清理它。

「自何時起為空」的計時器刻意放在記憶體中。一個重新啟動的代理程式會忘記它，並在砍之前多等一分鐘：這延後了一次退役，代價是一個程序多活六十秒。對稱的失敗——一個在重新啟動後被當成仍然有效的持久化計時器——則會根據一個沒有人做過的觀察去砍程序。遺忘才是正確的失敗方式。

Rule

The one who observes is the one who writes; the one who acts only reads.

The gateway observes the surplus and writes the condemnation; the agent observes two zeros and kills. Each fact has one writer, so N agents coexist without coordinating.

Règle

Celui qui constate est celui qui écrit ; celui qui agit ne fait que lire.

La gateway constate le surplus et écrit la condamnation ; l'agent constate deux zéros et tue. Chaque fait n'a qu'un écrivain : N agents coexistent sans se coordonner.

規則

觀察的人就是寫入的人；行動的人只讀取。

閘道觀察到多餘並寫下判定；代理程式觀察到兩個零並砍掉程序。每一項事實都只有一個寫入者，所以 N 個代理程式能在不協調的情況下共存。

Being a good supervisor

Without an operating-system service manager, the agent is the supervisor of its game servers, and a supervisor that dies leaving its children behind is worse than none: when it restarts, the old servers still hold the ports and identities it is about to hand out again. Windows has the right tool, better than an exit hook: a job object with "kill on job close". Processes placed in it die with the job's handle, hence with the agent, however it stops: Ctrl+C, an unhandled exception, "End task", a native crash. The kernel cleans up; a hook would assume a process still able to run it.

The job used to belong to the gateway, which launched servers before the agents existed. Restarting the gateway then killed every game server of the fleet: excellent against orphans, catastrophic for a routine operation. Stopping the agent, on the other hand, is the gesture that should stop its servers. The agent also listens on no port at all: there is literally no network from which a piece of data could come, and the code says so for the day someone wants to "just add a small API".

Measured

Ports are derived: game port = start + index. With a start at 9051, instance 1 asked for 9052, the port on which the gateway listens for its game servers. The server started, authenticated, received and loaded maps (all of that goes through its outgoing connection to the gateway, which worked perfectly) but its incoming listener for players never existed. A server that looked healthy, with eighty maps, on which no player ever arrived: three bench sessions to understand, because nothing distinguished "it listens" from "it cannot listen". The agent now checks the machine's UDP listeners before launching and refuses a busy port, loudly. It is a snapshot (someone can take the port in between, or a firewall rule can refuse it), so it catches the ordinary case, not every case.

Rule

A silent bind failure is the worst kind of outage.

The process lives, half its functions work, and the symptom appears three components away. Check what you can before starting, and make the process itself fail loudly when it cannot listen.

Être un bon superviseur

Sans gestionnaire de services du système, l'agent est le superviseur de ses serveurs de jeu, et un superviseur qui meurt en laissant ses enfants derrière lui est pire que pas de superviseur : à son redémarrage, les anciens serveurs tiennent encore les ports et les identités qu'il s'apprête à redistribuer. Windows a le bon outil, meilleur qu'un crochet de sortie : un objet job avec « tuer à la fermeture du job ». Les processus qu'on y place meurent avec le handle du job, donc avec l'agent, quelle que soit la façon dont il s'arrête : Ctrl+C, exception non rattrapée, « Fin de tâche », plantage natif. Le noyau nettoie ; un crochet supposerait un processus encore capable de l'exécuter.

Le job appartenait autrefois à la gateway, qui lançait les serveurs avant que les agents n'existent. Redémarrer la gateway tuait alors tous les serveurs de jeu du parc : excellent contre les orphelins, catastrophique pour une opération de routine. Arrêter l'agent, lui, est le geste qui doit arrêter ses serveurs. L'agent n'écoute d'ailleurs sur aucun port : il n'y a littéralement aucun réseau d'où une donnée pourrait venir, et le code le dit pour le jour où quelqu'un voudra « juste ajouter une petite API ».

Mesuré

Les ports sont dérivés : port de jeu = départ + index. Avec un départ à 9051, l'instance 1 demandait 9052, le port sur lequel la gateway écoute ses serveurs de jeu. Le serveur démarrait, s'authentifiait, recevait et chargeait des cartes (tout cela passe par sa connexion sortante vers la gateway, qui marchait parfaitement), mais son écoute entrante pour les joueurs n'a jamais existé. Un serveur en apparence sain, avec quatre-vingts cartes, sur lequel aucun joueur n'arrivait jamais : trois sessions de banc pour comprendre, parce que rien ne distinguait « il écoute » de « il ne peut pas écouter ». L'agent vérifie maintenant les écoutes UDP de la machine avant de lancer et refuse un port occupé, bruyamment. C'est une photo (quelqu'un peut prendre le port entre-temps, ou une règle de pare-feu le refuser) : elle attrape le cas ordinaire, pas tous les cas.

Règle

Un échec de liaison silencieux est la pire des pannes.

Le processus vit, la moitié de ses fonctions marche, et le symptôme apparaît trois composants plus loin. Vérifier ce qu'on peut avant de démarrer, et faire échouer bruyamment le processus lui-même quand il ne peut pas écouter.

做一個好的監督者

沒有作業系統的服務管理員時，代理程式就是它的遊戲伺服器的監督者，而一個死掉時留下子程序的監督者，比沒有監督者更糟：當它重新啟動時，舊的伺服器仍然佔著它正要再次發出的埠與身分。Windows 有正確的工具，比結束掛勾更好：一個設定了「關閉時終止」的工作物件（job object）。放在其中的程序會隨著工作物件的控制代碼一起死，因此也隨著代理程式一起死，不論它是怎麼停止的：Ctrl+C、未處理的例外、「結束工作」、原生當機。由核心負責清理；掛勾則假設還有一個能執行它的程序。

工作物件過去屬於閘道，在代理程式存在之前，是由它啟動伺服器的。於是重新啟動閘道，就會砍掉整個叢集的每一台遊戲伺服器：對付孤兒程序非常有效，對一次例行操作卻是災難。反過來說，停止代理程式正是應該停止它的伺服器的那個動作。代理程式也完全不監聽任何埠：根本不存在任何一片資料可能從中而來的網路，而程式碼也這樣寫著，留給哪天有人想「只是加一個小 API」的時候看。

實測

埠是推導出來的：遊戲埠 = 起始值 + 索引。起始值設為 9051 時，實例 1 要求的是 9052，而那正是閘道監聽它的遊戲伺服器的埠。伺服器啟動了、通過認證、收到並載入了地圖（這些全都經由它連到閘道的出站連線，而那條連線運作完美），但它給玩家用的入站監聽器從未存在。一台看起來健康、載有八十張地圖的伺服器，卻從來沒有任何玩家到達：花了三次測試台才弄懂，因為沒有任何東西能區分「它在監聽」與「它無法監聽」。現在代理程式在啟動之前會檢查機器的 UDP 監聽器，並大聲地拒絕已被佔用的埠。這是一張快照（中間可能有人搶走這個埠，或防火牆規則可能拒絕它），所以它抓得到一般情況，而不是所有情況。

規則

無聲的繫結失敗是最糟的一種停機。

程序活著，一半的功能能運作，而症狀出現在三個元件之外。能在啟動前檢查的就先檢查，並讓程序本身在無法監聽時大聲地失敗。

Key takeaways

  • Run a reconciler per machine that compares desired and actual state in a loop; describe resources, derive instances.
  • Serialize claims with a database row lock, count after locking, and write the row before starting the process.
  • Let each agent ask whether it is the best host from shared data, with a stable tie-break; failover then needs no code.
  • Size instances from the hardware with one knob; use different cooldowns for certain and uncertain needs.
  • Retire only on fresh, repeated observations, kill before deleting, and supervise children with a kernel job object.

À retenir

  • Faire tourner un réconciliateur par machine qui compare en boucle l'état désiré et l'état réel ; décrire les ressources, dériver les instances.
  • Sérialiser les prises de travail par un verrou de ligne en base, compter après avoir verrouillé, et écrire la ligne avant de démarrer le processus.
  • Laisser chaque agent se demander s'il est le meilleur hôte à partir de données partagées, avec un départage stable ; la bascule n'a alors besoin d'aucun code.
  • Dimensionner les instances sur le matériel avec un seul bouton ; utiliser des temporisations différentes pour les besoins certains et incertains.
  • Ne retirer que sur des observations fraîches et répétées, tuer avant d'effacer, et superviser les enfants avec un objet job du noyau.

重點整理

  • 每台機器執行一個調和器，在迴圈中比較期望狀態與實際狀態；描述資源，推導實例。
  • 以資料庫的資料列鎖讓認領依序進行，上鎖之後才計數，並在程序啟動之前寫入資料列。
  • 讓每個代理程式根據共用資料，自問自己是不是最好的主機，並使用穩定的平手決定方式；容錯移轉就不需要任何程式碼。
  • 以一個旋鈕依硬體調整實例規模；對確定與不確定的需求使用不同的冷卻時間。
  • 只根據新鮮、重複的觀察讓伺服器退役，先砍程序再刪除，並以核心的工作物件監督子程序。

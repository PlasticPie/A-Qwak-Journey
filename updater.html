Identify files by what they contain

A game build is tens of thousands of files and hundreds of megabytes, published several times an evening during development. Players must end up with exactly the right bytes, whatever state their installation is in: up to date, several versions behind, half-installed, or silently corrupted by a tired disk.

The obvious design, a version number per file, drags history along: to know what to download, you need to know where the player comes from. A hash of the content answers the only question that matters on its own: "is this file, on my disk, exactly the one the server describes?" Any client, in any state, gets the same answer: here are the objects that are missing. There is no "up to date" state to maintain anywhere, and therefore no state to fall out of sync.

Beginner note

A cryptographic hash such as SHA-256 turns any file into a 64-character fingerprint. Change one byte and the fingerprint changes completely; two different files practically never share one. So the fingerprint can serve as the file's name: this is content-addressed storage, the idea behind Git's object store and many package caches.

Two choices in how the hash is computed matter more than they look:

  • SHA-256, not a fast hash like xxHash. This hash decides that a file does not need to be downloaded again, and it is the only check that a byte received is the byte sent. A collision would not be a slowdown, it would be a silently wrong installation. Its cost, around a gigabyte per second on a modern CPU with hardware acceleration, is nothing next to the network it saves.
  • Streamed, never read whole. Files are hashed through a 64 KB buffer. A Unity .assets file commonly exceeds a gigabyte, and reading it whole to hash it would put that gigabyte on the managed heap, in the large object heap, which is not compacted. On a busy machine, that is an out-of-memory error for an operation that needs a few kilobytes.

Identifier les fichiers par ce qu'ils contiennent

Une version du jeu, ce sont des dizaines de milliers de fichiers et des centaines de mégaoctets, publiés plusieurs fois par soirée pendant le développement. Les joueurs doivent finir avec exactement les bons octets, quel que soit l'état de leur installation : à jour, en retard de plusieurs versions, à moitié installée, ou corrompue en silence par un disque fatigué.

La conception évidente, un numéro de version par fichier, traîne l'historique avec elle : pour savoir quoi télécharger, il faut savoir d'où vient le joueur. Un hachage du contenu répond tout seul à la seule question qui compte : « ce fichier, sur mon disque, est-il exactement celui que décrit le serveur ? » N'importe quel client, dans n'importe quel état, obtient la même réponse : voici les objets qui manquent. Il n'existe aucun état « à jour » à tenir quelque part, donc aucun état à désynchroniser.

Pour débuter

Un hachage cryptographique comme SHA-256 transforme n'importe quel fichier en une empreinte de 64 caractères. Changez un octet et l'empreinte change complètement ; deux fichiers différents n'en partagent pratiquement jamais une. L'empreinte peut donc servir de nom au fichier : c'est le stockage adressé par contenu, l'idée derrière le magasin d'objets de Git et de nombreux caches de paquets.

Deux choix dans le calcul du hachage comptent plus qu'il n'y paraît :

  • SHA-256, pas un hachage rapide comme xxHash. Ce hachage décide qu'un fichier n'a pas besoin d'être retéléchargé, et c'est la seule vérification qu'un octet reçu est l'octet envoyé. Une collision n'y serait pas un ralentissement, ce serait une installation silencieusement fausse. Son coût, de l'ordre d'un gigaoctet par seconde sur un CPU moderne avec accélération matérielle, n'est rien à côté du réseau qu'il économise.
  • En flux, jamais lu en entier. Les fichiers sont hachés à travers un tampon de 64 Ko. Un fichier .assets d'Unity dépasse couramment le gigaoctet, et le lire en entier pour le hacher mettrait ce gigaoctet sur le tas managé, dans le tas des grands objets, qui n'est pas compacté. Sur une machine chargée, c'est une erreur de mémoire pour une opération qui n'a besoin que de quelques kilo-octets.

以內容來識別檔案

一個遊戲組建有數萬個檔案、數百 MB，在開發期間一個晚上就會發布好幾次。不論玩家的安裝處於什麼狀態——最新、落後好幾個版本、裝到一半，或被一顆疲憊的硬碟悄悄損壞——他們最後都必須得到完全正確的位元組。

顯而易見的設計是每個檔案一個版本號，但它會拖著歷史走：要知道該下載什麼，就得知道玩家是從哪裡來的。內容的雜湊值則能獨力回答唯一重要的問題：「我磁碟上的這個檔案，是否正是伺服器所描述的那一個？」任何用戶端，不論處於什麼狀態，得到的都是同一個答案：這些是缺少的物件。任何地方都不需要維護一個「最新」狀態，因此也沒有任何會失去同步的狀態。

新手須知

像 SHA-256 這樣的密碼學雜湊，能把任何檔案變成一個 64 個字元的指紋。改一個位元組，指紋就完全不同；兩個不同的檔案實際上永遠不會有同一個指紋。所以指紋可以當作檔案的名稱：這就是內容定址儲存，也是 Git 的物件儲存區與許多套件快取背後的概念。

雜湊的計算方式中，有兩個選擇比看起來更重要：

  • 使用 SHA-256，而不是 xxHash 這類快速雜湊。這個雜湊決定的是一個檔案不需要重新下載，也是唯一能確認收到的位元組就是送出的位元組的檢查。一次碰撞不會只是變慢，而是一次無聲無息的錯誤安裝。它的成本，在有硬體加速的現代 CPU 上約每秒 1 GB，與它所省下的網路相比微不足道。
  • 以串流方式處理，絕不整個讀入。檔案透過一個 64 KB 的緩衝區計算雜湊。一個 Unity .assets 檔案常常超過 1 GB，把它整個讀進來計算雜湊，會把那 1 GB 放到受控堆積的大型物件堆積上，而那裡不會被壓縮整理。在一台忙碌的機器上，這就是為了一個只需要幾 KB 的操作而發生記憶體不足錯誤。

One object store, many builds

The update server does not store builds side by side, each complete. It stores objects under their hash, and a build is only a manifest: a list of paths, each with a size and the hash of its content. Two builds that share 95 % of their files share 95 % of their objects, on disk and on the network. If each build changes only a few percent of its files, ten versions of a 500 MB build take roughly 600 MB instead of five gigabytes. And "download only what changed" is not an optimization of the launcher: it is the only thing it knows how to do, because it asks for hashes, not files.

Un magasin d'objets, beaucoup de versions

Le serveur de mise à jour ne range pas les versions côte à côte, chacune complète. Il range des objets sous leur hachage, et une version n'est qu'un manifeste : une liste de chemins, chacun avec une taille et le hachage de son contenu. Deux versions qui partagent 95 % de leurs fichiers partagent 95 % de leurs objets, sur le disque comme sur le réseau. Si chaque version ne change que quelques pour cent de ses fichiers, dix versions d'une build de 500 Mo occupent environ 600 Mo au lieu de cinq gigaoctets. Et « ne télécharger que ce qui a changé » n'est pas une optimisation du launcher : c'est la seule chose qu'il sache faire, parce qu'il demande des hachages, pas des fichiers.

一個物件儲存區，許多組建

更新伺服器不會把每個完整的組建並排存放。它以雜湊值為名存放物件，而一個組建只是一份清單：一串路徑，每個路徑附上大小與其內容的雜湊值。兩個共用 95 % 檔案的組建，就共用 95 % 的物件，不論是在磁碟上還是在網路上。如果每個組建只改變百分之幾的檔案，一個 500 MB 組建的十個版本只佔大約 600 MB，而不是 5 GB。而且「只下載改變的部分」不是啟動器的一項最佳化：它是啟動器唯一會做的事，因為它要求的是雜湊值，而不是檔案。

A few details of the layout, each paid for by a real or easily imagined failure:

  • Objects are filed under a sub-folder named after the first two characters of their hash. A Unity build has tens of thousands of files, and common file systems slow down noticeably past a few thousand entries in one directory. Two hexadecimal characters give 256 drawers, which keeps each at a few hundred objects up to dozens of builds.
  • The manifest is indented JSON, although it is a machine file and that makes it larger. When an update goes wrong, the first diagnostic gesture is to open the manifest in a browser, and it can be diffed if versioned; a few percent on a file a thousand times smaller than the build it describes is worth it.
  • Paths always use forward slashes, and a single function converts them. One forgotten backslash would make the launcher re-download a file it already has, on every launch, with nothing to report it.
  • Paths compare case-insensitively. On Windows, Data/x.dll and data/X.dll are the same file; treating them as two entries would download one over the other, then find the first missing, forever.
  • Duplicates are copied once. A build contains identical files under different names (licenses, empty files). The hash merges them, which is intended; the publisher just must not copy the same object twice.

Quelques détails du rangement, chacun payé par une panne réelle ou facile à imaginer :

  • Les objets sont rangés dans un sous-dossier nommé d'après les deux premiers caractères de leur hachage. Une build Unity compte des dizaines de milliers de fichiers, et les systèmes de fichiers courants ralentissent nettement au-delà de quelques milliers d'entrées dans un même dossier. Deux caractères hexadécimaux donnent 256 tiroirs, ce qui garde chacun à quelques centaines d'objets jusqu'à des dizaines de versions.
  • Le manifeste est du JSON indenté, bien que ce soit un fichier de machine et que ça le grossisse. Quand une mise à jour se passe mal, le premier geste de diagnostic est d'ouvrir le manifeste dans un navigateur, et on peut le comparer s'il est versionné ; quelques pour cent sur un fichier mille fois plus petit que la build qu'il décrit, ça vaut le coup.
  • Les chemins utilisent toujours des barres obliques, et une seule fonction les convertit. Une seule barre oblique inverse oubliée ferait retélécharger au launcher un fichier qu'il possède déjà, à chaque lancement, sans que rien ne le signale.
  • Les chemins se comparent sans tenir compte de la casse. Sous Windows, Data/x.dll et data/X.dll sont le même fichier ; les traiter comme deux entrées ferait télécharger l'un par-dessus l'autre, puis trouver le premier manquant, pour toujours.
  • Les doublons sont copiés une fois. Une build contient des fichiers identiques sous des noms différents (licences, fichiers vides). Le hachage les confond, c'est voulu ; l'outil de publication doit simplement ne pas copier deux fois le même objet.

配置中的幾個細節，每一個都是用一次真實或很容易想像到的失敗換來的：

  • 物件被歸檔在一個以其雜湊值前兩個字元命名的子資料夾中。一個 Unity 組建有數萬個檔案，而常見的檔案系統在單一目錄中超過幾千個項目後，會明顯變慢。兩個十六進位字元能提供 256 個抽屜，讓每個抽屜在累積數十個組建時仍然只有幾百個物件。
  • 清單是縮排過的 JSON，雖然它是給機器看的檔案，這會讓它變大。當一次更新出錯時，第一個診斷動作就是在瀏覽器中打開清單，而如果它有版本控制，還可以做差異比對；對一個比它所描述的組建小一千倍的檔案來說，多幾個百分比是值得的。
  • 路徑一律使用正斜線，並由單一函式負責轉換。一個被遺忘的反斜線，會讓啟動器在每次啟動時重新下載一個它早已擁有的檔案，而且沒有任何東西會回報這件事。
  • 路徑比較時不分大小寫。在 Windows 上，Data/x.dll 和 data/X.dll 是同一個檔案；把它們當成兩個項目，會讓一個被下載蓋在另一個上面，然後發現第一個不見了，永無止境。
  • 重複的檔案只複製一次。一個組建中會有不同名稱的相同檔案（授權條款、空檔案）。雜湊會把它們合併，這是刻意的；發布端只要不把同一個物件複製兩次就好。

A pointer, written last

The launcher knows exactly one path by heart: game/latest.json. That small file names the current build, the path of its manifest and the hash of the manifest. Everything else is deduced from it. It exists as a separate file, rather than the server answering "what is the latest version?", because a server that has to answer questions has logic, and a server with logic cannot be replaced by a shared folder. The manifest path is written in the pointer rather than deduced from a naming convention for the same reason: the day the layout changes, launchers already distributed follow without being replaced.

The pointer is also what makes publishing atomic, simply through the order of operations. As long as latest.json points at the previous build, the new one is invisible, so it can be half uploaded without anyone seeing it. Step through a publication:

Un pointeur, écrit en dernier

Le launcher ne connaît qu'un seul chemin par cœur : game/latest.json. Ce petit fichier nomme la version courante, le chemin de son manifeste et le hachage du manifeste. Tout le reste s'en déduit. Il existe comme fichier séparé, plutôt que le serveur réponde à « quelle est la dernière version ? », parce qu'un serveur qui doit répondre à des questions a une logique, et qu'un serveur qui a une logique ne peut pas être remplacé par un dossier partagé. Le chemin du manifeste est écrit dans le pointeur plutôt que déduit d'une convention de nommage pour la même raison : le jour où le rangement change, les launchers déjà distribués suivent sans être remplacés.

Le pointeur est aussi ce qui rend la publication atomique, simplement par l'ordre des opérations. Tant que latest.json pointe vers la version précédente, la nouvelle est invisible : elle peut être à moitié téléversée sans que personne ne la voie. Déroulez une publication :

一個最後才寫入的指標

啟動器只牢記一條路徑：game/latest.json。這個小檔案寫著目前的組建、其清單的路徑，以及清單的雜湊值。其他一切都由它推導出來。它之所以是一個獨立的檔案，而不是由伺服器回答「最新的版本是什麼？」，是因為一個必須回答問題的伺服器就有了邏輯，而一個有邏輯的伺服器就無法被一個共用資料夾取代。清單的路徑寫在指標中，而不是由命名慣例推導，也是同樣的道理：配置改變的那一天，已經發出去的啟動器不需要被取代就能跟上。

指標也讓發布變得不可分割，單純是透過操作的順序。只要 latest.json 還指向上一個組建，新的組建就是看不見的，所以它可以上傳到一半而沒有任何人看到。一步步看一次發布：

// The next number is derived from the manifests already published.
var build = NextBuild(serverRoot, channel);

// 1. Hash every file of the build.
var scan = BuildScanner.Scan(buildDir, channel, build, label, protocol, executable);

// 2. Copy the objects that are missing. An object already present under its
//    hash is, by definition, the right one: this is where the "diff" happens.
foreach (var file in scan.Manifest.Files)
{
    var target = ObjectPath(file.Sha256);
    if (File.Exists(target)) continue;
    File.Copy(Source(file), target + ".tmp", overwrite: true);  // copy beside...
    File.Move(target + ".tmp", target, overwrite: true);        // ...then rename
}

// 3. The manifest.
File.WriteAllText(ManifestPath(channel, build), manifestJson);

// 4. The pointer, LAST, in one move. It carries sha256(manifest).
File.WriteAllText(latest + ".tmp", pointer.ToJson());
File.Move(latest + ".tmp", latest, overwrite: true);

Swap two lines, and a power cut during a publication would hand every player a manifest describing files that do not exist. The pointer, too, is written beside and renamed rather than overwritten: publishing while the server is serving is the normal case here, and a plain write leaves a few microseconds during which a request can read an empty or half-written file. The launcher would then report "unreadable" on a perfectly successful publication: rare, impossible to reproduce, and searched for on the wrong side.

Rule

When readers follow a pointer, publish everything the pointer leads to before moving the pointer, and move it atomically.

The order of writes is the only atomicity such a system needs. It works on any storage that can rename a file.

Inversez deux lignes, et une coupure de courant pendant une publication donnerait à tous les joueurs un manifeste décrivant des fichiers qui n'existent pas. Le pointeur, lui aussi, est écrit à côté puis renommé plutôt qu'écrasé : publier pendant que le serveur sert est le cas normal ici, et une écriture directe laisse quelques microsecondes pendant lesquelles une requête peut lire un fichier vide ou à moitié écrit. Le launcher dirait alors « illisible » sur une publication parfaitement réussie : rare, impossible à reproduire, et cherché du mauvais côté.

Règle

Quand des lecteurs suivent un pointeur, publier tout ce vers quoi mène le pointeur avant de déplacer le pointeur, et le déplacer de façon atomique.

L'ordre des écritures est la seule atomicité dont un tel système a besoin. Elle fonctionne sur n'importe quel stockage capable de renommer un fichier.

交換其中兩行，一次發布途中的停電就會給每位玩家一份描述著不存在之檔案的清單。指標同樣是寫在旁邊再改名，而不是直接覆寫：在這裡，一邊服務一邊發布是正常情況，而直接寫入會留下幾微秒的空檔，讓某個請求讀到一個空的或寫到一半的檔案。啟動器就會在一次完全成功的發布上回報「無法讀取」：罕見、無法重現，而且會在錯誤的那一端被追查。

規則

當讀取端是跟著指標走的時候，在移動指標之前，先發布指標所通往的一切，並以不可分割的方式移動它。

寫入的順序，就是這類系統唯一需要的不可分割性。它在任何能為檔案改名的儲存空間上都能運作。

Two channels, one store

The game and the launcher are published separately: they change at unrelated rhythms (the game three times an evening, the launcher three times a year), and each has its own pointer and its own build numbering. Mixing the numbering would make a number jump without any version being published. They share one object store anyway, not to save space (they share almost nothing) but because one store means one clean-up, one download path and one thing to back up.

Every manifest and every pointer names its channel, redundantly with the URL it came from, and the launcher refuses a manifest from the wrong one: a mistyped URL would otherwise install the launcher in the game's folder, then the game over the launcher. On the publishing side, the channel is a mandatory word with no default. A default of "game" would be handy nine times out of ten and catastrophic the tenth: publishing the launcher on the game channel would replace everyone's build with an executable that cannot play.

Deux canaux, un magasin

Le jeu et le launcher se publient séparément : ils changent à des rythmes sans rapport (le jeu trois fois par soirée, le launcher trois fois par an), et chacun a son propre pointeur et sa propre numérotation. Mélanger les numérotations ferait bondir un numéro sans qu'aucune version n'ait été publiée. Ils partagent quand même un seul magasin d'objets, non pour économiser (ils ne partagent presque rien) mais parce qu'un seul magasin veut dire un seul nettoyage, un seul chemin de téléchargement et une seule chose à sauvegarder.

Chaque manifeste et chaque pointeur nomme son canal, de façon redondante avec l'URL d'où il vient, et le launcher refuse un manifeste du mauvais canal : une URL mal recopiée installerait sinon le launcher dans le dossier du jeu, puis le jeu par-dessus le launcher. Côté publication, le canal est un mot obligatoire, sans valeur par défaut. Un défaut « game » serait pratique neuf fois sur dix et catastrophique la dixième : publier le launcher sur le canal du jeu remplacerait la build de tout le monde par un exécutable qui ne sait pas jouer.

兩個頻道，一個儲存區

遊戲與啟動器是分開發布的：它們以毫不相關的節奏改變（遊戲一個晚上三次，啟動器一年三次），而且各有自己的指標與自己的組建編號。混用編號，會讓一個號碼在沒有發布任何版本的情況下跳號。不過它們仍然共用一個物件儲存區，不是為了省空間（它們幾乎沒有共用任何東西），而是因為一個儲存區就意味著一次清理、一條下載路徑，以及一個要備份的東西。

每份清單與每個指標都會寫出自己的頻道，與它的來源 URL 互相重複，而啟動器會拒絕來自錯誤頻道的清單：否則一個打錯的 URL，就會把啟動器安裝到遊戲的資料夾中，再把遊戲裝在啟動器上面。在發布端，頻道是一個必填、沒有預設值的字。預設「game」十次有九次很方便，第十次卻是災難：把啟動器發布到遊戲頻道上，會把每個人的組建換成一個無法遊玩的執行檔。

What never ships

Some files in a build folder must never reach a player. The exclusion list is short and explicit, never a clever filter: the day a legitimate file disappears from players' installations, you want to read why in five seconds.

ExcludedWhy
.pdb, .mdbDebug symbols: heavy, useless to a player.
folders ending in _BurstDebugInformation_DoNotShip or _BackUpThisFolder_ButDontShipItWithYourGameUnity says so in the folder name. Hundreds of megabytes that the home upload link would carry to every new player.
.qwak-installed.json, launcher.json, anywhere in the treeFiles the launcher writes itself. Publishing them creates a cycle (below).
the launcher-neuf/ folderThe launcher's staging folder for its own updates (chapter 8.2).

Pitfall I hit

Unity prefixes those debug folders with the product name: the real folder is QwakClient_BurstDebugInformation_DoNotShip. The first filter tested equality with _BurstDebugInformation_DoNotShip, so it could never match, and debug symbols were published from the very beginning. Silently: the "skipped" counter faithfully displayed zero. The filter now tests the suffix. A filter that never matches looks exactly like a filter with nothing to do; test it once against the real case.

The launcher's control files deserve their own rule. .qwak-installed.json records which manifest was last applied; it is written by the launcher at the end of every update. Published inside a manifest, it describes a file whose content depends on the manifest itself. That exact cycle produced an infinite update loop, told in chapter 8.2. The player's launcher.json is excluded for a second reason, just as serious: publishing it would overwrite, at every launcher update, the server address each person typed.

Rule

A manifest never describes a file that depends on it.

Ce qui ne part jamais

Certains fichiers d'un dossier de build ne doivent jamais atteindre un joueur. La liste d'exclusion est courte et explicite, jamais un filtre malin : le jour où un fichier légitime disparaît des installations des joueurs, on veut pouvoir lire pourquoi en cinq secondes.

Le premier filtre testait l'égalité avec _BurstDebugInformation_DoNotShip : il ne pouvait jamais correspondre, et les symboles de débogage ont été publiés depuis le tout début. En silence : le compteur « ignoré(s) » affichait consciencieusement zéro. Le filtre teste maintenant le suffixe. Un filtre qui ne correspond jamais ressemble exactement à un filtre qui n'a rien à faire ; le tester une fois contre le cas réel.

Les fichiers de contrôle du launcher méritent leur propre règle. .qwak-installed.json enregistre quel manifeste a été appliqué en dernier ; le launcher l'écrit à la fin de chaque mise à jour. Publié dans un manifeste, il décrit un fichier dont le contenu dépend du manifeste lui-même. Ce cycle précis a produit une boucle de mise à jour infinie, racontée au chapitre 8.2. Le launcher.json du joueur est exclu pour une seconde raison, tout aussi grave : le publier écraserait, à chaque mise à jour du launcher, l'adresse de serveur que chacun a saisie.

Règle

Un manifeste ne décrit jamais un fichier qui dépend de lui.

永遠不會出貨的東西

組建資料夾中有些檔案絕不能送到玩家手上。排除清單簡短而明確，絕不是一個聰明的過濾器：當某個正當的檔案從玩家的安裝中消失的那一天，你會希望在五秒內讀到原因。

被排除的原因
.pdb、.mdb除錯符號：很重，對玩家毫無用處。

樹中任何位置的 .qwak-installed.json、launcher.json由啟動器自己寫入的檔案。發布它們會造成一個循環（見下文）。
launcher-neuf/ 資料夾啟動器為自己的更新所用的暫存資料夾（第 8.2 章）。

我踩過的坑

Unity 會在這些除錯資料夾前面加上產品名稱：真正的資料夾是 QwakClient_BurstDebugInformation_DoNotShip。第一版的過濾器測試的是與 _BurstDebugInformation_DoNotShip 相等，所以它永遠不可能相符，而除錯符號從一開始就被發布了出去。無聲無息：「已略過」計數器忠實地顯示著零。現在過濾器測試的是後綴。一個永遠不相符的過濾器，看起來就和一個沒事可做的過濾器一模一樣；拿真實的案例測試它一次。

啟動器的控制檔案值得一條自己的規則。.qwak-installed.json 記錄最後套用的是哪一份清單；它在每次更新結束時由啟動器寫入。如果它被發布在一份清單中，就是在描述一個內容取決於這份清單本身的檔案。正是這個循環造成了一次無窮的更新迴圈，在第 8.2 章中講述。玩家的 launcher.json 被排除還有第二個同樣嚴重的理由：發布它，會在每次啟動器更新時，覆寫每個人自己輸入的伺服器位址。

規則

清單永遠不描述一個依賴它的檔案。

An update server with no logic at all

The update server computes nothing, compares nothing, knows neither versions nor players. It serves bytes under paths, like a file share, and all the intelligence lives in the manifest the publishing tool wrote and the launcher interprets. That is a property, not laziness: the day the home upload link is not enough, the program can be replaced by an object-storage bucket or any static host behind a CDN, and the launcher will not notice. It changes a URL.

Its whole configuration is a caching policy of two lines, and it follows directly from the design:

FileCache headerWhy
Objects and manifestspublic, max-age=31536000, immutableAn object's name is its content: it can never change, so any cache in front can keep it for a year. A manifest's number is never reused either.
latest.jsonno-storeThe one mutable file of the system. A one-hour cache here and a player would download a build an hour old while believing it is current, a failure nobody could diagnose, since everything looks "up to date" from their side.

The rule matches the file name, not the full path, so it covers both channels' pointers without listing channels, and it will cover the third. Two more settings exist only because objects are unusual files: they have no extension, and the static-file middleware refuses unknown types by default, which would answer 404 to every file of the build. They are served as application/octet-stream, the most neutral type, since no browser is meant to interpret them. Directory listing and default pages are off: a silent redirect would make a 404 indistinguishable from a malformed path.

At startup, the server reads each pointer once, only to print what it is serving. "The server is running" and "the server has something to serve" are two different states, and confusing them costs the quarter of an hour spent wondering why the launcher says "up to date" right after a publication.

Un serveur de mise à jour sans aucune logique

Le serveur de mise à jour ne calcule rien, ne compare rien, ne connaît ni versions ni joueurs. Il sert des octets sous des chemins, comme un partage de fichiers, et toute l'intelligence vit dans le manifeste qu'a écrit l'outil de publication et qu'interprète le launcher. C'est une propriété, pas de la paresse : le jour où le lien montant domestique ne suffira plus, le programme pourra être remplacé par un seau de stockage d'objets ou n'importe quel hébergement statique derrière un CDN, et le launcher ne s'en apercevra pas. Il change une URL.

Toute sa configuration tient en une politique de cache de deux lignes, qui découle directement de la conception :

FichierEn-tête de cachePourquoi
Objets et manifestespublic, max-age=31536000, immutableLe nom d'un objet est son contenu : il ne peut jamais changer, et n'importe quel cache devant peut le garder un an. Le numéro d'un manifeste n'est jamais réutilisé non plus.
latest.jsonno-storeLe seul fichier modifiable du système. Un cache d'une heure ici, et un joueur téléchargerait une version vieille d'une heure en la croyant à jour, une panne que personne ne saurait diagnostiquer, puisque tout semble « à jour » de son côté.

La règle porte sur le nom du fichier, pas sur le chemin complet : elle couvre les pointeurs des deux canaux sans énumérer les canaux, et couvrira le troisième. Deux autres réglages n'existent que parce que les objets sont des fichiers inhabituels : ils n'ont pas d'extension, et le middleware de fichiers statiques refuse par défaut les types inconnus, ce qui répondrait 404 à tous les fichiers de la build. Ils sont servis en application/octet-stream, le type le plus neutre, puisqu'aucun navigateur n'est censé les interpréter. L'affichage des dossiers et les pages par défaut sont coupés : une redirection silencieuse rendrait un 404 indiscernable d'un chemin mal formé.

Au démarrage, le serveur lit chaque pointeur une fois, seulement pour afficher ce qu'il sert. « Le serveur tourne » et « le serveur a quelque chose à servir » sont deux états différents, et les confondre coûte le quart d'heure passé à se demander pourquoi le launcher dit « à jour » juste après une publication.

完全沒有邏輯的更新伺服器

更新伺服器不計算任何東西、不比較任何東西，既不知道版本也不知道玩家。它像檔案分享一樣，以路徑提供位元組，所有的智慧都存在於發布工具所寫、由啟動器解讀的清單中。這是一個特性，而不是偷懶：當家用上傳頻寬不夠用的那一天，這個程式可以被一個物件儲存空間的 bucket 或任何 CDN 後面的靜態主機取代，而啟動器不會察覺。它只是換一個 URL。

它全部的設定，就是兩行快取策略，而這直接來自設計本身：

檔案快取標頭原因
物件與清單public, max-age=31536000, immutable物件的名稱就是它的內容：它永遠不會改變，所以前面的任何快取都可以保留它一年。清單的編號也永遠不會被重複使用。
latest.jsonno-store系統中唯一可變的檔案。在這裡快取一小時，玩家就會下載一個一小時前的組建，同時以為它是最新的，這是一個沒有人能診斷的失敗，因為從他那一端看，一切都「已是最新」。

這條規則比對的是檔案名稱，而不是完整路徑，所以它不必列出頻道就能涵蓋兩個頻道的指標，未來也會涵蓋第三個。另外兩項設定之所以存在，只是因為物件是不尋常的檔案：它們沒有副檔名，而靜態檔案中介軟體預設會拒絕未知的類型，這會讓組建中的每個檔案都回應 404。它們以 application/octet-stream 提供，這是最中性的類型，因為沒有任何瀏覽器需要解讀它們。目錄列表與預設頁面都關閉了：一次無聲的重新導向，會讓 404 與一個格式錯誤的路徑無法區分。

啟動時，伺服器會讀取每個指標一次，只為了印出它正在提供什麼。「伺服器正在執行」和「伺服器有東西可以提供」是兩種不同的狀態，把它們搞混的代價，是花十五分鐘納悶為什麼啟動器在一次發布之後立刻說「已是最新」。

Publishing: a keyboard, not a route

Publishing happens from the update server's own console while it keeps serving, or from a small command-line tool for scripts. Both call the same Publisher: one implementation means one order of steps to keep right. A copy in each program would drift, and the day one side changed the order, the other would keep writing latest.json too early without anyone noticing until an interrupted publication broke someone's installation. The command-line tool returns a non-zero exit code on failure, because it will end up in a script, and a failed publication that returns zero lets the chain carry on and "successfully" deploy a version that never went up.

Trade-off

An HTTP route to publish would have been handier still: publish from anywhere. That is exactly the problem. The process is exposed to the Internet through a NAT rule, and a route that reads a folder and rewrites what every launcher will download is remote code execution disguised as a convenience. A token to protect it would live in plain text on the very machine it protects. The machine's keyboard is the authentication, and it is free: the server gives bytes and accepts none.

After each publication, the console prints the number that matters next: how many new bytes a player will actually download from the previous build. It is also the measurement that will decide whether binary deltas are worth their complexity on these particular files. Twelve new megabytes justify no binary-diff machinery; 340 justify it at once. A patches/ folder is already reserved in the layout, and a delta will go from one object to another, two stable identities, without ever talking about versions.

Publier : un clavier, pas une route

La publication se fait depuis la console du serveur de mise à jour, pendant qu'il continue de servir, ou depuis un petit outil en ligne de commande pour les scripts. Les deux appellent le même Publisher : une seule implémentation veut dire un seul ordre d'étapes à garder juste. Une copie dans chaque programme dériverait, et le jour où un côté changerait l'ordre, l'autre continuerait d'écrire latest.json trop tôt sans que personne ne s'en aperçoive avant qu'une publication interrompue ne casse l'installation de quelqu'un. L'outil en ligne de commande rend un code de sortie non nul en cas d'échec, parce qu'il finira dans un script, et une publication ratée qui rend zéro laisse la chaîne continuer et déployer « avec succès » une version qui n'est jamais montée.

Compromis

Une route HTTP pour publier aurait été plus pratique encore : publier de n'importe où. C'est précisément le problème. Le processus est exposé à Internet par une règle NAT, et une route qui lit un dossier et réécrit ce que tous les launchers vont télécharger est une exécution de code à distance déguisée en commodité. Un jeton pour la protéger vivrait en clair sur la machine même qu'il protège. Le clavier de la machine est l'authentification, et elle est gratuite : le serveur rend des octets et n'en accepte aucun.

Après chaque publication, la console affiche le chiffre qui compte pour la suite : combien d'octets neufs un joueur téléchargera réellement depuis la version précédente. C'est aussi la mesure qui dira si des deltas binaires valent leur complexité sur ces fichiers-là. Douze mégaoctets neufs ne justifient aucune machinerie de diff binaire ; 340 la justifient tout de suite. Un dossier patches/ est déjà réservé dans le rangement, et un delta ira d'un objet à un autre, deux identités stables, sans jamais parler de versions.

發布：用鍵盤，而不是用路由

發布是在更新伺服器自己的主控台上進行的，它同時持續提供服務；或是透過一個供指令碼使用的小型命令列工具。兩者都呼叫同一個 Publisher：一份實作，就意味著只有一個需要保持正確的步驟順序。每個程式各有一份副本就會分歧，而當某一邊改了順序的那一天，另一邊會繼續太早寫入 latest.json，直到一次中斷的發布弄壞了某人的安裝之前，都沒有人會察覺。命令列工具在失敗時會回傳非零的結束代碼，因為它最後會被放進指令碼裡，而一次回傳零的失敗發布，會讓整條流程繼續下去，「成功地」部署一個從未上傳的版本。

取捨

用一個 HTTP 路由來發布會更方便：從任何地方都能發布。而這正是問題所在。這個程序透過一條 NAT 規則暴露在網際網路上，而一個會讀取資料夾、並改寫每個啟動器要下載之內容的路由，就是一個偽裝成便利功能的遠端程式碼執行。保護它的權杖，會以明文存放在它所要保護的那台機器上。機器的鍵盤就是認證，而且是免費的：這個伺服器只送出位元組，不接受任何位元組。

每次發布後，主控台會印出接下來最重要的那個數字：一位玩家從上一個組建更新時，實際上要下載多少新的位元組。這也是決定二進位差量是否值得它的複雜度的量測依據，就這些特定的檔案而言。新增 12 MB 不值得任何二進位差異比對的機制；340 MB 則立刻值得。配置中已經預留了一個 patches/ 資料夾，而差量會從一個物件到另一個物件，兩個穩定的身分，完全不需要談到版本。

Cleaning up: mark, then sweep

Content-addressed storage never rewrites an object, so it never frees anything by itself. Each build adds what is unique to it, and after twenty publications the unique objects of the first nineteen sleep on the disk. The prune command keeps the last N builds of each channel and deletes the objects that no remaining manifest cites. It is a small garbage collector, and it is built like one: mark everything that is alive first, sweep after. Deleting while walking would remove an object shared with a build being kept.

Faire le ménage : marquer, puis balayer

Le stockage par contenu ne réécrit jamais un objet, donc il ne libère jamais rien tout seul. Chaque version ajoute ce qui lui est propre, et au bout de vingt publications les objets uniques des dix-neuf premières dorment sur le disque. La commande prune garde les N dernières versions de chaque canal et supprime les objets qu'aucun manifeste restant ne cite. C'est un petit ramasse-miettes, construit comme tel : marquer d'abord tout ce qui est vivant, balayer ensuite. Supprimer en parcourant effacerait un objet partagé avec une version qu'on garde.

清理：先標記，再清掃

內容定址儲存從不改寫物件，所以它從不自己釋放任何東西。每個組建都會加入它獨有的物件，而在二十次發布之後，前十九次的獨有物件都還躺在磁碟上。prune 指令會保留每個頻道最後 N 個組建，並刪除沒有任何剩餘清單引用的物件。它是一個小型的垃圾回收器，也是照垃圾回收器的方式打造的：先標記所有存活的東西，之後才清掃。邊走邊刪，會刪掉一個與被保留組建共用的物件。

Three details make it safe:

  • Marking always covers every channel, even when you only meant to tidy one. Objects are shared, so a sweep that looked only at the launcher channel would delete the game's files. No error, no trace: the first sign would be a player's download failing with a 404 on an object the manifest promises.
  • The online build of each channel is untouchable, whatever N says. Even a mistyped prune 1 leaves latest.json pointing at a manifest whose objects all exist.
  • Without the word go, it only reports. prune 3 shows what would be deleted; prune 3 go deletes it. Old builds exist nowhere else, so two extra characters are cheap insurance.

Trois détails la rendent sûre :

  • Le marquage couvre toujours tous les canaux, même quand on ne voulait ranger que l'un d'eux. Les objets sont partagés : un balayage qui ne regarderait que le canal du launcher effacerait les fichiers du jeu. Sans erreur, sans trace : le premier signe serait le téléchargement d'un joueur qui échoue sur un 404, pour un objet que le manifeste promet.
  • La version en ligne de chaque canal est intouchable, quoi que dise N. Même un prune 1 mal tapé laisse latest.json pointer vers un manifeste dont tous les objets existent.
  • Sans le mot go, elle ne fait que rapporter. prune 3 montre ce qui serait supprimé ; prune 3 go le supprime. Les anciennes versions n'existent nulle part ailleurs : deux caractères de plus sont une assurance bon marché.

有三個細節讓它安全：

  • 標記永遠涵蓋每一個頻道，即使你只想整理其中一個。物件是共用的，所以一次只看啟動器頻道的清掃，會刪掉遊戲的檔案。沒有錯誤、沒有痕跡：第一個徵兆會是某位玩家的下載在一個清單承諾存在的物件上得到 404。
  • 每個頻道的線上組建都不可碰，不論 N 是多少。即使打錯成 prune 1，latest.json 指向的清單所列出的物件也都仍然存在。
  • 沒有 go 這個字，它就只報告。prune 3 顯示會刪除什麼；prune 3 go 才真的刪除。舊組建在其他地方都不存在，多打兩個字元是便宜的保險。

Integrity is not authenticity

Hashes prove that a file is the one the manifest describes: nothing truncated, corrupted or mis-copied. They prove nothing about who wrote the manifest. Over plain HTTP, anyone on the path can serve a coherent manifest with the files of their choice, and the launcher will diligently verify that they match before running them. This is a channel that delivers code, and the source says so once, plainly, rather than spreading a false sense of security over three files.

The remedy is already prepared in the format. The pointer carries the hash of the manifest, which carries the hashes of every object, so the whole chain goes back to one small file: signing latest.json authenticates everything. The repository already has the RSA machinery (the one game servers use to prove their identity to the gateway, chapter 2.1). Nothing verifies a signature yet; the point is that the day it is added, no format has to change. Meanwhile, the manifest hash in the pointer already catches two very real failures: a manifest half written by an interrupted publication, and an HTTP cache serving one version of the pointer and another of the manifest.

Pitfall I hit

A build was published with its executable given as a full path, and the manifest went out with C:/Users/<me>/…/QwakClient.exe. The check "does the executable exist?" confirmed it, because combining a folder with an absolute path returns the absolute path, and on the publishing machine it existed. The other player's launcher looked for a folder that only existed on mine. Harmless that time, and it revealed a real hole: the launcher writes where the manifest says and runs what it names, so a path like C:/Windows/… or ../../.. would make it write, and run, anywhere on the machine. Now the publishing tool converts a full path that points inside the build into a relative one (pasting a path from the file explorer is the natural gesture) and refuses one outside it. The launcher checks every path again before believing anything, and a single bad path rejects the whole manifest.

Rule

A path that comes from the network is data, never a location. Check that it stays inside, where it enters.

L'intégrité n'est pas l'authenticité

Les hachages prouvent qu'un fichier est celui que décrit le manifeste : rien de tronqué, corrompu ou mal recopié. Ils ne prouvent rien sur qui a écrit le manifeste. En HTTP simple, n'importe qui sur le chemin peut servir un manifeste cohérent avec les fichiers de son choix, et le launcher vérifiera consciencieusement qu'ils correspondent avant de les lancer. C'est un canal qui livre du code, et le source le dit une fois, clairement, plutôt que de répandre un faux sentiment de sécurité sur trois fichiers.

Le remède est déjà préparé dans le format. Le pointeur porte le hachage du manifeste, qui porte les hachages de chaque objet : toute la chaîne remonte à un seul petit fichier, et signer latest.json authentifie tout. Le dépôt a déjà la mécanique RSA (celle qu'utilisent les serveurs de jeu pour prouver leur identité à la gateway, chapitre 2.1). Rien ne vérifie encore de signature ; l'intérêt est que le jour où on l'ajoute, aucun format n'a à changer. En attendant, le hachage du manifeste dans le pointeur attrape déjà deux pannes bien réelles : un manifeste à moitié écrit par une publication interrompue, et un cache HTTP qui sert une version du pointeur et une autre du manifeste.

Piège rencontré

Une build a été publiée avec son exécutable donné en chemin complet, et le manifeste est parti avec C:/Users/<moi>/…/QwakClient.exe. La vérification « l'exécutable existe-t-il ? » l'a confirmé, parce que combiner un dossier avec un chemin absolu rend le chemin absolu, et que sur la machine qui publiait, il existait. Le launcher de l'autre joueur a cherché un dossier qui n'existait que chez moi. Sans conséquence cette fois, et cela a révélé un vrai trou : le launcher écrit où dit le manifeste et lance ce qu'il nomme, donc un chemin comme C:/Windows/… ou ../../.. le ferait écrire, et exécuter, n'importe où sur la machine. Désormais, l'outil de publication convertit un chemin complet qui pointe dans la build en chemin relatif (coller un chemin depuis l'explorateur est le geste naturel) et refuse celui qui en sort. Le launcher revérifie chaque chemin avant de croire quoi que ce soit, et un seul mauvais chemin fait rejeter tout le manifeste.

Règle

Un chemin venu du réseau est une donnée, jamais un emplacement. Vérifier qu'il reste à l'intérieur, là où il entre.

完整性不等於真實性

雜湊能證明一個檔案就是清單所描述的那一個：沒有被截斷、損壞或複製錯誤。它無法證明清單是誰寫的。在純 HTTP 上，路徑上的任何人都可以提供一份前後一致、裝著他所選檔案的清單，而啟動器會勤奮地驗證它們相符之後再執行它們。這是一條傳遞程式碼的通道，而原始碼一次、明白地這樣寫著，而不是把一種虛假的安全感散布在三個檔案中。

補救方法已經在格式中準備好了。指標攜帶清單的雜湊值，清單攜帶每個物件的雜湊值，所以整條鏈都回溯到一個小檔案：為 latest.json 簽章，就能認證一切。程式庫中已經有 RSA 的機制（遊戲伺服器用來向閘道證明身分的那一套，第 2.1 章）。目前還沒有任何東西驗證簽章；重點是，加入它的那一天，不需要改變任何格式。在此同時，指標中的清單雜湊值已經能抓到兩種非常真實的失敗：一份被中斷的發布寫了一半的清單，以及一個提供某個版本的指標、卻提供另一個版本清單的 HTTP 快取。

我踩過的坑

有一個組建在發布時，執行檔是以完整路徑給定的，於是清單帶著 C:/Users/<me>/…/QwakClient.exe 被送了出去。「執行檔存在嗎？」的檢查確認了它，因為把一個資料夾與一個絕對路徑組合，會回傳那個絕對路徑，而在發布的機器上它確實存在。另一位玩家的啟動器去找一個只存在於我電腦上的資料夾。那次無害，卻揭露了一個真正的漏洞：啟動器會寫入清單說的地方，並執行它所指名的東西，所以一個像 C:/Windows/… 或 ../../.. 這樣的路徑，會讓它在機器上任何地方寫入並執行。現在發布工具會把指向組建內部的完整路徑轉成相對路徑（從檔案總管貼上路徑是很自然的動作），並拒絕指向組建外部的路徑。啟動器在相信任何東西之前，會再次檢查每一條路徑，只要有一條壞路徑就拒絕整份清單。

規則

來自網路的路徑是資料，絕不是位置。在它進入的地方，就檢查它是否留在內部。

Key takeaways

  • Identify files by the SHA-256 of their content, streamed; any client in any state then needs only "the missing objects".
  • Store objects once, under their hash, and describe builds as manifests; sharing between builds comes for free.
  • Publish objects, then the manifest, then a tiny pointer, each by write-then-rename; interruptions leave only orphans.
  • Keep the update server logic-free: cache immutable objects for a year and the pointer never.
  • Exclude debug output and every file the launcher writes itself; a manifest never describes a file that depends on it.
  • Collect garbage by marking across all channels before sweeping, never touch the online build, and default to a dry run.
  • Treat hashes as integrity only; prepare a signature on the pointer, and reject any manifest path that leaves the installation.

À retenir

  • Identifier les fichiers par le SHA-256 de leur contenu, calculé en flux ; tout client, dans n'importe quel état, n'a alors besoin que des « objets manquants ».
  • Stocker les objets une fois, sous leur hachage, et décrire les versions par des manifestes ; le partage entre versions vient gratuitement.
  • Publier les objets, puis le manifeste, puis un minuscule pointeur, chacun par écriture puis renommage ; les interruptions ne laissent que des orphelins.
  • Garder le serveur de mise à jour sans logique : mettre en cache les objets immuables pour un an et le pointeur jamais.
  • Exclure les sorties de débogage et chaque fichier que le launcher écrit lui-même ; un manifeste ne décrit jamais un fichier qui dépend de lui.
  • Ramasser les miettes en marquant sur tous les canaux avant de balayer, ne jamais toucher la version en ligne, et faire d'un essai à blanc le comportement par défaut.
  • Traiter les hachages comme de l'intégrité seulement ; préparer une signature sur le pointeur, et rejeter tout chemin de manifeste qui sort de l'installation.

重點整理

  • 以串流方式計算檔案內容的 SHA-256 來識別檔案；任何狀態下的任何用戶端，就都只需要「缺少的物件」。
  • 以雜湊值為名，每個物件只存一次，並把組建描述為清單；組建之間的共用就免費得到了。
  • 先發布物件，再發布清單，最後是一個小小的指標，每一步都是先寫入再改名；中斷只會留下孤兒。
  • 讓更新伺服器保持沒有邏輯：不可變的物件快取一年，指標永遠不快取。
  • 排除除錯輸出與啟動器自己寫入的每個檔案；清單永遠不描述一個依賴它的檔案。
  • 在清掃之前跨所有頻道標記來回收垃圾，絕不碰線上組建，並預設為只演練不執行。
  • 把雜湊只當作完整性；為指標準備一個簽章，並拒絕任何離開安裝目錄的清單路徑。

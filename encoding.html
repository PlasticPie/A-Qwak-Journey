Squeezing bytesÉconomiser les octets

Variable-length integers, zig-zag, quantization, and the size cliffs that quietly decide your bandwidth.Les entiers de taille variable, le zig-zag, la quantification, et les falaises de taille qui décident en silence de la bande passante.

Why one byte matters

A byte saved once is nothing. A byte saved on every object, in every snapshot, for every player is multiplied three times. One byte per ship, 60 ships in view, 25 snapshots a second, 600 players on a map: that is 900 KB/s of outgoing traffic for one byte. The encodings below are how the average ship in a MoonQwak snapshot came down to about 19 bytes: its id, its type, a flag byte, its position, heading and velocities, and the angle of its turrets.

Pourquoi un octet compte

Un octet économisé une fois, ce n'est rien. Un octet économisé sur chaque objet, dans chaque snapshot, pour chaque joueur est multiplié trois fois. Un octet par vaisseau, 60 vaisseaux en vue, 25 snapshots par seconde, 600 joueurs sur une carte : ça fait 900 Ko/s de trafic sortant pour un octet. Les encodages ci-dessous expliquent comment le vaisseau moyen d'un snapshot de MoonQwak est descendu à environ 19 octets : son identifiant, son type, un octet de drapeaux, sa position, son cap et ses vitesses, et l'angle de ses tourelles.

Variable-length integers

Most numbers in a game are small: counts, ids, quantities, small coordinates. Writing each one as a fixed 4- or 8-byte integer wastes most of those bytes. A varint uses fewer bytes for smaller values. MoonQwak's format puts the size in the top bits of the first byte, then stores the value big-endian:

anything larger90xFF + 8 bytes

The reader looks at one byte, knows the total size, and reads the rest in one go. The encoder in the lab below is a direct port of the project's code, so you can check any value.

Des entiers de taille variable

La plupart des nombres d'un jeu sont petits : comptes, identifiants, quantités, petites coordonnées. Écrire chacun sur 4 ou 8 octets fixes gaspille l'essentiel de ces octets. Un varint utilise moins d'octets pour les petites valeurs. Le format de MoonQwak met la taille dans les bits de poids fort du premier octet, puis stocke la valeur en gros-boutiste :

ValeursOctetsPremier octet
0 à 12610xxxxxxx, la valeur elle-même

jusqu'à 260 − 281110xxxx + 7 octets
au-delà90xFF + 8 octets

Le lecteur regarde un octet, connaît la taille totale, et lit le reste d'un coup. L'encodeur du labo ci-dessous est une transcription directe du code du projet : vous pouvez vérifier n'importe quelle valeur.

Trade-off

The format has no 3-byte size. The common alternative, LEB128 (used by Protocol Buffers), stores 7 bits per byte with a continuation bit and grows one byte at a time: 3 bytes reach 2,097,151. MoonQwak's layout decodes with a single branch but jumps from 2 to 4 bytes at 16,383. That jump is the "cliff" this chapter keeps coming back to. The format was kept because every byte already on the wire depends on it; the cliffs were worked around by choosing scales and id ranges instead.

One more oddity kept for compatibility: the one-byte test is "strictly less than 127", so the value 127 itself takes two bytes.

Compromis

Le format n'a pas de taille 3 octets. L'alternative courante, LEB128 (celle de Protocol Buffers), stocke 7 bits par octet avec un bit de continuation et grandit d'un octet à la fois : 3 octets vont jusqu'à 2 097 151. La disposition de MoonQwak se décode en une seule branche, mais saute de 2 à 4 octets à 16 383. Ce saut est la « falaise » dont ce chapitre reparle sans cesse. Le format a été gardé parce que chaque octet déjà sur le fil en dépend ; on a contourné les falaises en choisissant les échelles et les plages d'identifiants.

Une dernière bizarrerie gardée pour la compatibilité : le test à un octet est « strictement inférieur à 127 », donc la valeur 127 elle-même prend deux octets.

Network/VarInt.cs · encoding without allocating
private static int EncodeUVarInt(ulong value, Span<byte> dst)
{
    if (value < 0x7f) { dst[0] = (byte)value; return 1; }
    if (value < 0x3fff)
    {
        var v = (ushort)(value | 0x8000);    // prefix 10
        dst[0] = (byte)(v >> 8); dst[1] = (byte)v;
        return 2;
    }
    if (value < 0x1fffffff)
    {
        var v = (uint)(value | 0xc0000000);  // prefix 110
        dst[0] = (byte)(v >> 24); dst[1] = (byte)(v >> 16); dst[2] = (byte)(v >> 8); dst[3] = (byte)v;
        return 4;
    }
    // ... 8-byte (prefix 1110) and 9-byte (0xFF marker) cases
}

public static void WriteUVarInt(ulong value, BinaryWriter writer)
{
    Span<byte> buf = stackalloc byte[9];  // no heap allocation per value
    writer.Write(buf.Slice(0, EncodeUVarInt(value, buf)));
}

Measured

The first version of this encoder created a lambda and at least one byte[] per value written, including single-byte values, and the reader mirrored it. Every varint field of every packet went through it, on the server and on the client. Rewriting both sides with stackalloc and direct reads, checked byte for byte against the old output, was one of the largest CPU wins of the whole performance pass.

Mesuré

La première version de cet encodeur créait une lambda et au moins un byte[] par valeur écrite, y compris pour les valeurs d'un octet, et le lecteur faisait de même. Chaque champ varint de chaque paquet passait par là, côté serveur comme côté client. Réécrire les deux côtés avec stackalloc et des lectures directes, vérifiées octet pour octet contre l'ancienne sortie, a été l'un des plus gros gains CPU de toute la passe de performance.

Negative numbers: zig-zag

A varint is unsigned. Cast −1 to an unsigned 64-bit integer and you get the largest possible value, which costs the maximum 9 bytes, the opposite of what you want for a small offset. Zig-zag encoding interleaves positive and negative values before the varint: 0, −1, 1, −2, 2 become 0, 1, 2, 3, 4. Small magnitudes stay small whatever their sign.

Les nombres négatifs : le zig-zag

Un varint est non signé. Convertissez −1 en entier non signé de 64 bits et vous obtenez la plus grande valeur possible, qui coûte le maximum de 9 octets, l'inverse de ce qu'on veut pour un petit décalage. L'encodage zig-zag entrelace positifs et négatifs avant le varint : 0, −1, 1, −2, 2 deviennent 0, 1, 2, 3, 4. Les petites valeurs restent petites quel que soit leur signe.

Network/VarInt.cs
private static ulong ZigZagEncode(long value) => (ulong)((value << 1) ^ (value >> 63));
private static long ZigZagDecode(ulong value) => (long)(value >> 1) ^ -(long)(value & 1);

The price of zig-zag is that it doubles every magnitude. A signed value fits in two bytes only while its zig-zag form stays under 16,383, which means between −8,191 and +8,191. That factor of two is easy to forget when you do the arithmetic in your head, and the next section shows what it costs when you do.

Le prix du zig-zag est qu'il double chaque valeur absolue. Une valeur signée ne tient sur deux octets que tant que sa forme zig-zag reste sous 16 383, c'est-à-dire entre −8 191 et +8 191. Ce facteur deux est facile à oublier quand on fait le calcul de tête, et la section suivante montre ce que ça coûte quand on l'oublie.

Quantization: floats as scaled integers

A double always costs 8 bytes and carries far more precision than a screen can show. Quantization multiplies the value by a scale, rounds it, and sends the integer as a zig-zag varint. The receiver divides by the same scale. The scales live in one shared class, because a mismatched scale between writer and reader does not throw: it silently multiplies every position by the ratio.

QuantityScaleStepTwo-byte range
Ship and character position402.5 cm±204.8 units
Ship velocity1001 cm/s±81.9 units/s
Bullet position and velocity1010 cm±819.1 units
Angular velocity1,0000.001 rad/s±8.19 rad/s
Headingfixed 16 bits: a fraction of a full turn, about 0.0001 rad per step

The heading is the exception: a ship is as likely to point one way as another, so a varint (which rewards small values) would not help. Two fixed bytes covering the whole circle are four times smaller than a double and cost the same for every angle.

La quantification : des flottants en entiers mis à l'échelle

Un double coûte toujours 8 octets et porte bien plus de précision qu'un écran ne peut en montrer. La quantification multiplie la valeur par une échelle, l'arrondit, et envoie l'entier en varint zig-zag. Le récepteur divise par la même échelle. Les échelles vivent dans une seule classe partagée, parce qu'une échelle différente entre écrivain et lecteur ne lève pas d'erreur : elle multiplie en silence chaque position par le rapport.

GrandeurÉchellePasPlage sur deux octets
Position d'un vaisseau ou d'un personnage402,5 cm±204,8 unités
Vitesse d'un vaisseau1001 cm/s±81,9 unités/s
Position et vitesse d'une balle1010 cm±819,1 unités
Vitesse angulaire1 0000,001 rad/s±8,19 rad/s
Cap16 bits fixes : une fraction de tour complet, environ 0,0001 rad par pas

Le cap est l'exception : un vaisseau a autant de chances de pointer dans une direction que dans une autre, donc un varint (qui récompense les petites valeurs) n'aiderait pas. Deux octets fixes couvrant tout le cercle sont quatre fois plus petits qu'un double et coûtent pareil pour tous les angles.

Packet/BasePacket.cs
public void WriteQuantized(double value, double scale) => WriteVarInt((long)Math.Round(value * scale));
public double ReadQuantized(double scale) => ReadVarInt() / scale;

public void WriteAngle(double radians)
{
    var turns = radians / (2 * Math.PI);
    turns -= Math.Floor(turns);  // wrap into [0, 1)
    Write((ushort)((int)Math.Round(turns * 65536.0) & 0xFFFF));
}

The cliffs, three times

Because the size jumps from 2 to 4 bytes at a fixed threshold, a small change in a value can double its cost. Three separate optimizations in MoonQwak were about keeping frequent values on the right side of that edge.

Positions and the size of the map

When the map radius went from 100 to 400 units, ships spent most of their time far from the center, and their coordinates crossed the threshold. A trace showed the same ship weighing 23 bytes while cruising and 19 bytes in a fight near the center: the 4 extra bytes were two coordinates that had each grown to 4 bytes. The position scale went from 100 (1 cm) to 40 (2.5 cm), which moved the edge from 81.9 to 204.8 units from the center.

Pitfall I hit

The first calculation of this change divided 16,383 by the scale and concluded that ±409 units would fit in two bytes at a scale of 40, which would have covered the whole map. It forgot that zig-zag doubles the value first, so the real limit is 8,191 steps, ±204.8 units. On a map of radius 400, positions beyond about 205 units from the center still take four bytes per axis. The lab above shows it: try 204 and 206 in "Ship position". Covering the whole map in two bytes needs a scale of 20 (5 cm steps) or less.

Ids that kept growing

Every object gets a network id from a counter that is never reused. Bullets live about a second and hundreds are fired every second, so the counter passed 16,383 within minutes of a battle, and every id from then on cost four bytes. In a melee, ids were about 14% of the snapshot. The fix gives bullets their own recycled band of ids, 8,192 to 16,382, all of which fit in two bytes (ids are unsigned, so no zig-zag here). An id goes back to the band only after a 10-second quarantine, much longer than the client ever remembers a bullet, so a recycled id can never be confused with an old one. The counter for everything else skips the band. (3.6)

Bullet velocities

The fastest bullet in the catalog flies at 88 units per second. Written at the ship scale of 1/100, a velocity component that large is 8,800 steps before zig-zag and 17,600 after: four bytes. Bullets got their own scale of 1/10, where ±819 units per second fit in two bytes. The error is 5 cm on position and 5 cm/s on speed, which after a full second of flight puts the client's bullet 0.1 units away from the server's, on hulls whose cells have a radius of 3.

Les falaises, trois fois

Comme la taille saute de 2 à 4 octets à un seuil fixe, un petit changement de valeur peut doubler son coût. Trois optimisations distinctes de MoonQwak ont consisté à garder des valeurs fréquentes du bon côté de ce bord.

Les positions et la taille de la carte

Quand le rayon de la carte est passé de 100 à 400 unités, les vaisseaux ont passé l'essentiel de leur temps loin du centre, et leurs coordonnées ont franchi le seuil. Une trace a montré le même vaisseau à 23 octets en croisière et à 19 octets dans un combat près du centre : les 4 octets de plus étaient deux coordonnées passées chacune à 4 octets. L'échelle des positions est passée de 100 (1 cm) à 40 (2,5 cm), ce qui a déplacé le bord de 81,9 à 204,8 unités du centre.

Piège rencontré

Le premier calcul de ce changement divisait 16 383 par l'échelle et concluait qu'à 40, ±409 unités tiendraient sur deux octets, ce qui aurait couvert toute la carte. Il oubliait que le zig-zag double d'abord la valeur : la vraie limite est de 8 191 pas, soit ±204,8 unités. Sur une carte de rayon 400, les positions au-delà d'environ 205 unités du centre prennent encore quatre octets par axe. Le labo ci-dessus le montre : essayez 204 et 206 en « Position de coque ». Couvrir toute la carte sur deux octets demande une échelle de 20 (pas de 5 cm) ou moins.

Des identifiants qui grandissaient

Chaque objet reçoit un identifiant réseau d'un compteur jamais réutilisé. Une balle vit environ une seconde et il en part des centaines par seconde : le compteur a dépassé 16 383 en quelques minutes de bataille, et chaque identifiant a ensuite coûté quatre octets. Dans une mêlée, les identifiants faisaient environ 14 % du snapshot. La correction donne aux balles leur propre bande d'identifiants recyclés, de 8 192 à 16 382, qui tiennent tous sur deux octets (les identifiants sont non signés, donc sans zig-zag). Un identifiant ne revient dans la bande qu'après une quarantaine de 10 secondes, bien plus longue que la mémoire qu'a le client d'une balle : un identifiant recyclé ne peut jamais être confondu avec l'ancien. Le compteur de tout le reste saute la bande. (3.6)

La vitesse des balles

La balle la plus rapide du catalogue vole à 88 unités par seconde. Écrite à l'échelle des vaisseaux de 1/100, une composante de vitesse de cette taille fait 8 800 pas avant zig-zag et 17 600 après : quatre octets. Les balles ont reçu leur propre échelle de 1/10, où ±819 unités par seconde tiennent sur deux octets. L'erreur est de 5 cm sur la position et 5 cm/s sur la vitesse, ce qui, après une seconde de vol, place la balle du client à 0,1 unité de celle du serveur, sur des coques dont les cellules ont un rayon de 3.

Rule

For every frequent value, know which side of the size cliff it lives on, and compute it with the encoding actually used.

With a signed varint, the two-byte range is ±8,191 steps, not 16,383. Divide by the scale, then compare with the real range of the value (map radius, top speed, id lifetime).

Règle

Pour chaque valeur fréquente, savoir de quel côté de la falaise de taille elle vit, et le calculer avec l'encodage réellement utilisé.

Avec un varint signé, la plage sur deux octets est de ±8 191 pas, pas 16 383. Diviser par l'échelle, puis comparer avec la plage réelle de la valeur (rayon de la carte, vitesse maximale, durée de vie des identifiants).

Flag bytes: pay only for what changed

The cheapest field is the one you do not send. Each ship in a snapshot starts with a flag byte whose bits announce which optional blocks follow: movement, a hull rebuild, per-hex state, turret angles, laser beams, effects, crew posts, fire. A ship sitting still with nothing happening costs its id, its type and that byte.

Two details made this work. The movement bit is also sent on the exact tick a ship stops, so every viewer settles on the final position instead of extrapolating past it. And the per-hex state block covers every field it sends: an early version compared four of five fields, so the fifth (a hex running short of power) never triggered a send and was silently invisible to other players. Chapter 4.4 tells the full story of that block.

Les octets de drapeaux : ne payer que ce qui a changé

Le champ le moins cher est celui qu'on n'envoie pas. Chaque vaisseau d'un snapshot commence par un octet de drapeaux dont les bits annoncent quels blocs optionnels suivent : mouvement, reconstruction de coque, état par hex, angles des tourelles, rayons laser, effets, postes d'équipage, feu. Un vaisseau immobile à qui rien n'arrive coûte son identifiant, son type et cet octet.

Deux détails ont rendu ça correct. Le bit de mouvement est aussi envoyé au tick exact où un vaisseau s'arrête, pour que chaque spectateur se cale sur la position finale au lieu d'extrapoler au-delà. Et le bloc d'état par hex couvre tous les champs qu'il envoie : une première version comparait quatre champs sur cinq, si bien que le cinquième (un hex à court d'énergie) ne déclenchait jamais d'envoi et restait invisible aux autres joueurs. Le chapitre 4.4 raconte toute l'histoire de ce bloc.

Measure what the bytes are made of

Encoding work is easy to aim at the wrong target, and MoonQwak did it twice in a row.

Pitfall I hit

A batch "bullets at 1/10 plus one less angle" was expected to save 15% of snapshot size. It saved 0.7%. Two assumptions were wrong: bullets had been sent only at spawn and impact for a long time (so they were a small share of each snapshot), and most of their speeds were already under the two-byte threshold. Neither assumption had been measured.

The response was an instrument, not another optimization: a trace, switched on by an environment variable, that re-serializes one player's snapshot object by object once per second and prints the size by object type, the bytes spent on ids, and how many ships carry each optional block. A typical line from the 600-player bench:

Mesurer de quoi sont faits les octets

Le travail d'encodage vise facilement la mauvaise cible, et MoonQwak l'a fait deux fois de suite.

Piège rencontré

Un lot « balles au dixième plus un angle de moins » devait économiser 15 % de la taille des snapshots. Il en a économisé 0,7 %. Deux hypothèses étaient fausses : les balles n'étaient plus envoyées qu'à leur apparition et à leur impact depuis longtemps (donc une petite part de chaque snapshot), et la plupart de leurs vitesses étaient déjà sous le seuil des deux octets. Aucune des deux n'avait été mesurée.

La réponse a été un instrument, pas une optimisation de plus : une trace, activée par une variable d'environnement, qui re-sérialise le snapshot d'un joueur objet par objet une fois par seconde et affiche la taille par type d'objet, les octets passés en identifiants, et combien de vaisseaux portent chaque bloc optionnel. Une ligne typique du banc à 600 joueurs :

GameServer console · QWAK_SNAP_TRACE=1
[Snap bytes] peer 0: total 1449 · self+header 31 · ids 116 · Ship 60x22=1371 · Bullet 5x9=47
   hull blocks: movement 60 · turrets 60 · rebuild 0 · state 0 · beams 0 · effects 0 · posts 0 · fire 0

That line ended a debate: 95% of the snapshot was the fixed base of each ship, every optional block was already at zero, and there was nothing left to gain from encoding. The only remaining lever was how often each ship is sent, which is the subject of 4.5.

Rule

Before optimizing an encoding, break the real payload down by what it contains.

An estimate of where the bytes go is a hypothesis. A per-type breakdown of a real packet takes an afternoon to build and usually changes the plan.

Cette ligne a clos un débat : 95 % du snapshot était la base fixe de chaque vaisseau, chaque bloc optionnel était déjà à zéro, et il n'y avait plus rien à gagner sur l'encodage. Le seul levier restant était la fréquence d'envoi de chaque vaisseau, qui est le sujet du chapitre 4.5.

Règle

Avant d'optimiser un encodage, décomposer la vraie charge utile par ce qu'elle contient.

Une estimation de l'endroit où vont les octets est une hypothèse. Une décomposition par type d'un vrai paquet prend un après-midi à écrire et change en général le plan.

Key takeaways

  • Varints make small numbers cheap; zig-zag keeps small negative numbers cheap too, at the cost of halving the range.
  • Quantize floats to the precision the game needs, with scales defined once and shared by both ends.
  • A varint format with size jumps has cliffs; keep frequent values below them by choosing scales and id ranges.
  • Flag bytes let an idle object cost almost nothing.
  • Measure the composition of real packets before choosing what to optimize.

À retenir

  • Les varints rendent les petits nombres bon marché ; le zig-zag garde aussi les petits négatifs bon marché, au prix d'une plage divisée par deux.
  • Quantifier les flottants à la précision dont le jeu a besoin, avec des échelles définies une fois et partagées par les deux bouts.
  • Un format de varint à sauts de taille a des falaises ; garder les valeurs fréquentes en dessous en choisissant échelles et plages d'identifiants.
  • Les octets de drapeaux permettent à un objet au repos de ne coûter presque rien.
  • Mesurer la composition de vrais paquets avant de choisir quoi optimiser.

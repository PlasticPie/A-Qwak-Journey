From datagram to handler

Everything a client sends passes through the same short pipeline before any game code sees it. Each stage can refuse the packet, and each refusal has a defined outcome.

Du datagramme au gestionnaire

Tout ce qu'envoie un client passe par le même court pipeline avant que le moindre code de jeu ne le voie. Chaque étape peut refuser le paquet, et chaque refus a une issue définie.

從資料包到處理常式

用戶端送來的一切，在任何遊戲程式碼看到之前，都會經過同一條短短的管線。每個階段都可以拒絕封包，而每一種拒絕都有明確的結果。

The exception boundary

This code runs on the network library's thread, not on a request thread with a framework around it. In .NET, an exception that nobody catches on a background thread terminates the whole process. Not the handler, not the connection: the process, with every player on it.

Measured

During a one-hour load test with 1,200 players, one NullReferenceException in the input handler killed a game server and the 136 players it hosted, on a fleet otherwise running at a steady 25 ticks per second. The cause was a ship that became null between a check and the next line, during a map transition. The fix was three characters. The bill was a tenth of the population.

The bug itself was ordinary; there will always be a null somewhere. What was not acceptable was the proportion between the bug and its cost. The dispatcher, the point where packets from the network enter the game's domain, now catches exceptions from every handler:

La frontière des exceptions

Ce code tourne sur le thread de la bibliothèque réseau, pas sur un thread de requête entouré d'un framework. En .NET, une exception que personne n'attrape sur un thread de fond termine tout le processus. Pas le gestionnaire, pas la connexion : le processus, avec tous les joueurs dessus.

Mesuré

Pendant un banc de charge d'une heure avec 1 200 joueurs, une seule NullReferenceException dans le gestionnaire d'entrées a tué un serveur de jeu et les 136 joueurs qu'il hébergeait, sur un parc qui tournait par ailleurs à 25 ticks par seconde. La cause : un vaisseau devenu nul entre une vérification et la ligne suivante, pendant une transition de carte. La correction faisait trois caractères. La facture : un dixième de la population.

Le bug lui-même était banal ; il y aura toujours un nul quelque part. Ce qui n'était pas acceptable, c'était la disproportion entre le bug et son coût. Le dispatcher, le point où les paquets venus du réseau entrent dans le domaine du jeu, attrape désormais les exceptions de chaque gestionnaire :

例外邊界

這段程式碼在網路函式庫的執行緒上執行，而不是在一個外面包著框架的請求執行緒上。在 .NET 中，背景執行緒上沒有人攔截的例外會終止整個程序。不是處理常式，也不是連線：而是整個程序，連同上面的每一位玩家。

實測

在一場 1,200 名玩家、為時一小時的負載測試中，輸入處理常式裡的一個 NullReferenceException 弄死了一台遊戲伺服器以及它託管的 136 名玩家，而叢集的其他部分一直穩定地以每秒 25 tick 運作。原因是一艘船在切換地圖期間，於一次檢查與下一行之間變成了 null。修正只要三個字元。代價是十分之一的玩家。

這個 bug 本身很普通；總會有某個地方出現 null。不能接受的，是 bug 與其代價之間的比例。分派器——也就是來自網路的封包進入遊戲領域的那個點——現在會攔截每個處理常式拋出的例外：

Network/Dispatcher.cs
public bool Dispatch(int peerId, IPacket packet, object source)
{
    if (!map.ContainsKey(packet.Type)) return false;

    bool allSuccess = true;
    foreach (var handler in map[packet.Type])
    {
        try
        {
            if (!handler(peerId, packet, source)) allSuccess = false;
        }
        catch (Exception e)
        {
            // A BUG TO FIX, not a handled case: log everything, keep the process alive.
            allSuccess = false;
            Console.WriteLine($"[Dispatcher] EXCEPTION in a handler of packet 0x{packet.Type:X4} " +
                              $"(peer {peerId}), packet dropped, process continues:{Environment.NewLine}{e}");
        }
    }
    return allSuccess;  // false counts toward this peer's failure limit
}

Three choices make this a boundary rather than a rug to sweep bugs under. The full stack trace is logged with the packet type and the peer, so a crash is replaced by a precise report instead of by silence. The other handlers still run, because one failing has nothing to do with its neighbours. And the call reports failure, which advances the peer's failure counter: a client whose packets keep throwing ends up disconnected, which is the right outcome whether it is malicious or simply stuck in an impossible state.

The client applies the same idea more broadly. Its whole receive callback (decryption, parsing and dispatch) sits in one try, because an exception escaping from there would end the receive loop: the game would look connected and never receive anything again.

Trois choix en font une frontière plutôt qu'un tapis sous lequel balayer les bugs. La trace complète est journalisée avec le type de paquet et le pair : un plantage est remplacé par un rapport précis plutôt que par du silence. Les autres gestionnaires s'exécutent quand même, parce que l'échec de l'un n'a rien à voir avec ses voisins. Et l'appel rend un échec, ce qui fait avancer le compteur d'échecs du pair : un client dont les paquets lèvent sans cesse finit déconnecté, ce qui est la bonne issue, qu'il soit malveillant ou simplement coincé dans un état impossible.

Le client applique la même idée plus largement. Tout son rappel de réception (déchiffrement, parsing et distribution) est dans un seul try, parce qu'une exception qui s'en échapperait terminerait la boucle de réception : le jeu aurait l'air connecté et ne recevrait plus jamais rien.

有三個選擇讓這成為一道邊界，而不是一塊把 bug 掃到底下藏起來的地毯。完整的堆疊追蹤會連同封包類型與端點一起記錄，所以當機被一份精確的報告取代，而不是被沉默取代。其他處理常式仍然會執行，因為一個失敗與它的鄰居無關。而且這次呼叫會回報失敗，讓該端點的失敗計數器往前推進：一個封包不斷拋出例外的用戶端，最後會被斷線，無論它是惡意的，還是只是卡在某個不可能的狀態，這都是正確的結果。

用戶端以更廣的範圍套用同樣的概念。它整個接收回呼（解密、解析與分派）都包在一個 try 之中，因為從那裡逃出去的例外會終結接收迴圈：遊戲看起來仍然連線中，卻再也收不到任何東西。

Rule

The exception boundary starts at the first byte from the network: handshake, decryption, parsing and dispatch all belong inside it.

Anything that reads untrusted input on a background thread must be unable to take the process down. A crash traded for a log line with a stack trace is a good trade; a crash traded for silence is not.

Règle

La frontière des exceptions commence au premier octet venu du réseau : poignée de main, déchiffrement, parsing et distribution sont tous à l'intérieur.

Tout ce qui lit une entrée non fiable sur un thread de fond doit être incapable de faire tomber le processus. Échanger un plantage contre une ligne de journal avec sa pile est un bon échange ; l'échanger contre du silence ne l'est pas.

規則

例外邊界從來自網路的第一個位元組開始：交握、解密、解析與分派，全都屬於它的範圍之內。

任何在背景執行緒上讀取不可信輸入的東西，都必須無法讓程序倒下。用一次當機換一行附堆疊追蹤的日誌是划算的交易；用一次當機換來沉默則不是。

Rate limits: protecting availability

Every check in a game server protects correctness: you cannot steal an item, sell the same goods twice, or buy your own order. None of them protects availability. A modified client could send chat messages as fast as the link allows (each one fans out to every server, then every player), or loop on market requests, each of which opens a database transaction. Nothing would be stolen, and the server would fall over anyway.

MoonQwak's answer is a single admission gate, consulted by the network layer before any handler runs. It keeps one token bucket per player and per category, in RAM. The categories describe what the packet costs behind the handler, not what it looks like:

CategoryWhat it costsBurstSustained
TransactionOpens a database transaction and takes a per-character lock (post an order, send mail, transfer items)61.5 / s
BroadcastGoes to other players, so its cost is multiplied by the audience (chat, invitations)51 / s
QueryReads and replies with a full state (open a screen, refresh a list)208 / s

A token bucket allows short bursts (opening a screen sends several packets at once, and that is legitimate) while bounding the average. A fixed window counter would either refuse the burst or let twice the limit through at the window boundary.

Les limites de débit : protéger la disponibilité

Chaque vérification d'un serveur de jeu protège la correction : on ne peut pas voler un objet, vendre deux fois la même marchandise, ni acheter son propre ordre. Aucune ne protège la disponibilité. Un client modifié pourrait envoyer des messages de chat aussi vite que le lien le permet (chacun se diffuse vers tous les serveurs, puis tous les joueurs), ou boucler sur des requêtes de marché qui ouvrent chacune une transaction en base. Rien ne serait volé, et le serveur tomberait quand même.

La réponse de MoonQwak est un portillon d'admission unique, consulté par la couche réseau avant tout gestionnaire. Il tient un seau à jetons par joueur et par catégorie, en RAM. Les catégories décrivent ce que le paquet coûte derrière le gestionnaire, pas à quoi il ressemble :

CatégorieCe qu'elle coûteRafaleSoutenu
TransactionOuvre une transaction en base et prend un verrou de personnage (poster un ordre, envoyer un colis, transférer des objets)61,5 / s
DiffusionPart vers d'autres joueurs, donc son coût est multiplié par l'audience (chat, invitations)51 / s
RequêteLit et répond par un état complet (ouvrir un écran, rafraîchir une liste)208 / s

Un seau à jetons autorise de courtes rafales (ouvrir un écran envoie plusieurs paquets d'un coup, et c'est légitime) tout en bornant la moyenne. Un compteur par fenêtre fixe refuserait la rafale, ou laisserait passer le double de la limite à la frontière entre deux fenêtres.

速率限制：保護可用性

遊戲伺服器中的每一項檢查保護的都是正確性：你不能偷物品、不能把同一批貨賣兩次、不能買自己的訂單。但沒有一項保護可用性。一個被修改過的用戶端可以用連線所能承受的最快速度送出聊天訊息（每則都會擴散到每台伺服器，再到每位玩家），或不停迴圈送出市場請求，而每個請求都會開啟一筆資料庫交易。什麼都不會被偷，伺服器照樣會倒下。

MoonQwak 的答案是單一的准入閘門，由網路層在任何處理常式執行之前查詢。它在 RAM 中為每位玩家、每個類別維護一個權杖桶。這些類別描述的是封包在處理常式背後花費了什麼，而不是它看起來像什麼：

類別它的成本突發持續
交易開啟一筆資料庫交易，並取得一個角色層級的鎖（下單、寄信、轉移物品）61.5 / 秒
廣播送給其他玩家，所以成本會乘上受眾人數（聊天、邀請）51 / 秒
查詢讀取並回覆完整狀態（開啟畫面、重新整理清單）208 / 秒

權杖桶允許短暫的突發（開啟一個畫面會一次送出好幾個封包，這是正當的），同時限制平均值。固定視窗計數器則要嘛拒絕突發，要嘛在視窗邊界放進兩倍的上限。

GameServer/Services/RateLimiter.cs
public bool Allow(int peerId, Category category)
{
    var rule = _rules[(int)category];
    // Fail-open on the unknown: a peer without a bucket gets a full one.
    var bucket = _buckets.GetOrAdd((peerId, category),
        _ => new Bucket { Tokens = rule.Capacity, LastTicks = Stopwatch.GetTimestamp() });

    lock (bucket)  // two packets from the same peer can race on two threads
    {
        var now = Stopwatch.GetTimestamp();  // monotonic, never the wall clock
        var elapsed = (now - bucket.LastTicks) / (double)Stopwatch.Frequency;
        bucket.LastTicks = now;
        bucket.Tokens = Math.Min(rule.Capacity, bucket.Tokens + elapsed * rule.PerSecond);
        if (bucket.Tokens < 1.0) return false;
        bucket.Tokens -= 1.0;
        return true;
    }
}

Four decisions keep the gate from becoming a new source of bugs:

  • An unclassified packet is free. Forgetting to classify a new packet makes it unlimited, never blocked. A limit that breaks a feature when someone forgets it would turn hardening into a source of regressions.
  • Movement inputs are never limited. They arrive at the client's tick rate by design, and only the latest one per tick is kept. Limiting them would be limiting the game itself.
  • A refused packet is not a failure. It does not advance the counter that eventually disconnects the player. Someone clicking fast is noisy, not hostile.
  • The classification describes the player's initiative. Discover (the client asking for details of objects it has not seen yet) was first classified as a query. That was wrong: its rate is decided by the world, not by the player. Arriving on a crowded map produces dozens at once, and each one dropped was an object that never appeared on screen.

Quatre décisions empêchent le portillon de devenir une nouvelle source de bugs :

  • Un paquet non classé est libre. Oublier de classer un nouveau paquet le rend illimité, jamais bloqué. Une limite qui casserait une fonctionnalité quand quelqu'un l'oublie transformerait le durcissement en source de régressions.
  • Les entrées de mouvement ne sont jamais limitées. Elles arrivent à la cadence du client par conception, et seule la dernière de chaque tick est gardée. Les limiter, ce serait limiter le jeu lui-même.
  • Un paquet refusé n'est pas un échec. Il ne fait pas avancer le compteur qui finit par déconnecter le joueur. Quelqu'un qui clique vite est bruyant, pas hostile.
  • Le classement décrit l'initiative du joueur. Discover (le client qui demande les détails d'objets qu'il n'a pas encore vus) a d'abord été classé en requête. C'était un contresens : son débit est décidé par le monde, pas par le joueur. Arriver sur une carte peuplée en produit des dizaines d'un coup, et chacun de ceux qui étaient jetés était un objet qui n'apparaissait jamais à l'écran.

有四個決定，讓閘門不會變成新的 bug 來源：

  • 未分類的封包是免費的。忘記為新封包分類，結果是它不受限制，而不是被擋下。一個有人忘記就會弄壞功能的限制，會讓強化工作變成迴歸問題的來源。
  • 移動輸入永遠不受限制。它們依設計就是以用戶端的 tick 頻率到達，而每個 tick 只保留最新的一則。限制它們，等於限制遊戲本身。
  • 被拒絕的封包不算失敗。它不會推進最終讓玩家斷線的計數器。點得很快的人是吵了點，但不是懷有敵意。
  • 分類描述的是玩家的主動行為。Discover（用戶端索取它還沒看過的物件的細節）一開始被分類為查詢。這是錯的：它的頻率由世界決定，而不是由玩家決定。抵達一張擁擠的地圖時，會一次產生幾十個，而每一個被丟棄的，都是一個永遠不會出現在畫面上的物件。

Rule

Put a limit in one place in front of every handler, and classify packets by what they cost behind the handler.

Twenty limits written in twenty handlers are nineteen future omissions. One gate covers new packets the moment they are classified, and forgetting to classify fails open.

Règle

Mettre la limite à un seul endroit devant tous les gestionnaires, et classer les paquets par ce qu'ils coûtent derrière le gestionnaire.

Vingt limites écrites dans vingt gestionnaires, ce sont dix-neuf oublis à venir. Un seul portillon couvre les nouveaux paquets dès qu'ils sont classés, et oublier de classer laisse passer au lieu de bloquer.

規則

把限制放在所有處理常式前面的同一個地方，並依封包在處理常式背後的成本來分類。

寫在二十個處理常式裡的二十個限制，就是十九個未來的遺漏。一道閘門在新封包被分類的那一刻就涵蓋了它，而忘記分類時則會放行。

Never trust the client, concretely

"The server is authoritative" is easy to say. In practice it shows up as a set of small habits in the handlers:

  • The server re-derives where the player is. The admin command that places content in the world does not carry world coordinates: the server places the object where it knows the player's ship is. A packet with coordinates would be a way to write anywhere from the network.
  • Privileges are read from the account, never from the packet. The admin flag lives in the database row of the account; nothing the client says can raise it.
  • The client validates for comfort, the server for correctness. The ship editor highlights where a part can go, using the same shared rule the server uses, but the server re-validates the whole layout when it is applied.
  • Opening a menu requires being there. The build menu opens only if the player's character stands within range of a working console, re-checked on every action. A BuildMenu packet arriving on its own is refused. Closing, on the other hand, is always accepted: a player must never be stuck in a menu.

Ne jamais faire confiance au client, concrètement

« Le serveur fait autorité », c'est facile à dire. En pratique, ça se traduit par une série de petites habitudes dans les gestionnaires :

  • Le serveur redétermine où est le joueur. La commande d'admin qui pose du contenu dans le monde ne porte pas de coordonnées : le serveur pose l'objet là où il sait que se trouve le vaisseau du joueur. Un paquet avec des coordonnées serait un moyen d'écrire n'importe où depuis le réseau.
  • Les privilèges se lisent sur le compte, jamais dans le paquet. Le drapeau d'admin vit dans la ligne du compte en base ; rien de ce que dit le client ne peut l'élever.
  • Le client valide pour le confort, le serveur pour la justesse. L'éditeur de vaisseau surligne où une pièce peut aller, avec la même règle partagée que le serveur, mais le serveur revalide toute la disposition quand elle est appliquée.
  • Ouvrir un menu demande d'être sur place. Le menu de construction ne s'ouvre que si le personnage se tient à portée d'une console en état de marche, revérifiée à chaque action. Un paquet BuildMenu qui arrive seul est refusé. Fermer, en revanche, est toujours accepté : un joueur ne doit jamais rester coincé dans un menu.

具體地說，永遠不要信任用戶端

「伺服器具有權威」說起來很容易。實務上，它表現為處理常式中的一組小習慣：

  • 由伺服器重新推導玩家的位置。在世界中放置內容的管理員指令不攜帶世界座標：伺服器把物件放在它知道玩家船艦所在的位置。一個帶著座標的封包，就是一條能從網路寫入任何地方的途徑。
  • 權限從帳號讀取，絕不從封包讀取。管理員旗標存在帳號的資料庫資料列中；用戶端說什麼都無法提升它。
  • 用戶端的驗證是為了舒適，伺服器的驗證是為了正確。船艦編輯器會用與伺服器相同的共用規則，標示出零件可以放在哪裡，但套用時伺服器會重新驗證整個配置。
  • 開啟選單需要人在現場。只有當玩家的角色站在一個運作中的主控台範圍內時，建造選單才會開啟，而且每個動作都會重新檢查。單獨到達的 BuildMenu 封包會被拒絕。反過來說，關閉選單永遠會被接受：玩家絕不能被困在選單裡。

Handlers do not touch the world directly

Handlers run on the network thread. The world, including its Box2D physics, belongs to the tick thread, and the physics engine is only safe to modify between two simulation steps. So a handler never moves a ship. It records an intention that the next tick consumes:

  • for inputs, it overwrites a "pending" field on the player's ship (the latest input wins, so no queue can grow);
  • for anything that must create or destroy physics bodies (docking, spawning an admin object), it enqueues an action that the map runs at the start of its next tick.

Chapter 3.3 explains why this separation is what allows maps to run in parallel at all.

Les gestionnaires ne touchent pas le monde directement

Les gestionnaires tournent sur le thread réseau. Le monde, y compris sa physique Box2D, appartient au thread du tick, et le moteur physique ne peut être modifié sans danger qu'entre deux pas de simulation. Un gestionnaire ne déplace donc jamais un vaisseau. Il enregistre une intention que le prochain tick consommera :

  • pour les entrées, il écrase un champ « en attente » sur le vaisseau du joueur (la dernière entrée gagne, donc aucune file ne peut grossir) ;
  • pour tout ce qui doit créer ou détruire des corps physiques (s'amarrer, poser un objet d'admin), il met en file une action que la carte exécute au début de son tick suivant.

Le chapitre 3.3 explique pourquoi cette séparation est ce qui permet aux cartes de tourner en parallèle.

處理常式不直接碰世界

處理常式在網路執行緒上執行。世界（包括它的 Box2D 物理）屬於 tick 執行緒，而物理引擎只有在兩次模擬步驟之間修改才是安全的。所以處理常式從不移動船艦。它記錄一個意圖，由下一個 tick 消化：

  • 對於輸入，它覆寫玩家船艦上的一個「待處理」欄位（最新的輸入獲勝，所以沒有任何佇列會增長）；
  • 對於任何必須建立或摧毀物理剛體的事情（停靠、產生管理員物件），它把一個動作排入佇列，由地圖在下一個 tick 開始時執行。

第 3.3 章會解釋，為什麼正是這種分離，才讓地圖能夠平行執行。

Say why a connection ended

The network layer logs a reason for every disconnection: Timeout (nobody answered: look at who ran out of CPU, not at the code), RemoteConnectionClose (the other side chose to leave, so its own log explains why), ConnectionRejected (a peer cap), or a socket error code from the operating system.

Pitfall I hit

The client had learned this lesson first: it took "twenty fake clients and half an hour" to tell a rejection, a timeout and a takeover kick apart, because all three printed the same line. The fix went into the client. The server kept printing a line without the reason, and at 750 bots it showed four hundred identical disconnections with nothing to tell them apart. A correction that does not migrate to its twin is not finished.

Dire pourquoi une connexion s'est terminée

La couche réseau journalise une raison pour chaque déconnexion : Timeout (personne n'a répondu : regarder qui a manqué de CPU, pas le code), RemoteConnectionClose (l'autre côté a choisi de partir, c'est donc son journal qui explique pourquoi), ConnectionRejected (un plafond de pairs), ou un code d'erreur socket du système.

Piège rencontré

Le client avait appris cette leçon en premier : il avait fallu « vingt faux clients et une demi-heure » pour distinguer un refus, un délai dépassé et une éjection pour reprise de session, parce que les trois écrivaient la même ligne. La correction est allée dans le client. Le serveur a continué d'écrire une ligne sans la raison, et à 750 robots il a montré quatre cents déconnexions identiques, sans rien pour les distinguer. Une correction qui ne migre pas vers son jumeau n'est pas terminée.

說明連線為什麼結束

網路層會為每一次斷線記錄原因：Timeout（沒有人回應：去看是誰的 CPU 不夠用，而不是去看程式碼）、RemoteConnectionClose（另一端選擇離開，所以它自己的日誌會解釋原因）、ConnectionRejected（連線數上限），或是作業系統的 socket 錯誤碼。

我踩過的坑

用戶端先學到了這個教訓：花了「二十個假用戶端和半個小時」才區分出拒絕、逾時與接管踢除，因為三者印出的都是同一行。修正放進了用戶端。伺服器則繼續印著沒有原因的一行，結果在 750 個機器人時，它顯示了四百次一模一樣的斷線，完全無從分辨。一個沒有移植到它的雙胞胎身上的修正，就還沒有完成。

Key takeaways

  • Every stage of the receive pipeline can refuse a packet, and each refusal has a defined, cheap outcome.
  • On a background thread, an uncaught exception ends the process; put the whole receive path inside a boundary that logs and continues.
  • Protect availability as well as correctness: one rate-limit gate, classified by cost, failing open when a packet is unclassified.
  • Handlers record intentions; only the tick changes the world.
  • Log the reason for every disconnection and every refusal.

À retenir

  • Chaque étape du pipeline de réception peut refuser un paquet, et chaque refus a une issue définie et bon marché.
  • Sur un thread de fond, une exception non attrapée termine le processus ; mettre tout le chemin de réception dans une frontière qui journalise et continue.
  • Protéger la disponibilité autant que la correction : un seul portillon de débit, classé par coût, qui laisse passer quand un paquet n'est pas classé.
  • Les gestionnaires enregistrent des intentions ; seul le tick change le monde.
  • Journaliser la raison de chaque déconnexion et de chaque refus.

重點整理

  • 接收管線的每個階段都可以拒絕封包，而每一種拒絕都有明確且便宜的結果。
  • 在背景執行緒上，未被攔截的例外會終結程序；把整條接收路徑放在一道會記錄並繼續執行的邊界之內。
  • 除了正確性，也要保護可用性：一道依成本分類的速率限制閘門，遇到未分類的封包時放行。
  • 處理常式記錄意圖；只有 tick 會改變世界。
  • 記錄每一次斷線與每一次拒絕的原因。

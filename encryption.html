What the encryption is for

Game traffic carries passwords at login, session tokens, chat, and every action of a player. Anyone on the same network as the player could read or alter it if it travelled in clear. The goals were modest and precise: confidentiality (nobody on the path reads the traffic), integrity (nobody alters a packet without it being detected), fresh keys for every connection, low CPU cost, and something that also runs inside Unity.

Beginner note

Encryption protects the traffic between the client and the server. It does not make the client trustworthy: a player controls their own machine and can send anything. That is what server authority is for (chapter 1.5). The two are complementary, and neither replaces the other.

À quoi sert le chiffrement

Le trafic du jeu transporte les mots de passe au login, les jetons de session, le chat et chaque action d'un joueur. N'importe qui sur le même réseau que le joueur pourrait le lire ou le modifier s'il voyageait en clair. Les objectifs étaient modestes et précis : la confidentialité (personne sur le chemin ne lit le trafic), l'intégrité (personne ne modifie un paquet sans que ce soit détecté), des clés neuves pour chaque connexion, un faible coût CPU, et quelque chose qui tourne aussi dans Unity.

Pour débuter

Le chiffrement protège le trafic entre le client et le serveur. Il ne rend pas le client digne de confiance : un joueur contrôle sa machine et peut envoyer n'importe quoi. C'est le rôle de l'autorité du serveur (chapitre 1.5). Les deux sont complémentaires, et aucun ne remplace l'autre.

加密是為了什麼

遊戲流量在登入時攜帶密碼，還有連線階段權杖、聊天內容，以及玩家的每一個動作。如果以明文傳送，任何與玩家位於同一網路的人都能讀取或竄改。目標既保守又明確：機密性（路徑上沒有人能讀取流量）、完整性（沒有人能竄改封包而不被察覺）、每條連線都有新的金鑰、CPU 成本低，而且也要能在 Unity 中執行。

新手須知

加密保護的是用戶端與伺服器之間的流量。它並不會讓用戶端變得可信：玩家掌控自己的機器，想送什麼都可以。這正是伺服器權威存在的目的（第 1.5 章）。兩者互補，任一方都無法取代另一方。

The handshake

As soon as the transport connection opens, each side sends its public key in clear, as the first reliable message. Then both compute the same shared secret, and never send it.

  1. The client generates a fresh X25519 key pair for this connection. The server has a long-lived key pair, created on first start and kept in a file.
  2. Each side sends its public key. Each side combines its own private key with the other's public key and obtains the same 32-byte shared secret: that is the Diffie-Hellman property.
  3. The shared secret goes through HKDF with SHA-256: an extract step that turns it into a uniform key, then two expand steps with the labels "C2S" and "S2C" that derive two independent 32-byte keys.
  4. The client encrypts with the client-to-server key and decrypts with the other one; the server does the opposite. From this point on, every packet in both directions is encrypted and authenticated.

La poignée de main

Dès que la connexion de transport s'ouvre, chaque côté envoie sa clé publique en clair, en premier message fiable. Puis les deux calculent le même secret partagé, sans jamais l'envoyer.

  1. Le client génère une paire de clés X25519 neuve pour cette connexion. Le serveur a une paire de clés longue durée, créée au premier démarrage et gardée dans un fichier.
  2. Chaque côté envoie sa clé publique. Chaque côté combine sa clé privée avec la clé publique de l'autre et obtient le même secret partagé de 32 octets : c'est la propriété de Diffie-Hellman.
  3. Le secret partagé passe dans HKDF avec SHA-256 : une étape d'extraction qui en fait une clé uniforme, puis deux étapes d'expansion avec les étiquettes "C2S" et "S2C" qui dérivent deux clés indépendantes de 32 octets.
  4. Le client chiffre avec la clé client-vers-serveur et déchiffre avec l'autre ; le serveur fait l'inverse. À partir de là, chaque paquet dans les deux sens est chiffré et authentifié.

交握

傳輸層連線一開啟，雙方就以明文送出自己的公開金鑰，作為第一則可靠訊息。接著雙方算出同一個共享秘密，而且從不傳送它。

  1. 用戶端為這條連線產生一組全新的 X25519 金鑰對。伺服器則有一組長期使用的金鑰對，在第一次啟動時建立並保存在檔案中。
  2. 雙方各自送出公開金鑰。每一方把自己的私密金鑰與對方的公開金鑰結合，得到同一個 32 位元組的共享秘密：這就是 Diffie-Hellman 的特性。
  3. 共享秘密經過以 SHA-256 為基礎的 HKDF：先以一個 extract 步驟把它轉成均勻分布的金鑰，再以標籤 "C2S" 與 "S2C" 進行兩個 expand 步驟，衍生出兩把彼此獨立的 32 位元組金鑰。
  4. 用戶端以「用戶端到伺服器」的金鑰加密，用另一把解密；伺服器則相反。從這一刻起，雙向的每個封包都經過加密與認證。
Network/Peer.cs · deriving the session keys
internal void HandshakeReceived(byte[] remotePublic, byte[] selfPrivate)
{
    var shared = X25519KeyAgreement.Agreement(selfPrivate, remotePublic);
    var prk = HKDF.Extract(HashAlgorithmName.SHA256, shared);
    var c2s = HKDF.Expand(HashAlgorithmName.SHA256, prk, 32, Encoding.ASCII.GetBytes("C2S"));
    var s2c = HKDF.Expand(HashAlgorithmName.SHA256, prk, 32, Encoding.ASCII.GetBytes("S2C"));
    _c2s = new AesGcm(c2s, tagSizeInBytes: 16);
    _s2c = new AesGcm(s2c, tagSizeInBytes: 16);
    Handshaked = true;
}

Every packet, authenticated

AES-GCM is an AEAD cipher: it encrypts the data and produces a 16-byte tag that proves the ciphertext was not modified. Decryption checks the tag first; a single altered bit makes the whole packet fail, and it is dropped.

GCM has one absolute rule: never encrypt two messages with the same key and the same nonce. MoonQwak builds the 12-byte nonce from a 64-bit counter that each peer increments atomically on every send, followed by one byte for the direction. The counter guarantees uniqueness for the life of the connection, and the direction byte keeps the two directions apart even though they already use separate keys. The counter travels in front of the ciphertext as a varint, so the receiver can rebuild the nonce.

Chaque paquet, authentifié

AES-GCM est un chiffrement AEAD : il chiffre les données et produit une étiquette (tag) de 16 octets qui prouve que le chiffré n'a pas été modifié. Le déchiffrement vérifie l'étiquette d'abord ; un seul bit modifié fait échouer tout le paquet, qui est jeté.

GCM a une règle absolue : ne jamais chiffrer deux messages avec la même clé et le même nonce. MoonQwak construit le nonce de 12 octets à partir d'un compteur de 64 bits que chaque pair incrémente de façon atomique à chaque envoi, suivi d'un octet de sens. Le compteur garantit l'unicité pendant toute la vie de la connexion, et l'octet de sens sépare les deux directions alors qu'elles utilisent déjà des clés distinctes. Le compteur voyage devant le chiffré sous forme de varint, pour que le récepteur puisse reconstruire le nonce.

每個封包都經過認證

AES-GCM 是一種 AEAD 加密法：它加密資料，並產生一個 16 位元組的標籤，證明密文沒有被修改。解密時會先檢查標籤；只要改動一個位元，整個封包就會失敗並被丟棄。

GCM 有一條絕對規則：絕不能用同一把金鑰和同一個 nonce 加密兩則訊息。MoonQwak 用一個 64 位元計數器加上一個代表方向的位元組，組成 12 位元組的 nonce；每個端點在每次傳送時以不可分割的方式遞增計數器。計數器保證在連線的整個生命週期中不會重複，方向位元組則把兩個方向區隔開來，即使它們已經使用不同的金鑰。計數器以 varint 形式放在密文前面傳送，讓接收端能重建 nonce。

Network/Peer.cs · sending one packet
public void SendRaw(byte[] plain, int length, DeliveryMethod method)
{
    var cipher = ArrayPool<byte>.Shared.Rent(length);
    var tag = ArrayPool<byte>.Shared.Rent(16);
    var counter = NextNonce();          // Interlocked.Increment: read it once
    var nonce = BuildNonce(counter, IsClient ? (byte)1 : (byte)0);

    RequireCipher(IsClient ? _c2s : _s2c)
        .Encrypt(nonce.AsSpan(0, 12), plain.AsSpan(0, length), cipher.AsSpan(0, length), tag.AsSpan(0, 16));

    lock (_sendLock)                    // two threads may send to the same peer
    {
        _writer.Reset();                // one writer per peer, reused
        _writer.Put(tag.AsSpan(0, 16));
        VarInt.WriteUVarInt((ulong)counter, _writer);
        _writer.Put(cipher.AsSpan(0, length));
        NetPeer.Send(_writer, method);  // LiteNetLib copies the bytes before returning
    }
    // rented buffers are returned here
}

Pitfall I hit

Sending reused one writer per peer to avoid allocating a new one for every packet. The same peer is legitimately sent to from two threads at once: the snapshot thread sends the tick's state while the network thread answers a request. Without the lock, the two payloads interleave in the shared writer and produce one corrupt datagram, which fails its tag check on the other side. The lock is uncontended almost all the time and costs a few nanoseconds.

Piège rencontré

L'envoi réutilise un seul writer par pair pour ne pas en allouer un neuf à chaque paquet. Or le même pair reçoit légitimement des envois de deux threads à la fois : le thread des snapshots envoie l'état du tick pendant que le thread réseau répond à une requête. Sans le verrou, les deux charges utiles s'entrelacent dans le writer partagé et produisent un datagramme corrompu, qui échoue à la vérification de son étiquette de l'autre côté. Le verrou n'est presque jamais contendu et coûte quelques nanosecondes.

我踩過的坑

傳送時，每個端點重複使用一個寫入器，以免每個封包都配置一個新的。但同一個端點確實可能同時被兩條執行緒傳送：快照執行緒在送出該 tick 的狀態，而網路執行緒在回應一個請求。沒有鎖的話，兩份酬載會在共用的寫入器中交錯，產生一個損壞的資料包，在另一端無法通過標籤檢查。這個鎖幾乎從不發生競爭，只花幾奈秒。

Unity and a hand-written AES-GCM

The server runs on .NET 10 and uses the platform's AesGcm class. The Unity client targets an older API surface (netstandard 2.1) where that class does not exist. The shared network library therefore compiles two ways: with the real implementation on the server, and with a small polyfill on the client: AES in counter mode starting from counter 2, the GHASH polynomial, a constant-time tag comparison, and HKDF on top of HMAC-SHA256.

Trade-off

Hand-written cryptography is a risk surface. The construction follows the GCM specification and interoperates with the server's standard implementation on every packet, which catches most mistakes, but interoperability is not a security review. It is the first thing to replace with a vetted library if the client platform allows it. The server logs once at startup which implementation it is running, so there is never a doubt about which side uses what.

Unity et un AES-GCM écrit à la main

Le serveur tourne sur .NET 10 et utilise la classe AesGcm de la plateforme. Le client Unity cible une surface d'API plus ancienne (netstandard 2.1) où cette classe n'existe pas. La bibliothèque réseau partagée se compile donc de deux façons : avec la vraie implémentation côté serveur, et avec un petit polyfill côté client : AES en mode compteur à partir du compteur 2, le polynôme GHASH, une comparaison d'étiquette en temps constant, et HKDF au-dessus de HMAC-SHA256.

Compromis

La cryptographie écrite à la main est une surface de risque. La construction suit la spécification de GCM et interopère avec l'implémentation standard du serveur à chaque paquet, ce qui attrape la plupart des erreurs, mais l'interopérabilité n'est pas un audit de sécurité. C'est la première chose à remplacer par une bibliothèque éprouvée si la plateforme du client le permet. Le serveur écrit une fois au démarrage quelle implémentation il utilise : on ne doute jamais de qui utilise quoi.

Unity 與手寫的 AES-GCM

伺服器在 .NET 10 上執行，使用平台的 AesGcm 類別。Unity 用戶端的目標是較舊的 API（netstandard 2.1），其中沒有這個類別。因此共用網路函式庫有兩種編譯方式：在伺服器上使用真正的實作，在用戶端上使用一個小型的替代實作（polyfill）：從計數器 2 開始的 CTR 模式 AES、GHASH 多項式、常數時間的標籤比對，以及建立在 HMAC-SHA256 之上的 HKDF。

取捨

手寫的密碼學是一個風險面。這套構造遵循 GCM 規格，而且每個封包都與伺服器的標準實作互通，這能抓到大部分的錯誤，但互通並不等於安全審查。如果用戶端平台允許，這是第一個該換成經過審核的函式庫的東西。伺服器在啟動時會記錄一次它使用的是哪一種實作，所以永遠不會搞不清楚哪一端用的是什麼。

What this does not protect

A security layer is only useful if its limits are written down. These are the current ones:

  • The server is not authenticated. The client accepts whatever public key arrives first. That defeats passive eavesdropping, but an attacker placed on the network path could run one handshake with the client and another with the server and relay between them. The standard fixes are to ship the server's public key inside the client build and refuse any other ("pinning"), or to sign the handshake with a long-term key the client knows. Both are small changes; neither is in place yet.
  • Replays are not rejected at this layer. The receiver rebuilds the nonce from the counter in the packet and does not remember which counters it has already seen. A hardened version keeps a sliding window of recent counters and drops anything older or repeated, as DTLS and QUIC do.
  • The transport's connection key is not a secret. LiteNetLib's connection key is a constant string. It filters stray connections from other programs; it authenticates nothing.
  • Game servers authenticate to the gateway differently. They sign their announcement with an RSA key (chapter 2.1), which is a separate trust relationship from the client's.

Ce que ça ne protège pas

Une couche de sécurité n'est utile que si ses limites sont écrites. Voici celles d'aujourd'hui :

  • Le serveur n'est pas authentifié. Le client accepte la première clé publique qui arrive. Ça déjoue l'écoute passive, mais un attaquant placé sur le chemin réseau pourrait faire une poignée de main avec le client, une autre avec le serveur, et relayer entre les deux. Les corrections habituelles sont d'embarquer la clé publique du serveur dans le build du client et de refuser toute autre (l'« épinglage »), ou de signer la poignée de main avec une clé longue durée que le client connaît. Les deux sont de petits changements ; aucun n'est encore en place.
  • Les rejeux ne sont pas refusés à cette couche. Le récepteur reconstruit le nonce à partir du compteur présent dans le paquet et ne se souvient pas des compteurs déjà vus. Une version durcie garde une fenêtre glissante des compteurs récents et jette tout ce qui est plus ancien ou répété, comme le font DTLS et QUIC.
  • La clé de connexion du transport n'est pas un secret. La clé de connexion de LiteNetLib est une chaîne constante. Elle filtre les connexions égarées d'autres programmes ; elle n'authentifie rien.
  • Les serveurs de jeu s'authentifient autrement auprès de la gateway. Ils signent leur annonce avec une clé RSA (chapitre 2.1), une relation de confiance distincte de celle du client.

它不保護什麼

資安層只有在它的限制被寫下來時才有用。以下是目前的限制：

  • 伺服器沒有經過認證。用戶端接受最先到達的任何公開金鑰。這能擋住被動竊聽，但一個位於網路路徑上的攻擊者，可以和用戶端進行一次交握、和伺服器進行另一次，然後在兩者之間轉送。標準的解法是把伺服器的公開金鑰內建在用戶端組建中並拒絕其他任何金鑰（「pinning」，金鑰釘選），或是用用戶端知道的長期金鑰為交握簽章。兩者都是小改動；目前都還沒做。
  • 這一層不會拒絕重送攻擊。接收端從封包中的計數器重建 nonce，但不會記得自己已經看過哪些計數器。強化版會像 DTLS 與 QUIC 一樣，維護一個最近計數器的滑動視窗，丟棄任何較舊或重複的封包。
  • 傳輸層的連線金鑰不是秘密。LiteNetLib 的連線金鑰是一個常數字串。它能過濾掉其他程式誤連的連線；它不認證任何東西。
  • 遊戲伺服器向閘道認證的方式不同。它們用 RSA 金鑰為自己的宣告簽章（第 2.1 章），這是一段與用戶端不同的信任關係。

Rule

Write down what your security layer does not protect, next to what it does.

A list of limits turns vague unease into a backlog of small, specific fixes, and it stops anyone from assuming a guarantee the code never made.

Règle

Écrire ce que votre couche de sécurité ne protège pas, à côté de ce qu'elle protège.

Une liste de limites transforme un malaise vague en une liste de petites corrections précises, et empêche quiconque de supposer une garantie que le code n'a jamais donnée.

規則

把資安層不保護的東西，寫在它保護的東西旁邊。

一份限制清單，能把模糊的不安變成一串小而具體的待修項目，也能阻止任何人假設程式碼從未提供過的保證。

Key takeaways

  • An X25519 exchange plus HKDF gives each connection fresh keys without sending any secret over the network.
  • Use one key per direction and a nonce that can never repeat under the same key; a per-peer atomic counter does that.
  • AEAD tags make tampering detectable: a modified packet fails as a whole and is dropped.
  • Reusing send buffers is worth it, but a buffer shared by threads needs a lock.
  • List the limits: server authentication and replay windows are the next steps here.

À retenir

  • Un échange X25519 suivi de HKDF donne à chaque connexion des clés neuves sans envoyer aucun secret sur le réseau.
  • Utiliser une clé par sens et un nonce qui ne peut jamais se répéter sous la même clé ; un compteur atomique par pair le fait.
  • Les étiquettes AEAD rendent toute altération détectable : un paquet modifié échoue en bloc et est jeté.
  • Réutiliser les tampons d'envoi en vaut la peine, mais un tampon partagé entre threads demande un verrou.
  • Lister les limites : l'authentification du serveur et une fenêtre anti-rejeu sont les prochaines étapes ici.

重點整理

  • X25519 交換加上 HKDF，讓每條連線都有新的金鑰，而不必在網路上傳送任何秘密。
  • 每個方向使用一把金鑰，並使用在同一把金鑰下永不重複的 nonce；每個端點一個不可分割遞增的計數器就能做到。
  • AEAD 標籤讓竄改可被偵測：被修改的封包會整個失敗並被丟棄。
  • 重複使用傳送緩衝區是值得的，但被多條執行緒共用的緩衝區需要鎖。
  • 列出限制：伺服器認證與重送視窗是這裡的下一步。

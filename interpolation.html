Between two snapshots

The server describes a remote ship 25 times per second at best, and less often when it is far away (chapter 4.5). The screen refreshes 60 times per second or more. Packets arrive with jitter, some late, some not at all. Drawing a remote object is the art of deciding where it is between the samples you have.

Beginner note

There are two families. Interpolation renders slightly in the past, between two samples you already have: perfectly smooth, but everything is shown late by the buffer's delay. Extrapolation (dead reckoning) projects the latest sample forward using its velocity: no added delay, but it guesses, and every wrong guess must be corrected. Most games mix them, and the mix is what this chapter is about.

Try the four strategies in the lab. Snapping to the latest sample stutters; pure extrapolation overshoots every turn; buffered interpolation is smooth but visibly behind the dashed circle; smoothing toward an extrapolated target sits in between.

Entre deux snapshots

Le serveur décrit un vaisseau distant 25 fois par seconde au mieux, et moins souvent quand il est loin (chapitre 4.5). L'écran se rafraîchit 60 fois par seconde ou plus. Les paquets arrivent avec de la gigue, certains en retard, d'autres pas du tout. Dessiner un objet distant, c'est l'art de décider où il est entre les échantillons dont on dispose.

Pour débuter

Il existe deux familles. L'interpolation affiche légèrement dans le passé, entre deux échantillons qu'on possède déjà : parfaitement fluide, mais tout est montré en retard du délai du tampon. L'extrapolation (estime) projette le dernier échantillon vers l'avant avec sa vitesse : aucun délai ajouté, mais elle devine, et chaque mauvaise estimation doit être corrigée. La plupart des jeux mélangent les deux, et c'est ce mélange que traite ce chapitre.

Essayez les quatre stratégies dans le labo. Coller au dernier échantillon saccade ; l'extrapolation pure dépasse chaque virage ; l'interpolation tamponnée est fluide mais visiblement en retard sur le cercle pointillé ; lisser vers une cible extrapolée se place entre les deux.

In MoonQwak

The linear mode samples in tick space, not in arrival time. Server ticks are exactly one tick apart, so the interpolation factor between two consecutive samples is just the fractional part of the read cursor, uniform whatever the network did to their arrival times. The cursor advances at the snapshot rate and is clamped so it never reaches the newest sample, which is what removes jumps between snapshots.

Dans MoonQwak

Le mode linéaire échantillonne en espace de ticks, pas en temps d'arrivée. Les ticks serveur sont espacés d'exactement un tick : le facteur d'interpolation entre deux échantillons consécutifs est simplement la partie fractionnaire du curseur de lecture, uniforme quoi que le réseau ait fait à leurs heures d'arrivée. Le curseur avance à la cadence des snapshots et reste bridé pour ne jamais atteindre l'échantillon le plus récent, ce qui supprime les sauts entre snapshots.

Extrapolate like the server simulates

Ships in MoonQwak have linear damping: when the pilot releases the thrusters, the velocity decays exponentially instead of staying constant. Extrapolating with position + velocity × time therefore overshoots whenever a ship is coasting: each new snapshot landed slightly behind the prediction, and the renderer produced a steady stream of small backward corrections. It read as a light rollback jitter during otherwise smooth flight, worse on ships than on characters precisely because only ships carry meaningful damping.

The fix is to extrapolate with the same law the server simulates. For a velocity decaying as v₀·e−λt, the displacement is v₀·(1 − e−λt)/λ:

Extrapoler comme le serveur simule

Les vaisseaux de MoonQwak ont un amortissement linéaire : quand le pilote relâche les propulseurs, la vitesse décroît exponentiellement au lieu de rester constante. Extrapoler avec position + vitesse × temps dépasse donc la vraie position chaque fois qu'un vaisseau file sur son élan : chaque nouveau snapshot tombait un peu derrière la prédiction, et le rendu produisait un flot régulier de petites corrections vers l'arrière. Cela se lisait comme une légère gigue de retour en arrière pendant un vol par ailleurs fluide, pire sur les vaisseaux que sur les personnages justement parce que seuls les vaisseaux portent un amortissement notable.

La correction consiste à extrapoler avec la même loi que celle que simule le serveur. Pour une vitesse qui décroît en v₀·e−λt, le déplacement vaut v₀·(1 − e−λt)/λ :

QwakClient/Scripts/Core/RemotePhysicsController.cs
private Vector2 ExtrapolatePosition(Vector2 pos, Vector2 vel, float t)
{
    if (_cachedShip != null)
    {
        var damping = (float)PhysicsConfig.I.HexLinearDamping;  // the SAME value Box2D uses
        if (damping > 1e-4f)
            return pos + vel * ((1f - Mathf.Exp(-damping * t)) / damping);
    }
    return pos + vel * t;                                       // bullets: no damping at all
}

Rule

Your client's model of motion should be the server's model of motion, fed with the same constants.

Every difference between the two laws becomes a correction the player sees. Sharing the configuration file between client and server makes that agreement a matter of reading the same number.

Règle

Le modèle de mouvement du client doit être celui du serveur, nourri des mêmes constantes.

Chaque différence entre les deux lois devient une correction que le joueur voit. Partager le fichier de configuration entre client et serveur réduit cet accord à la lecture d'un même nombre.

Dead-zones: do not chase noise

Even with the right law, a curving ship's new sample rarely lands exactly where the previous extrapolation said. The first version rebased the extrapolation onto every raw sample, so any tiny disagreement, even sub-centimetre quantization noise, moved the target every tick, and the spring dutifully chased each micro-correction: a small constant "bounce" in flight.

The answer is a dead-zone sized from the physics, not from float noise. The server applies an input for a whole tick, so the moment it recognizes a change can differ from the client's by up to one tick, that is up to speed / tick rate of distance. The tolerance is that, plus 20 %. Inside it, the correction is not ignored outright either: the baseline is pulled a quarter of the way toward the authoritative sample. Adopting the prediction unchanged let sub-threshold errors compound during long accelerations until they crossed the threshold all at once, a periodic hitch out of nowhere. The partial pull keeps every correction invisible while bounding the drift.

Zones mortes : ne pas courir après le bruit

Même avec la bonne loi, le nouvel échantillon d'un vaisseau qui vire tombe rarement exactement là où l'extrapolation précédente l'attendait. La première version recalait l'extrapolation sur chaque échantillon brut : le moindre désaccord, même un bruit de quantification sous le centimètre, déplaçait la cible à chaque tick, et le ressort poursuivait consciencieusement chaque micro-correction : un petit « rebond » constant en vol.

La réponse est une zone morte dimensionnée par la physique, pas par le bruit des flottants. Le serveur applique une entrée pendant un tick entier : l'instant où il reconnaît un changement peut différer de celui du client d'un tick au plus, soit jusqu'à vitesse / cadence de distance. La tolérance vaut cela, plus 20 %. À l'intérieur, la correction n'est pas ignorée pour autant : la référence est tirée d'un quart du chemin vers l'échantillon qui fait autorité. Adopter la prédiction telle quelle laissait les erreurs sous le seuil s'accumuler pendant les longues accélérations, jusqu'à franchir le seuil d'un coup : un à-coup périodique sorti de nulle part. La traction partielle garde chaque correction invisible tout en bornant la dérive.

QwakClient/Scripts/Core/RemotePhysicsController.cs · ApplyState, simplified
float elapsed = Mathf.Min(Time.time - _snapshotTime, MaxExtrapolationTime);
Vector2 predictedNow = ExtrapolatePosition(_snapshotPos, _snapshotVel, elapsed);
float epsilon = speed / WorldTps * 1.2f;  // one tick of quantization, plus margin

if (Vector2.Distance(predictedNow, position) > epsilon)
    _snapshotPos = position;              // real disagreement: rebase fully
else
    _snapshotPos = Vector2.Lerp(predictedNow, position, 0.25f);  // noise: pull a quarter

_snapshotVel = velocity;
_snapshotTime = Time.time;                // always refresh, even inside the zone

The last line matters as much as the others. The baseline time is refreshed on every sample, not only on real corrections; otherwise a ship cruising in a long straight line, every sample inside the dead-zone, would let its extrapolation age run out to the maximum and freeze in place.

La dernière ligne compte autant que les autres. L'heure de référence est rafraîchie à chaque échantillon, pas seulement lors des vraies corrections ; sinon un vaisseau qui file en ligne droite, chaque échantillon dans la zone morte, laisserait l'âge de son extrapolation atteindre le maximum et se figerait sur place.

Smoothing constants in ticks, not seconds

The smoothing time and the maximum extrapolation used to be fixed durations, 0.1 s and 0.5 s. They "felt right", and it turned out they felt right by accident: they had been tuned while the server's timer bug (chapter 3.1) silently capped the real tick rate around 21 Hz. Once the server delivered its configured rate, the fixed durations no longer matched the real interval between new states. Both are now expressed in snapshot ticks (2 and 10) and converted with the live snapshot rate, so the renderer keeps the same relative behaviour at any configured rate.

Des constantes de lissage en ticks, pas en secondes

Le temps de lissage et l'extrapolation maximale étaient des durées fixes, 0,1 s et 0,5 s. Elles « semblaient justes », et elles l'étaient par accident : elles avaient été réglées pendant que le bug de minuterie du serveur (chapitre 3.1) plafonnait en silence la cadence réelle vers 21 Hz. Une fois que le serveur a livré sa cadence configurée, les durées fixes ne correspondaient plus à l'intervalle réel entre deux nouveaux états. Les deux sont maintenant exprimées en ticks de snapshot (2 et 10) et converties avec la cadence en vigueur, pour que le rendu garde le même comportement relatif à n'importe quelle cadence configurée.

Trade-off

This looks like it contradicts the rule of chapter 4.2 ("any constant whose comment names a tick rate is in the wrong unit"). It does not: that rule is about contracts between two ends and durations that matter to a human, like a grace period. These constants describe the signal itself: "smooth over two samples" is naturally counted in samples.

Compromis

Cela semble contredire la règle du chapitre 4.2 (« toute constante dont le commentaire nomme une cadence est dans la mauvaise unité »). Ce n'est pas le cas : cette règle vise les contrats entre deux bouts et les durées qui comptent pour un humain, comme une grâce. Ces constantes décrivent le signal lui-même : « lisser sur deux échantillons » se compte naturellement en échantillons.

The order in which things are drawn

A subtle stutter, "sometimes", had nothing to do with networking. Unity runs every component's late update in an unspecified order that depends on creation order. The walking character is carried by its hull's transform; the camera follows the character; both read transforms written by the remote renderer. Depending on the session, they read the position from one frame ago.

The order is now a written contract, enforced by explicit execution-order attributes: remote physics renderer first (−100), then the local character controller that stands on it (−50), then the character renderer (−20), and the camera last (+100). Each stage reads the previous one's output of the same frame.

Rule

When several components read each other's output in the same frame, make their order explicit.

Implicit ordering works until the day objects are created in a different order, and then produces the hardest kind of bug to report: "it stutters a little, sometimes".

L'ordre dans lequel on dessine

Un léger à-coup, « parfois », n'avait rien à voir avec le réseau. Unity exécute la mise à jour tardive de chaque composant dans un ordre non spécifié, qui dépend de l'ordre de création. Le personnage à pied est porté par le transform de sa coque ; la caméra suit le personnage ; tous deux lisent des transforms écrits par le rendu distant. Selon la session, ils lisaient la position d'il y a une image.

L'ordre est maintenant un contrat écrit, imposé par des attributs explicites d'ordre d'exécution : le rendu physique distant d'abord (−100), puis le contrôleur du personnage local qui se tient dessus (−50), puis le rendu du personnage (−20), et la caméra en dernier (+100). Chaque étape lit la sortie de la précédente de la même image.

Règle

Quand plusieurs composants lisent la sortie les uns des autres dans la même image, rendre leur ordre explicite.

Un ordre implicite marche jusqu'au jour où les objets sont créés dans un autre ordre, et produit alors le genre de bug le plus dur à signaler : « ça saccade un peu, parfois ».

Bullets: forward only, except on impact

A bullet's velocity never changes in flight, so the client can simulate it almost exactly from its spawn state. Corrections are accepted only if they do not require drawing the bullet behind where it already is: for a fast, short-lived object, a continuous path matters more than resynchronizing every tick, and a backward correction reads as an ugly one-frame hitch. The one case where "behind" is right is a hit: the bullet genuinely stopped, often short of where free flight would have carried it. Fed through the forward-only rule, the impact was dropped and the bullet kept flying through the target. A hit therefore rebases unconditionally, to the impact point with zero velocity.

Les balles : en avant seulement, sauf à l'impact

La vitesse d'une balle ne change jamais en vol : le client peut la simuler presque exactement depuis son état de départ. Les corrections ne sont acceptées que si elles n'obligent pas à dessiner la balle derrière l'endroit où elle est déjà : pour un objet rapide et éphémère, une trajectoire continue compte plus que de se resynchroniser à chaque tick, et une correction vers l'arrière se lit comme un vilain à-coup d'une image. Le seul cas où « derrière » est juste est l'impact : la balle s'est vraiment arrêtée, souvent en deçà de l'endroit où le vol libre l'aurait portée. Passé par la règle « en avant seulement », l'impact était ignoré et la balle continuait de voler à travers la cible. Un impact recale donc la balle sans condition, au point d'impact avec une vitesse nulle.

Key takeaways

  • Choose the render strategy per kind of motion: extrapolate-and-smooth for ships, dead reckoning for bullets, buffered interpolation where jumps are unacceptable.
  • Extrapolate with the server's own motion law and constants, damping included.
  • Size dead-zones from one tick of simulation quantization, and pull partially inside them instead of ignoring or chasing.
  • Interpolate in tick space so arrival jitter cannot disturb the spacing.
  • Make the frame's update order explicit, and let impacts override forward-only rules.

À retenir

  • Choisir la stratégie de rendu selon le genre de mouvement : extrapoler et lisser pour les vaisseaux, estime pour les balles, interpolation tamponnée là où les sauts sont inacceptables.
  • Extrapoler avec la loi de mouvement et les constantes du serveur, amortissement compris.
  • Dimensionner les zones mortes sur un tick de quantification de la simulation, et tirer partiellement à l'intérieur au lieu d'ignorer ou de poursuivre.
  • Interpoler en espace de ticks pour que la gigue d'arrivée ne puisse pas perturber l'espacement.
  • Rendre explicite l'ordre de mise à jour de l'image, et laisser les impacts passer outre les règles « en avant seulement ».

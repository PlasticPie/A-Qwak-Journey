The launcherLe launcher啟動器

Planning, verifying and applying an update atomically, and replacing yourself while you are running.Planifier, vérifier et appliquer une mise à jour de façon atomique, et se remplacer soi-même en cours d'exécution.以不可分割的方式規劃、驗證並套用更新，以及在執行中替換自己。

A small job that must never lie

The launcher's job fits in one sentence: find out what the server publishes (chapter 8.1), compare it with what is on the disk, fetch the difference, verify it, and start the game. What makes it delicate is that every step can be interrupted: a network cut, a closed laptop, an antivirus holding a file. The design rule is that an interruption, at any point, leaves an installation that is either still the old version or repaired by the next launch. Never one that claims to be complete when it is not.

The engine that checks and applies has no user interface at all. The window only displays what the engine reports, through a callback, and it is the window's job to hop back onto its own thread. Everything interesting can therefore be tested without the UI framework, and a command-line launcher (for a Linux friend, or a test machine) would need nothing rewritten.

Un petit travail qui ne doit jamais mentir

Le travail du launcher tient en une phrase : savoir ce que publie le serveur (chapitre 8.1), le comparer à ce qu'il y a sur le disque, récupérer la différence, la vérifier, et lancer le jeu. Ce qui le rend délicat, c'est que chaque étape peut être interrompue : une coupure réseau, un portable qu'on referme, un antivirus qui tient un fichier. La règle de conception est qu'une interruption, à n'importe quel moment, laisse une installation qui est soit encore l'ancienne version, soit réparée par le lancement suivant. Jamais une installation qui prétend être complète alors qu'elle ne l'est pas.

Le moteur qui vérifie et applique n'a aucune interface. La fenêtre ne fait qu'afficher ce que le moteur rapporte, par un rappel, et c'est à la fenêtre de repasser sur son propre thread. Tout ce qui est intéressant se teste donc sans le framework d'interface, et un launcher en ligne de commande (pour un ami sous Linux, ou une machine de test) n'aurait rien à réécrire.

一份絕不能說謊的小差事

啟動器的工作一句話就能說完：找出伺服器發布了什麼（第 8.1 章）、與磁碟上的內容比較、取得差異、驗證，然後啟動遊戲。讓它變得棘手的是，每一步都可能被中斷：網路斷線、筆電被闔上、防毒軟體鎖住某個檔案。設計規則是：在任何時間點的中斷，留下的安裝要嘛仍是舊版本，要嘛會在下次啟動時被修復。絕不會是一個宣稱自己完整、實際上卻不完整的安裝。

負責檢查與套用的引擎完全沒有使用者介面。視窗只顯示引擎透過回呼回報的內容，而跳回自己的執行緒是視窗的工作。因此所有有趣的部分都能在沒有 UI 框架的情況下測試，而一個命令列版的啟動器（給用 Linux 的朋友，或一台測試機）也不需要改寫任何東西。

The order is deliberate: the launcher first, always. The launcher is what knows how to install the game, and a new game build may require a newer launcher (a wider manifest format, one more channel); the reverse never happens. Updating the game first would install a version with a tool that does not fully understand it, the kind of failure that only shows on the third deployment. Startup and the "Verify files" button also share one single path: two paths would have diverged at the first special case.

L'ordre est voulu : le launcher d'abord, toujours. Le launcher est ce qui sait installer le jeu, et une nouvelle build du jeu peut exiger un launcher plus récent (un format de manifeste élargi, un canal de plus) ; l'inverse n'arrive jamais. Mettre à jour le jeu d'abord installerait une version avec un outil qui ne la comprend pas tout à fait, le genre de panne qui ne se voit qu'au troisième déploiement. Le démarrage et le bouton « Vérifier les fichiers » partagent aussi un seul et même chemin : deux chemins auraient divergé au premier cas particulier.

這個順序是刻意的：永遠先更新啟動器。知道如何安裝遊戲的是啟動器，而新的遊戲組建可能需要較新的啟動器（更寬的清單格式、多一個頻道）；反過來則從來不會發生。先更新遊戲，等於用一個不完全理解它的工具去安裝一個版本，這種失敗只會在第三次部署時才出現。啟動時與「驗證檔案」按鈕也共用同一條路徑：兩條路徑會在第一個特殊情況時就分歧。

A plan, not an action

Comparing the installation with the manifest produces a plan: a list of files to fetch and a list of files to delete. A plan is computed, displayed ("340 MB to download"), then executed. Separating the two lets the launcher ask before using someone's bandwidth, and above all lets the decision be tested without touching a disk. The comparison runs in one of two regimes:

Fast path (every launch)

Trust the manifest the launcher itself wrote after the last successful update, and check only each file's size on disk. A 500 MB build compares in a few tens of milliseconds instead of several seconds of SHA-256. On a hard drive, that is the difference between "instant" and "has the launcher crashed?"

Deep path ("Verify files")

Ignore the local manifest and re-hash every file. The only way to detect silent corruption (a dead sector, an antivirus that truncates, a manual edit), and the only way to repair an installation whose local manifest was lost.

Size proves nothing in theory: a file can be corrupted without changing size. But it catches everything that actually happens after a successful update: a deleted file, an interrupted write, a partial replacement. And the real guarantee lives elsewhere: every downloaded file is verified against its hash before it is put in place. The fast path only decides what to download again, never what to believe.

Un plan, pas une action

Comparer l'installation au manifeste produit un plan : une liste de fichiers à récupérer et une liste de fichiers à supprimer. Un plan se calcule, s'affiche (« 340 Mo à télécharger »), puis s'exécute. Séparer les deux permet au launcher de demander avant de consommer la bande passante de quelqu'un, et surtout de tester la décision sans toucher à un disque. La comparaison suit l'un de deux régimes :

Chemin rapide (chaque lancement)

Faire confiance au manifeste que le launcher a lui-même écrit après la dernière mise à jour réussie, et ne vérifier que la taille de chaque fichier sur le disque. Une build de 500 Mo se compare en quelques dizaines de millisecondes au lieu de plusieurs secondes de SHA-256. Sur un disque dur, c'est la différence entre « instantané » et « le launcher a planté ? »

Chemin complet (« Vérifier les fichiers »)

Ignorer le manifeste local et rehacher chaque fichier. Le seul moyen de détecter une corruption silencieuse (un secteur mort, un antivirus qui tronque, une modification à la main), et le seul moyen de réparer une installation dont le manifeste local a été perdu.

La taille ne prouve rien en théorie : un fichier peut être corrompu sans changer de taille. Mais elle attrape tout ce qui arrive réellement après une mise à jour réussie : un fichier effacé, une écriture interrompue, un remplacement partiel. Et la vraie garantie vit ailleurs : chaque fichier téléchargé est vérifié par son hachage avant d'être mis en place. Le chemin rapide ne décide que quoi retélécharger, jamais quoi croire.

一個計畫，而不是一個動作

把安裝內容與清單比較，產生的是一個計畫：一份要取得的檔案清單，以及一份要刪除的檔案清單。計畫先被計算、顯示（「要下載 340 MB」），然後才執行。把兩者分開，讓啟動器能在使用某人的頻寬之前先詢問，更重要的是，讓這個決定能在不碰磁碟的情況下被測試。比較以兩種模式之一進行：

快速路徑（每次啟動）

信任啟動器在上次成功更新後自己寫下的清單，只檢查磁碟上每個檔案的大小。一個 500 MB 的組建只需幾十毫秒就能比較完，而不是好幾秒的 SHA-256。在傳統硬碟上，這就是「瞬間完成」與「啟動器當掉了嗎？」之間的差別。

深度路徑（「驗證檔案」）

忽略本機清單，重新計算每個檔案的雜湊。這是偵測無聲損壞（壞軌、會截斷檔案的防毒軟體、手動修改）的唯一方法，也是修復一個本機清單已遺失之安裝的唯一方法。

理論上，大小什麼都證明不了：一個檔案可以在大小不變的情況下損壞。但它能抓到成功更新之後實際會發生的一切：被刪除的檔案、中斷的寫入、部分的取代。而真正的保證在別處：每個下載的檔案在被放到位之前，都會先與它的雜湊值比對驗證。快速路徑只決定要重新下載什麼，從不決定要相信什麼。

Qwak.Patcher/UpdatePlan.cs · Compute, simplified
foreach (var want in remote.Files)
{
    var full = Path.Combine(root, want.Path);
    if (!File.Exists(full)) { plan.Fetch.Add(want); continue; }

    if (installedByPath != null)
    {
        // Fast path: does the manifest we applied last time already say this hash,
        // and does the size on disk match? A "no" to either re-fetches the file.
        if (installedByPath.TryGetValue(want.Path, out var had)
            && had.Sha256 == want.Sha256
            && new FileInfo(full).Length == want.Size)
            continue;
        plan.Fetch.Add(want);
        continue;
    }

    // Deep path: believe only what we just computed.
    if (BuildScanner.HashFile(full) != want.Sha256) plan.Fetch.Add(want);
}

// Orphans: ONLY what the previous manifest claimed. No manifest, no deletion.
if (installedByPath == null) return plan;
foreach (var path in installedByPath.Keys)
{
    if (wanted.ContainsKey(path)) continue;
    if (IsControlFile(path)) continue;                 // the launcher's own files
    if (!ManifestFile.IsSafeRelative(path)) continue;  // never outside the folder
    if (File.Exists(Path.Combine(root, path))) plan.Delete.Add(path);
}

Deleting is necessary, and dangerous

An installer that only adds files accumulates orphans, because Unity renames and moves files from one version to the next. The case that hurts is a renamed assembly: two DLLs exporting the same types, and a loader that picks the wrong one depending on the order the file system lists them. So deleting is part of the plan. But a File.Delete driven by a list is the most dangerous line of a launcher, and it is surrounded by four guards:

  • Only what the previous manifest claimed, never "everything in the folder that is not in the new manifest". That is the difference between cleaning your own installation and erasing what you find on the player's disk: a save, a screenshot or a config file placed next to the game would vanish at the first update.
  • No local manifest, no deletion. If the launcher does not know what belongs to it, it deletes nothing.
  • Never the launcher's control files, even when an old manifest claims them. That is the transition case: manifests published before the control files were excluded still list them.
  • Never outside the folder, even for paths from the local manifest, which the launcher wrote itself. "In principle safe" is not enough when the consequence is a delete on an absolute path, and an old version of the manifest may have been written before any validation existed.

The same reasoning places the game in a jeu/ sub-folder under the launcher rather than in the launcher's own folder. The launcher deletes files where it installs; installing the game over itself would give it the right to erase its own executable, its configuration, and whatever the player put there. A clear border between "what I manage" and "what is next to me" is worth the ten characters of a sub-folder.

Rule

Delete only what you can prove you created.

Absence from the new list is not proof. Presence in the previous list you wrote is.

Supprimer est nécessaire, et dangereux

Un installateur qui ne fait qu'ajouter accumule des orphelins, parce qu'Unity renomme et déplace des fichiers d'une version à l'autre. Le cas qui fait mal est l'assembly renommée : deux DLL qui exportent les mêmes types, et un chargeur qui prend la mauvaise selon l'ordre dans lequel le système de fichiers les liste. Supprimer fait donc partie du plan. Mais un File.Delete piloté par une liste est la ligne la plus dangereuse d'un launcher, et elle est entourée de quatre gardes :

  • Seulement ce que le manifeste précédent revendiquait, jamais « tout ce qui, dans le dossier, n'est pas dans le nouveau manifeste ». C'est la différence entre nettoyer sa propre installation et effacer ce qu'on trouve sur le disque du joueur : une sauvegarde, une capture d'écran ou un fichier de configuration posé à côté du jeu disparaîtrait à la première mise à jour.
  • Pas de manifeste local, pas de suppression. Si le launcher ne sait pas ce qui lui appartient, il ne supprime rien.
  • Jamais les fichiers de contrôle du launcher, même quand un ancien manifeste les revendique. C'est le cas de transition : les manifestes publiés avant l'exclusion des fichiers de contrôle les citent encore.
  • Jamais hors du dossier, même pour des chemins venant du manifeste local, que le launcher a écrit lui-même. « En principe sain » ne suffit pas quand la conséquence est une suppression sur un chemin absolu, et une ancienne version du manifeste a pu être écrite avant que la moindre validation existe.

Le même raisonnement place le jeu dans un sous-dossier jeu/ sous le launcher plutôt que dans le dossier du launcher lui-même. Le launcher supprime des fichiers là où il installe ; installer le jeu par-dessus lui-même lui donnerait le droit d'effacer son propre exécutable, sa configuration, et tout ce que le joueur y a posé. Une frontière nette entre « ce que je gère » et « ce qui est à côté de moi » vaut bien la dizaine de caractères d'un sous-dossier.

Règle

Ne supprimer que ce qu'on peut prouver avoir créé.

L'absence de la nouvelle liste n'est pas une preuve. La présence dans la liste précédente, écrite par soi, en est une.

刪除是必要的，也是危險的

一個只會新增檔案的安裝程式會累積孤兒檔案，因為 Unity 在版本之間會重新命名並移動檔案。真正傷人的情況是一個被改名的組件：兩個匯出相同型別的 DLL，而載入器會依檔案系統列出它們的順序挑到錯的那一個。所以刪除是計畫的一部分。但一個由清單驅動的 File.Delete，是啟動器中最危險的一行，它被四道防護圍繞著：

  • 只刪除上一份清單宣稱的東西，絕不是「資料夾中所有不在新清單裡的東西」。這就是清理自己的安裝，與抹除你在玩家磁碟上找到的東西之間的差別：放在遊戲旁邊的存檔、截圖或設定檔，會在第一次更新時消失。
  • 沒有本機清單，就不刪除。如果啟動器不知道哪些東西屬於它，它就什麼都不刪。
  • 絕不刪除啟動器的控制檔案，即使一份舊清單宣稱擁有它們。這是過渡期的情況：在控制檔案被排除之前發布的清單，仍然列著它們。
  • 絕不刪除資料夾以外的東西，即使是來自本機清單、由啟動器自己寫下的路徑。當後果是對一個絕對路徑執行刪除時，「原則上安全」是不夠的，而舊版的清單可能是在任何驗證存在之前就寫下的。

同樣的推理，讓遊戲被放在啟動器底下的 jeu/ 子資料夾中，而不是啟動器自己的資料夾裡。啟動器會在它安裝的地方刪除檔案；把遊戲安裝在它自己身上，等於給了它抹除自己的執行檔、自己的設定，以及玩家放在那裡的任何東西的權利。在「我管理的東西」與「我旁邊的東西」之間劃一條清楚的界線，值得一個子資料夾的那幾個字元。

規則

只刪除你能證明是你建立的東西。

不在新清單中並不是證明。存在於你寫下的上一份清單中才是。

Applying: the order is the safety

Applying a plan is four steps, and their order is what makes every interruption harmless:

  1. 1

    Fetch in parallel, bounded

    Four downloads at a time by default, configurable. Beyond that, a home connection does not go faster: the same bandwidth is split over more connections. Below it, round-trip latency dominates the thousands of small files of a Unity build. The bound is a semaphore around the requests, not a parallel loop: the work is waiting on the network, and a degree of parallelism chosen by the thread pool would bear no relation to what a home line can take.

  2. 2

    Each file: temporary name, hash, rename

    The body is streamed into a temporary file beside the target, hashed, and renamed over the target only if the hash matches. A rename on the same volume is atomic, so there is never a moment when the final file exists half-written. An abandoned temporary file fools no one, and the next pass overwrites it.

  3. 3

    Delete the orphans, after

    After all downloads, never before. If the update fails on the way, an installation with extra files is better than one with missing files: the first still runs (it is the old version), the second does not start.

  4. 4

    Write the installed manifest, last

    The local manifest is the promise "this is what is installed". Written before the end, any interruption would turn it into a permanent lie: the next launch's fast path would believe the installation complete and download nothing, leaving a half-updated game with no way out except "Verify files". Written last, an interruption simply leaves the previous manifest, and the next plan asks again for what is missing.

Appliquer : l'ordre est la sécurité

Appliquer un plan, c'est quatre étapes, et leur ordre est ce qui rend toute interruption inoffensive :

  1. 1

    Récupérer en parallèle, avec une borne

    Quatre téléchargements à la fois par défaut, réglable. Au-delà, une connexion domestique ne va pas plus vite : la même bande passante se répartit sur plus de connexions. En dessous, la latence d'aller-retour domine sur les milliers de petits fichiers d'une build Unity. La borne est un sémaphore autour des requêtes, pas une boucle parallèle : le travail consiste à attendre le réseau, et un degré de parallélisme choisi par le pool de threads n'aurait aucun rapport avec ce qu'une ligne domestique supporte.

  2. 2

    Chaque fichier : nom temporaire, hachage, renommage

    Le contenu est écrit en flux dans un fichier temporaire à côté de la cible, haché, et renommé sur la cible seulement si le hachage correspond. Un renommage sur le même volume est atomique : il n'existe jamais de moment où le fichier final est à moitié écrit. Un fichier temporaire abandonné ne trompe personne, et le passage suivant l'écrase.

  3. 3

    Supprimer les orphelins, après

    Après tous les téléchargements, jamais avant. Si la mise à jour échoue en route, une installation avec des fichiers en trop vaut mieux qu'une installation avec des fichiers en moins : la première marche encore (c'est l'ancienne version), la seconde ne démarre pas.

  4. 4

    Écrire le manifeste installé, en dernier

    Le manifeste local est la promesse « voici ce qui est installé ». Écrit avant la fin, toute interruption en ferait un mensonge permanent : le chemin rapide du lancement suivant croirait l'installation complète et ne téléchargerait rien, laissant un jeu à moitié à jour sans autre issue que « Vérifier les fichiers ». Écrit en dernier, une interruption laisse simplement le manifeste précédent, et le plan suivant redemande ce qui manque.

套用：順序就是安全

套用一個計畫有四個步驟，而它們的順序讓每一次中斷都無害：

  1. 1

    平行取得，有上限

    預設同時四個下載，可以設定。超過這個數量，家用網路也不會變快：同樣的頻寬只是被分給更多連線。低於這個數量，往返延遲會主宰 Unity 組建中的數千個小檔案。上限是包住請求的號誌，而不是平行迴圈：工作是在等網路，而由執行緒集區選擇的平行度，與家用線路能承受的程度毫無關係。

  2. 2

    每個檔案：暫存名稱、雜湊、改名

    內容以串流方式寫入目標旁邊的暫存檔，計算雜湊，只有在雜湊相符時才改名蓋過目標。在同一個磁碟區上改名是不可分割的，所以永遠不會有某一刻最終檔案是寫到一半的。被遺棄的暫存檔騙不了任何人，而下一輪會覆寫它。

  3. 3

    之後才刪除孤兒

    在所有下載之後，絕不在之前。如果更新在途中失敗，一個多了檔案的安裝，好過一個少了檔案的安裝：前者仍然能執行（它就是舊版本），後者根本無法啟動。

  4. 4

    最後寫入已安裝的清單

    本機清單是「這就是已安裝的內容」的承諾。如果在結束之前寫入，任何中斷都會讓它變成一個永久的謊言：下次啟動的快速路徑會相信安裝是完整的，什麼都不下載，留下一個更新到一半的遊戲，除了「驗證檔案」之外別無出路。最後才寫入的話，中斷只會留下上一份清單，而下一個計畫會再次要求缺少的部分。

var temp = target + ".qwaktmp";

using (var response = await http.GetAsync(url,
           HttpCompletionOption.ResponseHeadersRead, ct))
{
    response.EnsureSuccessStatusCode();
    await using var source = await response.Content.ReadAsStreamAsync(ct);
    await using var destination = new FileStream(temp, FileMode.Create,
        FileAccess.Write, FileShare.None, bufferSize: 1 << 16, useAsync: true);
    await source.CopyToAsync(destination, ct);   // streamed, never all in memory
}

if (BuildScanner.HashFile(temp) != file.Sha256)
{
    File.Delete(temp);
    throw new InvalidDataException($"{file.Path} arrived damaged.");
}

File.Move(temp, target, overwrite: true);               // atomic on the same volume

The guarantee here is local and depends on nothing else: a file appears under its real name only if its content has the right hash. Before this, a truncated download under the right name would have been caught only because the installed manifest had not been written yet. Saved by accident, by the order of another file: exactly the kind of safety you do not want to rely on. If the rename fails because the file is locked, the error says so in the words of the likely cause: "is the game still open?"

Before anything is downloaded, the manifest itself is checked three times: its hash against the one the pointer announced, its channel against the one requested, and every path against the installation folder, a single bad path rejecting the whole manifest (chapter 8.1). Ignoring only the faulty line would apply a partial update described by a file that has just been proven wrong.

La garantie est ici locale et ne dépend de rien d'autre : un fichier n'apparaît sous son vrai nom que si son contenu a le bon hachage. Avant cela, un téléchargement tronqué sous le bon nom n'aurait été rattrapé que parce que le manifeste installé n'était pas encore écrit. Sauvé par accident, par l'ordre d'un autre fichier : exactement le genre de sécurité sur laquelle on ne veut pas compter. Si le renommage échoue parce que le fichier est verrouillé, l'erreur le dit avec les mots de la cause probable : « le jeu est-il encore ouvert ? »

Avant le moindre téléchargement, le manifeste lui-même est vérifié trois fois : son hachage contre celui qu'annonçait le pointeur, son canal contre celui demandé, et chaque chemin contre le dossier d'installation, un seul mauvais chemin faisant rejeter tout le manifeste (chapitre 8.1). N'ignorer que la ligne fautive appliquerait une mise à jour partielle décrite par un fichier dont on vient de prouver qu'il est faux.

這裡的保證是局部的，不依賴任何其他東西：一個檔案只有在內容具有正確的雜湊值時，才會以它真正的名稱出現。在這之前，一個名稱正確卻被截斷的下載，之所以會被抓到，只是因為已安裝的清單還沒被寫入。碰巧得救，靠的是另一個檔案的順序：這正是你不想依賴的那一種安全。如果改名因為檔案被鎖住而失敗，錯誤訊息會用最可能原因的話來說：「遊戲還開著嗎？」

在下載任何東西之前，清單本身會被檢查三次：它的雜湊與指標宣告的是否相符、它的頻道與所請求的是否相符，以及每一條路徑是否位於安裝資料夾內，只要有一條壞路徑就拒絕整份清單（第 8.1 章）。只忽略有問題的那一行，等於套用一份由一個剛被證明有錯的檔案所描述的部分更新。

Replacing yourself while running

Windows locks the image of a running executable, and its DLLs with it. A launcher therefore cannot write over its own files: anything that tries fails with "access denied" at the worst moment, once the new version is already downloaded. The solution is a small dance in which the same program plays two roles from two different folders:

Se remplacer en cours d'exécution

Windows verrouille l'image d'un exécutable en cours d'exécution, et ses DLL avec. Un launcher ne peut donc pas écrire par-dessus ses propres fichiers : tout ce qui essaie échoue avec « accès refusé » au pire moment, une fois la nouvelle version déjà téléchargée. La solution est une petite danse dans laquelle le même programme joue deux rôles depuis deux dossiers différents :

在執行中替換自己

Windows 會鎖住執行中執行檔的映像，連同它的 DLL。因此啟動器無法覆寫自己的檔案：任何嘗試都會在最糟的時刻失敗並顯示「存取被拒」，也就是在新版本已經下載完之後。解決方法是一支小小的舞步，同一個程式從兩個不同的資料夾扮演兩個角色：

Until step 4, the installed launcher is intact. A failed download, a power cut, an antivirus that blocks: what remains is a half-filled staging folder, erased at the next start, and a launcher that still works. The only risky instant is the copy itself, a handful of milliseconds on files that are already local.

The staging folder is always complete, even when the update changes a single DLL, and that is not waste. The copier is the staged executable. With only the changed files in staging, an update that did not touch the executable (the most common case) would leave no one to perform the copy. The rule "which files are missing" and the rule "who performs the hand-over" would have to stay compatible forever, a coupling that no test would ever see break. The launcher weighs a few tens of megabytes and changes a few times a year; paying for the whole of it on those occasions goes unnoticed.

Trade-off

A separate updater.exe is the classic alternative. It would have to be maintained, published and verified too, and it raises the question nobody likes: who updates the updater? One binary that copies itself from elsewhere has none of these problems: the program doing the copy is always the version that was just downloaded and verified. Windows also lets you rename a running executable, and many updaters use that trick instead; the dance used here keeps every installed file untouched until the new version is complete.

One detail makes the two roles clean: the role is decided in the application's startup code, before any window exists. With the window declared as the startup page, the launcher's screen would flash for a fraction of a second before the program decided it was a copier.

Jusqu'à l'étape 4, le launcher installé est intact. Un téléchargement raté, une coupure de courant, un antivirus qui bloque : il reste un dossier de transit à moitié rempli, effacé au démarrage suivant, et un launcher qui fonctionne toujours. Le seul instant risqué est la copie elle-même, une poignée de millisecondes sur des fichiers déjà locaux.

Le dossier de transit est toujours complet, même quand la mise à jour ne change qu'une DLL, et ce n'est pas du gaspillage. Le copieur est l'exécutable en transit. Avec seulement les fichiers changés en transit, une mise à jour qui ne touche pas l'exécutable (le cas le plus courant) ne laisserait personne pour faire la copie. La règle « quels fichiers manquent » et la règle « qui fait la relève » devraient rester compatibles pour toujours, un couplage qu'aucun test ne verrait jamais casser. Le launcher pèse quelques dizaines de mégaoctets et change quelques fois par an ; payer l'intégralité à ces occasions passe inaperçu.

Compromis

Un updater.exe séparé est l'alternative classique. Il faudrait le maintenir, le publier et le vérifier lui aussi, et il pose la question que personne n'aime : qui met à jour l'updater ? Un seul binaire qui se copie lui-même depuis ailleurs n'a aucun de ces problèmes : le programme qui fait la copie est toujours la version qu'on vient de télécharger et de vérifier. Windows permet aussi de renommer un exécutable en cours d'exécution, et beaucoup d'updaters utilisent plutôt cette astuce ; la danse choisie ici garde chaque fichier installé intact jusqu'à ce que la nouvelle version soit complète.

Un détail rend les deux rôles propres : le rôle se décide dans le code de démarrage de l'application, avant qu'aucune fenêtre n'existe. Avec la fenêtre déclarée comme page de démarrage, l'écran du launcher clignoterait une fraction de seconde avant que le programme ne décide qu'il est un copieur.

在第 4 步之前，已安裝的啟動器都是完好的。下載失敗、停電、防毒軟體阻擋：留下的只是一個填到一半的暫存資料夾，會在下次啟動時被清除，以及一個仍然能運作的啟動器。唯一有風險的瞬間是複製本身，對已經在本機的檔案而言只有幾毫秒。

暫存資料夾永遠是完整的，即使更新只改了一個 DLL，而這並不是浪費。複製者就是暫存區中的那個執行檔。如果暫存區中只有改變的檔案，一次沒有動到執行檔的更新（最常見的情況）就會沒有人來執行複製。「缺少哪些檔案」的規則與「由誰執行交接」的規則就必須永遠保持相容，這種耦合，沒有任何測試會看到它壞掉。啟動器只有幾十 MB，一年改變幾次；在那幾次為它的全部付出代價，根本不會被注意到。

取捨

一個獨立的 updater.exe 是經典的替代方案。它同樣需要被維護、發布與驗證，而且它會引出一個沒有人喜歡的問題：誰來更新更新程式？一個從別處複製自己的單一執行檔，完全沒有這些問題：負責複製的程式，永遠是剛下載並驗證過的那個版本。Windows 也允許為執行中的執行檔改名，很多更新程式改用這個技巧；這裡使用的舞步，則讓每個已安裝的檔案在新版本完整之前都保持不動。

有一個細節讓兩個角色乾淨地分開：角色是在應用程式的啟動程式碼中、在任何視窗存在之前就決定好的。如果把視窗宣告為啟動頁面，啟動器的畫面會在程式決定自己是複製者之前閃現零點幾秒。

Qwak.Launcher/App.xaml.cs · OnStartup, simplified
protected override void OnStartup(StartupEventArgs e)
{
    base.OnStartup(e);

    // Copier role: running from launcher-neuf/, never shows a window.
    if (e.Args.Length >= 3 && e.Args[0] == SelfUpdate.ApplyFlag
        && int.TryParse(e.Args[2], out var pid))
    {
        // Wait for the old pid, copy every file, relaunch the target.
        var failure = SelfUpdate.ApplyFromStaging(e.Args[1], pid);
        if (failure != null) ShowWarning(failure);    // speak only when it failed
        Shutdown();
        return;
    }

    // Normal role. Clean first: a successful update and an abandoned one look alike.
    SelfUpdate.CleanStaging();
    new MainWindow(justUpdated: e.Args.Contains(SelfUpdate.RelaunchedFlag)).Show();
}

The infinite update loop

Pitfall I hit

The launcher folder that was published still contained a .qwak-installed.json, so the launcher channel's manifest listed that file, with the hash of its content at publication time: an older manifest. Every update downloaded it, then, as its very last gesture, overwrote it with the new manifest. The file on disk could therefore never match what the manifest announced. The relaunched launcher saw it "different", staged the update again, handed over, relaunched, and started over. Forever, without ever converging, because the divergence was structural, not accidental. From the player's side: a launcher closing and reopening endlessly, eating bandwidth, without a window open long enough to click anything, or even to read a message.

La boucle de mise à jour infinie

Piège rencontré

Le dossier du launcher qui avait été publié contenait encore un .qwak-installed.json : le manifeste du canal launcher listait donc ce fichier, avec le hachage de son contenu au moment de la publication, un manifeste plus ancien. Chaque mise à jour le téléchargeait, puis, en tout dernier geste, l'écrasait avec le nouveau manifeste. Le fichier sur le disque ne pouvait donc jamais correspondre à ce qu'annonçait le manifeste. Le launcher relancé le voyait « différent », remettait la mise à jour en transit, passait la main, se relançait, et recommençait. Indéfiniment, sans jamais converger, parce que la divergence était structurelle et pas accidentelle. Du côté du joueur : un launcher qui se ferme et se rouvre sans fin, en mangeant de la bande passante, sans qu'aucune fenêtre ne reste ouverte assez longtemps pour cliquer quoi que ce soit, ni même lire un message.

無窮的更新迴圈

我踩過的坑

被發布的啟動器資料夾中仍然有一個 .qwak-installed.json，所以啟動器頻道的清單列出了這個檔案，附上它在發布當時內容的雜湊值：一份較舊的清單。每次更新都會下載它，然後在最後一個動作中，以新的清單覆寫它。因此磁碟上的檔案永遠不可能符合清單所宣告的內容。重新啟動的啟動器看到它「不同」，就再次暫存更新、交接、重新啟動、從頭開始。永無止境，從不收斂，因為這個分歧是結構性的，而不是偶然的。從玩家那一端看：一個不斷關閉又重新開啟的啟動器，吃掉頻寬，視窗開著的時間短到無法點擊任何東西，連讀一則訊息都不夠。

The fix came in three parts. The cause: the launcher's control files are never published (chapter 8.1). The transition: they are never deleted either, even when an older manifest still claims them. And a guard that assumes nothing about the cause: the copier relaunches with --relaunched-after-update, and a launcher carrying that flag refuses to hand over a second time in the same session. A real update always passes, since it needs exactly one round trip. A divergence that does not converge now stops and says so, naming one file that does not converge, because the person who publishes is the one who can fix it and needs the name. Then it moves on to the game, which has no reason to be affected.

Rule

Fix the cause, then bound the shape of the failure.

The cause was one file. The shape, an automatic action that repeats itself with no window for a human, deserves its own guard, because the next cause will be different and the shape the same.

La correction s'est faite en trois temps. La cause : les fichiers de contrôle du launcher ne sont jamais publiés (chapitre 8.1). La transition : ils ne sont jamais supprimés non plus, même quand un ancien manifeste les revendique encore. Et une garde qui ne suppose rien de la cause : le copieur relance avec --relaunched-after-update, et un launcher qui porte ce drapeau refuse de passer la main une seconde fois dans la même session. Une vraie mise à jour passe toujours, puisqu'elle n'a besoin que d'un aller-retour. Une divergence qui ne converge pas s'arrête maintenant et le dit, en nommant un fichier qui ne converge pas, parce que c'est celui qui publie qui peut corriger et qu'il lui faut le nom. Puis elle passe au jeu, qui n'a aucune raison d'être affecté.

Règle

Corriger la cause, puis borner la forme de la panne.

La cause était un fichier. La forme, une action automatique qui se répète sans laisser de fenêtre à un humain, mérite sa propre garde, parce que la prochaine cause sera différente et la forme identique.

修正分成三部分。原因：啟動器的控制檔案永遠不被發布（第 8.1 章）。過渡期：即使一份較舊的清單仍然宣稱擁有它們，它們也永遠不會被刪除。以及一道對原因不做任何假設的防護：複製者以 --relaunched-after-update 重新啟動，而帶著這個旗標的啟動器，在同一個工作階段中會拒絕第二次交接。真正的更新永遠能通過，因為它只需要剛好一次往返。一個不收斂的分歧現在會停下來並說出來，指名一個不收斂的檔案，因為負責發布的人才能修正它，而他需要那個名稱。然後它繼續處理遊戲，遊戲沒有理由受到影響。

規則

修正原因，然後為失敗的形狀設下界限。

原因是一個檔案。形狀——一個會自我重複、不給人類任何反應空檔的自動動作——值得一道自己的防護，因為下一個原因會不同，而形狀會相同。

Failing gently

Most of a launcher's code runs when something is wrong, and the question is always the same: what can the player still do?

  • The self-update can never prevent playing. It is the one place that swallows every error: the launcher channel may not exist yet (nothing ever published there, a 404), be mid-publication, or serve a damaged manifest. None of these makes the game unplayable. The message goes to the status line, where the game check replaces it a second later: visible to someone watching, blocking for no one.
  • Playing stays possible after a failed update, if the game is installed. The update server being down does not make the local build useless. Compatibility is not the launcher's decision: the gateway compares the protocol version the client announces with its own and has the last word (chapter 1.6). The protocol number in the manifest is only there so the launcher can explain a refusal ("the online build speaks protocol 3, yours 2") instead of showing "connection refused".
  • An unreachable server gets its own message: server off, NAT rule missing, wrong address in launcher.json. A generic "network error" sends players to check their own connection, which works fine.
  • An unexpected exception is shown, and the window stays open, with its "Verify files" button, which is precisely what repairs most states the launcher can end up in. Without that last net, the window would close without a word, and the player would have nothing to report.
  • A configuration problem is shown first, and stops there. Otherwise the cause would flash for a second before being replaced by its symptom, "server unreachable".

Pitfall I hit

launcher.json is edited by hand, in a text editor. An earlier version rewrote the file with default values when it could not parse it. One extra comma, and the carefully typed server address was silently replaced. The symptom was "I edit the file and it changes back", which looks like anything but a syntax error. Now the file is only written when it does not exist; an unreadable file is kept as is (the only state from which its author can fix the mistake) and the parser's message, which carries the line and position, is displayed. The reader also accepts trailing commas and comments: the format is strict between machines for good reasons, and this one has a human at the other end.

Échouer en douceur

La plus grande partie du code d'un launcher s'exécute quand quelque chose ne va pas, et la question est toujours la même : que peut encore faire le joueur ?

  • L'auto-mise à jour ne peut jamais empêcher de jouer. C'est le seul endroit qui avale toutes les erreurs : le canal launcher peut ne pas exister encore (rien n'y a jamais été publié, un 404), être en cours de publication, ou servir un manifeste abîmé. Aucune de ces situations ne rend le jeu injouable. Le message passe dans la ligne de statut, où la vérification du jeu le remplace une seconde plus tard : visible pour qui regarde, bloquant pour personne.
  • Jouer reste possible après une mise à jour ratée, si le jeu est installé. Un serveur de mise à jour éteint ne rend pas la build locale inutilisable. La compatibilité n'est pas la décision du launcher : la gateway compare la version de protocole annoncée par le client à la sienne et a le dernier mot (chapitre 1.6). Le numéro de protocole dans le manifeste n'est là que pour que le launcher puisse expliquer un refus (« la build en ligne parle le protocole 3, la tienne le 2 ») au lieu d'afficher « connexion refusée ».
  • Un serveur injoignable a son propre message : serveur éteint, règle NAT manquante, mauvaise adresse dans launcher.json. Une « erreur réseau » générique envoie les joueurs vérifier leur propre connexion, qui marche très bien.
  • Une exception inattendue est affichée, et la fenêtre reste ouverte, avec son bouton « Vérifier les fichiers », qui est précisément ce qui répare la plupart des états dans lesquels le launcher peut tomber. Sans ce dernier filet, la fenêtre se fermerait sans un mot, et le joueur n'aurait rien à rapporter.
  • Un problème de configuration s'affiche en premier, et s'arrête là. Sinon la cause clignoterait une seconde avant d'être remplacée par son symptôme, « serveur injoignable ».

Piège rencontré

launcher.json se modifie à la main, dans un éditeur de texte. Une version précédente réécrivait le fichier avec les valeurs par défaut quand elle n'arrivait pas à le lire. Une virgule de trop, et l'adresse du serveur patiemment saisie était remplacée en silence. Le symptôme était « je modifie le fichier et il revient comme avant », ce qui ressemble à tout sauf à une erreur de syntaxe. Désormais le fichier n'est écrit que s'il n'existe pas ; un fichier illisible est conservé tel quel (le seul état depuis lequel son auteur peut corriger sa faute) et le message de l'analyseur, qui porte la ligne et la position, est affiché. La lecture accepte aussi les virgules finales et les commentaires : le format est strict entre machines pour de bonnes raisons, et celui-ci a un humain au bout.

溫和地失敗

啟動器大部分的程式碼都在出問題時執行，而問題永遠是同一個：玩家還能做什麼？

  • 自我更新永遠不能阻止遊玩。這是唯一一個吞下所有錯誤的地方：啟動器頻道可能還不存在（那裡從未發布過任何東西，404）、可能正在發布中，或提供一份損壞的清單。這些都不會讓遊戲無法遊玩。訊息會顯示在狀態列上，一秒後就被遊戲檢查的訊息取代：對正在看的人是可見的，但不會擋住任何人。
  • 更新失敗後仍然可以遊玩，只要遊戲已經安裝。更新伺服器掛掉，並不會讓本機的組建變得無用。相容性不是啟動器的決定：閘道會比較用戶端宣告的協定版本與它自己的版本，並擁有最終決定權（第 1.6 章）。清單中的協定編號，只是為了讓啟動器能解釋一次拒絕（「線上組建使用協定 3，你的是 2」），而不是顯示「連線被拒絕」。
  • 無法連上伺服器有自己的訊息：伺服器關閉、缺少 NAT 規則、launcher.json 中的位址錯誤。一個籠統的「網路錯誤」，會讓玩家去檢查他們自己完全正常的網路連線。
  • 預期之外的例外會被顯示，而且視窗保持開啟，連同它的「驗證檔案」按鈕，而這正是能修復啟動器可能陷入的大部分狀態的東西。少了這最後一張網，視窗會一聲不響地關閉，玩家什麼都無從回報。
  • 設定問題會最先顯示，並停在那裡。否則原因會閃現一秒，然後被它的症狀「無法連上伺服器」取代。

我踩過的坑

launcher.json 是在文字編輯器中手動編輯的。早期的版本在無法解析它時，會用預設值改寫這個檔案。多一個逗號，辛苦輸入的伺服器位址就被悄悄地取代了。症狀是「我編輯了檔案，它又變回去了」，看起來完全不像語法錯誤。現在這個檔案只在不存在時才會被寫入；無法讀取的檔案會原封不動地保留（這是它的作者唯一能修正錯誤的狀態），並顯示解析器那則帶有行號與位置的訊息。讀取端也接受尾隨逗號與註解：機器之間的格式有充分的理由保持嚴格，而這一個的另一端是人類。

Small decisions at the edges

DecisionWhy
launcher.json lives next to the executable, created with defaults if missingDistribution is "here is a zipped folder". A configuration in the user profile would force the other player to type the server's address on first launch, exactly what the launcher is meant to spare them.
The launcher's folder is the executable's folder, never the current directoryA Windows shortcut can start the process from anywhere. With the current directory, the launcher would create its game folder on the player's desktop and reinstall everything, without understanding why.
The installed manifest lives inside the folder it describesDeleting the folder must also delete what the launcher believed about it. A manifest that survived its installation would announce "nothing to do" in front of an empty folder.
A launcher sent by hand writes its installed manifest after a full check that finds it conformOtherwise every start would re-hash everything to conclude "nothing to do". The discovery is paid once.
One HTTP client for the whole processOne per download exhausts the system's ephemeral ports (closed sockets linger in TIME_WAIT), long before the end of a first installation of tens of thousands of files, with an incomprehensible network error.
Progress reported every 100 files while checking, and posted to the UI without waitingHopping to the UI thread for every file of a 30,000-file build would cost more than the check itself; waiting for the UI from four parallel downloads would pace them on the display.
The game starts with its own folder as working directoryUnity looks for its *_Data folder, logs and configuration there. Started from elsewhere: a black screen and a log nowhere to be found.
The executable path is checked once more just before it is startedIt was already validated with the manifest, but this is the last line before executing something: it costs nothing and depends on no check made elsewhere.
The launcher closes once the game has startedLeft open, it would hold files of the folder it manages, and suggest that an update could run while the game locks the files it would need to replace.

Petites décisions aux bords

DécisionPourquoi
launcher.json vit à côté de l'exécutable, créé avec les valeurs par défaut s'il manqueLa distribution, c'est « voici un dossier zippé ». Une configuration dans le profil utilisateur obligerait l'autre joueur à saisir l'adresse du serveur au premier lancement, exactement ce que le launcher doit lui épargner.
Le dossier du launcher est celui de l'exécutable, jamais le répertoire courantUn raccourci Windows peut démarrer le processus depuis n'importe où. Avec le répertoire courant, le launcher créerait son dossier de jeu sur le bureau du joueur et réinstallerait tout, sans comprendre pourquoi.
Le manifeste installé vit dans le dossier qu'il décritEffacer le dossier doit aussi effacer ce que le launcher croyait savoir de lui. Un manifeste qui survivrait à son installation annoncerait « rien à faire » devant un dossier vide.
Un launcher envoyé à la main écrit son manifeste installé après une vérification complète qui le trouve conformeSinon chaque démarrage rehacherait tout pour conclure « rien à faire ». La découverte ne se paie qu'une fois.
Un seul client HTTP pour tout le processusUn par téléchargement épuise les ports éphémères du système (les sockets fermées restent en TIME_WAIT), bien avant la fin d'une première installation de dizaines de milliers de fichiers, avec une erreur réseau incompréhensible.
Progression rapportée tous les 100 fichiers pendant la vérification, et postée à l'interface sans attendreRepasser sur le thread d'interface pour chaque fichier d'une build de 30 000 fichiers coûterait plus que la vérification elle-même ; attendre l'interface depuis quatre téléchargements parallèles les cadencerait sur l'affichage.
Le jeu démarre avec son propre dossier comme répertoire de travailUnity y cherche son dossier *_Data, ses journaux et sa configuration. Lancé d'ailleurs : un écran noir et un journal introuvable.
Le chemin de l'exécutable est vérifié une dernière fois juste avant son lancementIl a déjà été validé avec le manifeste, mais c'est la dernière ligne avant d'exécuter quelque chose : elle ne coûte rien et ne dépend d'aucune vérification faite ailleurs.
Le launcher se ferme une fois le jeu lancéResté ouvert, il tiendrait des fichiers du dossier qu'il gère, et laisserait croire qu'une mise à jour pourrait tourner pendant que le jeu verrouille les fichiers qu'elle devrait remplacer.

邊緣上的小決定

決定原因
launcher.json 放在執行檔旁邊，不存在時以預設值建立發行方式就是「這裡有一個壓縮過的資料夾」。如果設定放在使用者設定檔中，另一位玩家在第一次啟動時就得輸入伺服器位址，而這正是啟動器本來要替他們省掉的事。
啟動器的資料夾就是執行檔所在的資料夾，絕不是目前目錄Windows 捷徑可以從任何地方啟動程序。如果用目前目錄，啟動器會在玩家的桌面上建立遊戲資料夾並重新安裝一切，而且搞不懂為什麼。
已安裝的清單放在它所描述的資料夾內刪除資料夾時，也必須刪除啟動器對它的認知。一份在它的安裝消失後仍然存活的清單，會對著一個空資料夾宣告「沒事可做」。
手動送過去的啟動器，在一次完整檢查確認它符合之後，會寫下它的已安裝清單否則每次啟動都會重新計算所有雜湊，只為了得出「沒事可做」。這個發現只需付出一次代價。
整個程序只用一個 HTTP 用戶端每次下載一個，會耗盡系統的臨時埠（關閉的 socket 會停留在 TIME_WAIT），遠在一次數萬個檔案的首次安裝結束之前，並出現一個令人費解的網路錯誤。
檢查時每 100 個檔案回報一次進度，並以不等待的方式送到 UI對一個 30,000 個檔案的組建，每個檔案都跳到 UI 執行緒，成本會比檢查本身還高；讓四個平行下載等待 UI，會讓它們的速度被顯示拖著走。
遊戲以它自己的資料夾作為工作目錄啟動Unity 會在那裡尋找它的 *_Data 資料夾、日誌與設定。從別處啟動：黑畫面，以及一個不知道在哪裡的日誌。
執行檔路徑在啟動前會再檢查一次它已經隨著清單驗證過了，但這是執行某樣東西之前的最後一行：不花任何成本，也不依賴在別處所做的任何檢查。
遊戲啟動後啟動器就關閉如果保持開啟，它會持有它所管理之資料夾中的檔案，並暗示在遊戲鎖住它要取代的檔案時仍可以進行更新。

Key takeaways

  • Update the launcher before the game, and share one code path between startup and "Verify files".
  • Compute a plan, then apply it; trust sizes on the fast path, re-hash on demand, and verify every downloaded file before it takes its real name.
  • Delete only what the previous manifest you wrote claimed, never outside the folder, and nothing at all when you do not know what is yours.
  • Order the writes so that any interruption leaves the old version or a repairable one: files, then orphans, then the installed manifest.
  • Replace yourself from a complete staging copy that never copies onto itself, and allow at most one hand-over per launch.
  • Never let a secondary failure block the primary task, and never rewrite a file a human wrote that you could not read.

À retenir

  • Mettre à jour le launcher avant le jeu, et partager un seul chemin de code entre le démarrage et « Vérifier les fichiers ».
  • Calculer un plan, puis l'appliquer ; croire les tailles sur le chemin rapide, rehacher à la demande, et vérifier chaque fichier téléchargé avant qu'il ne prenne son vrai nom.
  • Ne supprimer que ce que revendiquait le manifeste précédent écrit par soi, jamais hors du dossier, et rien du tout quand on ne sait pas ce qui nous appartient.
  • Ordonner les écritures pour qu'une interruption laisse l'ancienne version ou une version réparable : les fichiers, puis les orphelins, puis le manifeste installé.
  • Se remplacer depuis une copie de transit complète qui ne copie jamais sur elle-même, et n'autoriser qu'une relève par lancement.
  • Ne jamais laisser une panne secondaire bloquer la tâche principale, et ne jamais réécrire un fichier écrit par un humain qu'on n'a pas su lire.

重點整理

  • 先更新啟動器，再更新遊戲，並讓啟動與「驗證檔案」共用同一條程式碼路徑。
  • 先計算計畫，再套用它；快速路徑信任檔案大小，需要時再重新計算雜湊，並在每個下載的檔案取得真正的名稱之前驗證它。
  • 只刪除你寫下的上一份清單所宣稱的東西，絕不刪除資料夾以外的東西，而在你不知道什麼屬於你時，什麼都不刪。
  • 安排寫入的順序，讓任何中斷都留下舊版本或可修復的版本：先檔案，再孤兒，最後是已安裝的清單。
  • 從一份完整、永遠不會複製到自己身上的暫存副本替換自己，並且每次啟動最多只交接一次。
  • 絕不讓次要的失敗阻擋主要的工作，也絕不改寫一個你讀不懂、由人類寫下的檔案。

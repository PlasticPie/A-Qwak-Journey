Schema, seeding and live catalogsSchéma, amorçage et catalogues à chaud

Migrations, a seed lock shared by several processes, and game data you can change without restarting anything.Les migrations, un verrou d'amorçage partagé par plusieurs processus, et des données de jeu modifiables sans rien redémarrer.

Two kinds of data

An MMO carries two very different kinds of data, and mixing them up causes most of the pain around "the database":

  • World state: characters, ships, inventories, maps, orders. It changes as people play, it must survive restarts, and it lives in the database (MySQL, through Entity Framework Core).
  • Game data: what a part weighs, how fast a bullet flies, what a recipe needs. It changes when a designer edits it, it is identical for everyone, and it lives in JSON catalogs embedded in a shared library that both the server and the Unity client load, so both sides read the same numbers.

This chapter is about getting both in place and keeping them consistent: the schema and its migrations, the initial world (the seed), and catalogs that can change while the server runs.

Deux genres de données

Un MMO transporte deux genres de données très différents, et les confondre cause l'essentiel des douleurs autour de « la base » :

  • L'état du monde : personnages, vaisseaux, inventaires, cartes, ordres. Il change quand les gens jouent, il doit survivre aux redémarrages, et il vit en base (MySQL, via Entity Framework Core).
  • Les données de jeu : ce que pèse une pièce, à quelle vitesse vole une balle, ce qu'exige une recette. Elles changent quand un concepteur les édite, sont identiques pour tout le monde, et vivent dans des catalogues JSON embarqués dans une bibliothèque partagée que chargent à la fois le serveur et le client Unity, pour que les deux côtés lisent les mêmes nombres.

Ce chapitre traite de la mise en place des deux et de leur cohérence : le schéma et ses migrations, le monde initial (l'amorçage), et des catalogues qui peuvent changer pendant que le serveur tourne.

Schema: convenient for servers, strict for agents

The schema is defined in code and evolves through EF Core migrations, about seventy of them over the project's life. The servers' database-context factory makes sure the schema exists when a context is created, which lets a fresh development machine boot on an empty database with no manual step. Existing databases are migrated explicitly with the EF tooling.

The node agent (chapter 7.3) deliberately does not use that factory, and the reason is a good principle. The agent creates a context every two seconds, forever, and must not create the schema: if the fleet tables do not exist, a migration was not applied, and an agent that fabricated them itself would hide exactly what the operator needs to see. There, the error is the desired behaviour.

Trade-off

"Create the schema if it is missing" and "evolve the schema with migrations" are two mechanisms that do not compose well: a database created the first way has no migration history for the second to build on. It is convenient during development and marked as a to-do in the code; a production setup would run migrations as an explicit deployment step and let every process fail loudly on a schema mismatch.

Le schéma : pratique pour les serveurs, strict pour les agents

Le schéma est défini dans le code et évolue par des migrations EF Core, environ soixante-dix au fil du projet. La fabrique de contextes des serveurs s'assure que le schéma existe à la création d'un contexte, ce qui permet à une machine de développement neuve de démarrer sur une base vide sans aucune étape manuelle. Les bases existantes sont migrées explicitement avec l'outillage EF.

L'agent de machine (chapitre 7.3) n'utilise délibérément pas cette fabrique, et la raison est un bon principe. L'agent crée un contexte toutes les deux secondes, pour toujours, et ne doit pas créer le schéma : si les tables du parc n'existent pas, une migration n'a pas été appliquée, et un agent qui les fabriquerait lui-même masquerait exactement ce que l'opérateur doit voir. Là, l'erreur est le comportement voulu.

Compromis

« Créer le schéma s'il manque » et « faire évoluer le schéma par migrations » sont deux mécanismes qui se composent mal : une base créée de la première façon n'a pas d'historique de migrations sur lequel la seconde puisse s'appuyer. C'est pratique en développement et marqué comme à faire dans le code ; une installation de production passerait les migrations comme une étape de déploiement explicite et laisserait chaque processus échouer bruyamment sur un schéma qui ne correspond pas.

A seed lock shared by processes that never talk

The seed creates the initial world: the map grid, resource nodes, fauna, portals, factions, the fleet's capacity row. It is idempotent per process: "does the world exist? No, then create it." But the gateway, the game server and the world simulation start together and ask that question at the same instant. All see "no", all insert world number 1, one wins, and the others fail with a duplicate key. The next run failed one step further, on a faction name.

And the exception was the kind case. The "heal" part of the seed (adding missing nodes and fauna to an existing world) has no unique key at all, so two processes running it together silently doubled every resource deposit, with no error anywhere.

These processes share nothing but the database, so the lock has to live there. MySQL's GET_LOCK is an inter-process mutex: a name, a timeout, held by a connection. The first process to arrive seeds; the others wait, then find the world in place and only heal.

Un verrou d'amorçage partagé par des processus qui ne se parlent pas

L'amorçage crée le monde initial : la grille des cartes, les nœuds de ressources, la faune, les portails, les factions, la ligne de capacité du parc. Il est idempotent par processus : « le monde existe-t-il ? Non, alors je le crée. » Mais la gateway, le serveur de jeu et la simulation du monde démarrent ensemble et posent la question au même instant. Tous voient « non », tous insèrent le monde numéro 1, un seul gagne, et les autres échouent sur une clé en double. Au lancement suivant, l'échec arrivait une étape plus loin, sur un nom de faction.

Et l'exception était le cas aimable. La partie « soigner » de l'amorçage (ajouter les nœuds et la faune manquants à un monde existant) n'a aucune clé unique : deux processus qui la couraient ensemble doublaient chaque gisement en silence, sans aucune erreur nulle part.

Ces processus ne partagent que la base : le verrou doit donc y vivre. Le GET_LOCK de MySQL est un verrou entre processus : un nom, un délai, tenu par une connexion. Le premier processus arrivé amorce ; les autres attendent, puis trouvent le monde en place et ne font que soigner.

Qwak.Data/QwakDataHelper.cs · SeedAll, simplified
db.Database.OpenConnection();  // kept open: EF opens and closes per command, and a lock
try  // taken on a closed connection no longer exists
{
    var got = db.Database.SqlQueryRaw<long?>("SELECT GET_LOCK('qwak_seed', 60) AS Value")
                         .AsEnumerable().FirstOrDefault();
    if (got != 1)
    {
        // Timeout or error: never seed WITHOUT the lock. A server that starts on a world
        // being created is better than a second seed.
        Console.WriteLine("[Seed] lock unavailable, another process is seeding");
        return;
    }
    try { SeedWorldData(db); SeedWorldCapacity(db); SeedFactions(db); }
    finally { db.Database.ExecuteSqlRaw("SELECT RELEASE_LOCK('qwak_seed')"); }
}
finally { db.Database.CloseConnection(); }

Rule

Between processes that do not talk to each other, the only lock they share is the database's.

The same reasoning appears again in the fleet: node agents claim work with SELECT … FOR UPDATE on a shared row (chapter 7.3). An in-process lock, however careful, protects nothing across processes.

One more detail from the seed: it says what it did. A seed that silently skips an existing world is indistinguishable from a seed that does not work: you start the server, nothing appears, and you look for a bug that does not exist. Every branch logs a line, including "world already exists, geography kept".

Règle

Entre des processus qui ne se parlent pas, le seul verrou qu'ils partagent est celui de la base.

Le même raisonnement revient dans le parc : les agents de machine prennent du travail avec SELECT … FOR UPDATE sur une ligne partagée (chapitre 7.3). Un verrou interne au processus, aussi soigné soit-il, ne protège rien entre processus.

Un détail de plus de l'amorçage : il dit ce qu'il a fait. Un amorçage qui saute en silence un monde existant est indiscernable d'un amorçage qui ne marche pas : on lance le serveur, rien ne s'affiche, et on cherche un bug qui n'existe pas. Chaque branche écrit une ligne, y compris « le monde existe déjà, géographie conservée ».

Live catalogs: the file is the protocol

Changing a number in a catalog used to mean recompiling the shared library, rebuilding the client libraries and restarting Unity. Now the embedded JSON is only a default, and two sources can supersede it without touching any client file or library:

Des catalogues à chaud : le fichier est le protocole

Changer un nombre dans un catalogue voulait dire recompiler la bibliothèque partagée, reconstruire les bibliothèques du client et relancer Unity. Le JSON embarqué n'est plus qu'une valeur par défaut, et deux sources peuvent la supplanter sans toucher à aucun fichier ni bibliothèque du client :

  • Debounced. Editors write a file in several events (truncate, write, rename a temporary), so the watcher waits for 400 ms of silence before reloading.
  • Swapped between ticks. The watcher only queues a name; the reload runs on the tick thread before any map moves, so no parallel loop ever reads half the old catalog and half the new one. A few milliseconds of JSON parsing: a rare stutter, of the same order as a minute sweep.
  • Refused if inconsistent. Cross-checks that can only run once every catalog is built (a weapon whose ammunition does not exist, an NPC that references a missing part) run at boot and after every reload. A catalog saved half-way does not take the server down; it is rejected and reported.
  • Sent to clients as data. A catalog is 1 to 45 KB of very repetitive JSON, 4 to 8 times smaller once compressed: less than a second of snapshots. Clients receive the catalogs that differ from the version compiled into their library when they connect (and each player's received version is remembered, so the ~20 KB are not resent on every map change), and again after every reload.

Some things cannot reload by nature: what was built from a catalog and then lives on its own (a physics body already created, an NPC already flying, a recipe in progress), and enumerations, which are code. And a catalog's keys are a contract: renaming an item family or a bullet id is not a tuning change, it is a migration, because inventories and hulls in the database carry those ids.

  • Avec anti-rebond. Les éditeurs écrivent un fichier en plusieurs événements (tronquer, écrire, renommer un temporaire) : la surveillance attend 400 ms de silence avant de recharger.
  • Échangé entre deux ticks. La surveillance ne fait que mettre un nom en file ; le rechargement tourne sur le thread du tick avant que la moindre carte ne bouge : aucune boucle parallèle ne lit jamais la moitié de l'ancien catalogue et la moitié du nouveau. Quelques millisecondes d'analyse JSON : un à-coup rare, du même ordre qu'un balayage à la minute.
  • Refusé s'il est incohérent. Les vérifications croisées qui ne peuvent tourner qu'une fois tous les catalogues construits (une arme dont la munition n'existe pas, un PNJ qui référence une pièce absente) tournent au démarrage et après chaque rechargement. Un catalogue sauvé à moitié ne fait pas tomber le serveur ; il est rejeté et signalé.
  • Envoyé aux clients comme des données. Un catalogue fait de 1 à 45 Ko de JSON très répétitif, 4 à 8 fois moins une fois compressé : moins d'une seconde de snapshots. Les clients reçoivent à la connexion les catalogues qui diffèrent de la version compilée dans leur bibliothèque (et la version reçue par chaque joueur est retenue, pour ne pas renvoyer les ~20 Ko à chaque changement de carte), puis de nouveau après chaque rechargement.

Certaines choses ne peuvent pas se recharger par nature : ce qui a été construit à partir d'un catalogue et vit ensuite seul (un corps physique déjà créé, un PNJ déjà en vol, une recette en cours), et les énumérations, qui sont du code. Et les clés d'un catalogue sont un contrat : renommer une famille d'objets ou un identifiant de balle n'est pas un réglage, c'est une migration, parce que les inventaires et les coques en base portent ces identifiants.

Game data on the hot path

A catalog that can be edited live is still read tens of thousands of times per tick, and how it is read matters. On a 400-ship bench, firing turned out to cost 60 to 80 % of the per-ship work. Each weapon queried the catalog a dozen times per tick, before even knowing whether it was on cooldown, and each read walked a generic JSON object: integer-to-string conversions (allocations), indexers, a token conversion, and for part types an enum parse from text. Worse, the bullet catalog deserialized a whole bullet entry by reflection on every call.

The hot catalogs now build a flat cache at load: one entry per part, with arrays of numbers indexed by property and the types already decoded; bullet entries deserialized once and shared. A hot read is one dictionary lookup and one array index, with no allocation. Hot reload is unaffected: the cache is immutable and replaced as a block.

Measured

On the next bench, the "fire" step went from 11 to 3.1 ms, "pilot input" from 23 to 0.5 ms, and the worst tick from 68.7 to 57.9 ms. Rereading the fire code on the way also found a real gameplay bug: the angle check (is the target within this weapon's arc?) had been lost in an unrelated change, so every weapon off cooldown fired in its own direction whatever the angle to the target. On the bench it counted twice: 400 ships firing 100 % of the time also meant hundreds of extra bullets per volley.

Rule

Separate how data is stored (editable, validated, versioned) from how it is read on the hot path (flat, typed, immutable).

Editing wants flexibility; the tick wants arrays. Building the second from the first at load time gives both, and a reload simply builds it again.

Les données de jeu sur le chemin chaud

Un catalogue qu'on peut éditer à chaud est tout de même lu des dizaines de milliers de fois par tick, et la façon de le lire compte. Sur un banc à 400 vaisseaux, le tir s'est révélé coûter 60 à 80 % du travail par vaisseau. Chaque arme interrogeait le catalogue une douzaine de fois par tick, avant même de savoir si elle était en recharge, et chaque lecture parcourait un objet JSON générique : conversions d'entiers en chaînes (des allocations), indexeurs, une conversion de jeton, et pour les types de pièces une analyse d'énumération depuis du texte. Pire, le catalogue des balles désérialisait une entrée complète par réflexion à chaque appel.

Les catalogues chauds construisent maintenant un cache plat au chargement : une entrée par pièce, avec des tableaux de nombres indexés par propriété et les types déjà décodés ; les entrées de balles désérialisées une fois et partagées. Une lecture chaude, c'est une recherche dans un dictionnaire et un accès à un tableau, sans aucune allocation. Le rechargement à chaud n'en souffre pas : le cache est immuable et remplacé d'un bloc.

Mesuré

Au banc suivant, l'étape « tir » est passée de 11 à 3,1 ms, « entrée pilote » de 23 à 0,5 ms, et le pire tick de 68,7 à 57,9 ms. Relire le code du tir en chemin a aussi trouvé un vrai bug de jeu : la vérification d'angle (la cible est-elle dans l'arc de cette arme ?) avait disparu lors d'un changement sans rapport, et toute arme hors recharge tirait dans sa propre direction, quel que soit l'angle vers la cible. Au banc, cela comptait double : 400 vaisseaux qui tirent 100 % du temps, c'étaient aussi des centaines de balles en trop à chaque salve.

Règle

Séparer la façon dont les données sont stockées (éditables, validées, versionnées) de la façon dont elles sont lues sur le chemin chaud (plates, typées, immuables).

L'édition veut de la souplesse ; le tick veut des tableaux. Construire la seconde forme à partir de la première au chargement donne les deux, et un rechargement la reconstruit simplement.

Key takeaways

  • Keep world state in the database and game data in shared catalogs that client and server both load.
  • Let tools that must never guess (agents) fail on a missing schema instead of creating it.
  • Seed under a database lock when several processes start together; healing paths without unique keys duplicate silently.
  • Reload catalogs from files, between ticks, with cross-checks that refuse inconsistent data and keep the previous version.
  • Compile editable data into flat, immutable structures for hot reads, and treat catalog keys as a contract.

À retenir

  • Garder l'état du monde en base et les données de jeu dans des catalogues partagés que chargent client et serveur.
  • Laisser les outils qui ne doivent jamais deviner (les agents) échouer sur un schéma absent au lieu de le créer.
  • Amorcer sous un verrou de base quand plusieurs processus démarrent ensemble ; les chemins de soin sans clé unique dupliquent en silence.
  • Recharger les catalogues depuis des fichiers, entre deux ticks, avec des vérifications croisées qui refusent les données incohérentes et gardent la version précédente.
  • Compiler les données éditables en structures plates et immuables pour les lectures chaudes, et traiter les clés de catalogue comme un contrat.

What an entity is here

Everything that exists on a map implements one small interface: an id, a position, a rotation, and a way to be disposed. On top of that, each kind of object picks only the capabilities it needs: a body in the physics world, a tick of its own, a description sent once to clients, or a compact state sent every tick. MoonQwak does not use a general-purpose entity-component system on the server; it uses a shallow hierarchy (a hull base class, then player ships, NPC ships and stations) split into partial files by concern (power, physics, shields, serialization), and composition for behaviour. Ce qu'est une entité ici

Tout ce qui existe sur une carte implémente une petite interface : un identifiant, une position, une rotation, et un moyen d'être libéré. Par-dessus, chaque sorte d'objet ne prend que les capacités dont elle a besoin : un corps dans le monde physique, un tick à elle, une description envoyée une fois aux clients, ou un état compact envoyé à chaque tick. MoonQwak n'utilise pas de système entité-composant généraliste côté serveur ; il utilise une hiérarchie peu profonde (une classe de base de coque, puis vaisseaux de joueurs, vaisseaux PNJ et stations) découpée en fichiers partiels par préoccupation (énergie, physique, boucliers, sérialisation), et la composition pour les comportements. 在這裡，實體是什麼

地圖上存在的一切都實作同一個小介面：一個 ID、一個位置、一個旋轉，以及一種被釋放的方式。在這之上，每一種物件只挑選自己需要的能力：物理世界中的剛體、自己的 tick、只送給用戶端一次的描述，或每個 tick 送出的精簡狀態。MoonQwak 的伺服器並沒有使用通用的實體元件系統；它用的是一個淺層的繼承階層（一個船體基底類別，接著是玩家船艦、NPC 船艦與太空站），依關注點拆成多個 partial 檔案（電力、物理、護盾、序列化），行為則以組合的方式處理。比風格更重要的是，每一種物件都明確地回答同樣幾個問題：

One door in, one door out

An object enters a map through one method and leaves through one method, and both are deferred: they enqueue the work for the tick's "apply pending" phase (chapter 3.3), because they are usually called from the network thread (a connection, a docking request, a disconnection) and must not touch the physics world directly.

Inside the map, the single registration method does everything in one branch: it adds the object to the id table, to the list of tickables if it has a tick, and to the typed lists of hulls or characters. Nothing else has to remember to register. The single removal method is the mirror, and it is also the only place that announces the departure to clients. Any reason an object leaves (death, docking, a jump, a disconnection, an NPC expiring) goes through it, so the "gone" announcement cannot be forgotten for one of them.

Une porte pour entrer, une porte pour sortir

Un objet entre dans une carte par une méthode et en sort par une méthode, et les deux sont différées : elles mettent le travail en file pour la phase « appliquer l'attente » du tick (chapitre 3.3), parce qu'elles sont en général appelées depuis le thread réseau (une connexion, une demande d'amarrage, une déconnexion) et ne doivent pas toucher directement au monde physique.

Dans la carte, l'unique méthode d'enregistrement fait tout dans une seule branche : elle ajoute l'objet à la table des identifiants, à la liste des objets qui tickent s'il a un tick, et aux listes typées des coques ou des personnages. Rien d'autre n'a à penser à s'enregistrer. L'unique méthode de retrait est son miroir, et c'est aussi le seul endroit qui annonce le départ aux clients. Toute raison qu'a un objet de partir (mort, amarrage, saut, déconnexion, PNJ qui expire) passe par elle, donc l'annonce « parti » ne peut être oubliée pour aucune.

一道入口，一道出口

物件經由一個方法進入地圖，經由一個方法離開，而且兩者都是延後的：它們把工作排入 tick 的「套用待處理項目」階段（第 3.3 章），因為它們通常是從網路執行緒呼叫的（一條連線、一個停靠請求、一次斷線），不能直接碰物理世界。

在地圖內部，唯一的註冊方法在一個分支中完成所有事：把物件加入 ID 表，如果它有 tick 就加入可 tick 清單，並加入船體或角色的型別清單。沒有任何其他東西需要記得去註冊。唯一的移除方法是它的鏡像，也是唯一向用戶端宣告離開的地方。物件離開的任何原因（死亡、停靠、跳躍、斷線、NPC 到期）都經過它，所以不可能有哪一種原因忘了宣告「已離開」。

GameServer/Maps/MapInstance.cs · simplified
public void Update(IMetaObject obj)                 // tick thread, from "apply pending"
{
    if (!Objects.TryAdd(obj.Id, obj)) return;       // first insertion only
    lock (_tickLock)
    {
        if (obj is ITickable t) _tickables.Add(t);  // ticking follows membership
        if (obj is Ship ship) _ships.Add(ship);     // stations included: Station : Ship
        else if (obj is Character c) _characters.Add(c);
    }
    // No interest-grid registration: the grid is rebuilt from Objects every tick.
}

public void Remove(ulong id)
{
    if (!Objects.TryRemove(id, out var removed)) return;
    lock (_tickLock)
    {
        if (removed is ITickable t) _tickables.Remove(t);
        if (removed is Ship ship) _ships.Remove(ship);
        else if (removed is Character c) _characters.Remove(c);
    }
    AnnounceGone(id);                               // the one place departures are announced
}

Pitfall I hit

A disconnected player's ship sometimes reappeared as a ghost. Box2D can report a movement event for a body in the very step it is destroyed, and the code that kept the interest grid up to date re-inserted any object that moved, including one that had just been removed. The first fix guarded the re-insertion. The real fix removed the whole class of bug: the grid is rebuilt from the object table every tick, so it cannot contain an object the table does not.

Rule

Derive secondary structures from the primary one instead of maintaining them in parallel.

Every extra bookkeeping path that must "stay in sync" is a place where one day it will not. An index rebuilt from what exists cannot contain what does not.

Piège rencontré

Le vaisseau d'un joueur déconnecté réapparaissait parfois en fantôme. Box2D peut signaler un mouvement pour un corps dans le pas même où il est détruit, et le code qui tenait la grille d'intérêt à jour réinsérait tout objet qui bougeait, y compris celui qu'on venait de retirer. La première correction gardait la réinsertion. La vraie correction a supprimé toute la famille de bugs : la grille est reconstruite depuis la table des objets à chaque tick, donc elle ne peut pas contenir un objet que la table ne contient pas.

Règle

Dériver les structures secondaires de la structure principale plutôt que de les tenir en parallèle.

Chaque chemin de comptabilité supplémentaire qui doit « rester synchronisé » est un endroit où, un jour, il ne le sera plus. Un index reconstruit à partir de ce qui existe ne peut pas contenir ce qui n'existe pas.

我踩過的坑

斷線玩家的船有時會以幽靈的形式再次出現。Box2D 可能在剛體被摧毀的同一個步驟中回報它的移動事件，而負責維護興趣網格的程式碼，會把任何移動過的物件重新插入，包括一個剛被移除的物件。第一個修正為重新插入加了防護。真正的修正則消除了整類 bug：網格每個 tick 都從物件表重建，所以它不可能包含物件表裡沒有的物件。

規則

從主要結構推導出次要結構，而不是平行地維護它們。

每一條必須「保持同步」的額外簿記路徑，都是一個總有一天會不同步的地方。從現存之物重建的索引，不可能包含不存在之物。

Ticking follows membership

An object that needs its own per-tick logic (a piloted ship consuming input, an NPC running its behaviours) implements a single WorldTick(dt) method. It is called because the object is on a map, and stops the instant it leaves. That replaced a static "world tick" event that every object subscribed to and was supposed to unsubscribe from by hand. That discipline leaked twice: NPC ships kept dead handlers alive after their map was unloaded, still ticking objects nobody could see.

The map ticks its objects from a copy: under the lock it copies the tickables into a reusable buffer, then ticks outside the lock, because an object's tick is allowed to do anything, including adding or removing objects. The unused tail of the buffer is cleared each tick so the map does not keep dead hulls alive through a stale reference.

The typed lists exist for a reason that only shows in a fight. The id table holds everything: hulls, characters, and every bullet, missile and debris. Almost every question the game asks is narrow ("the nearest player ship", "characters in the blast"), and answering it by scanning everything makes its cost grow with the fight itself: three hundred bullets in flight make finding four ships a hundred times more expensive, exactly when it must not be. The lists are two plain fields rather than a dictionary keyed by type, because a station is a ship and almost every caller means "any hull, stations included".

Le tick suit l'appartenance

Un objet qui a besoin de sa propre logique par tick (un vaisseau piloté qui consomme des entrées, un PNJ qui fait tourner ses comportements) implémente une seule méthode WorldTick(dt). Elle est appelée parce que l'objet est sur une carte, et s'arrête à l'instant où il la quitte. Cela a remplacé un événement statique de « tick du monde » auquel chaque objet s'abonnait et était censé se désabonner à la main. Cette discipline a fui deux fois : des vaisseaux PNJ gardaient des gestionnaires morts en vie après le déchargement de leur carte, et continuaient de faire ticker des objets que personne ne voyait.

La carte fait ticker ses objets depuis une copie : sous le verrou, elle copie les objets à ticker dans un tampon réutilisé, puis les fait ticker hors du verrou, parce que le tick d'un objet a le droit de tout faire, y compris ajouter ou retirer des objets. La queue inutilisée du tampon est effacée à chaque tick pour que la carte ne garde pas des coques mortes en vie par une référence périmée.

Les listes typées existent pour une raison qui ne se voit qu'en combat. La table des identifiants contient tout : coques, personnages, et chaque balle, missile et débris. Presque toutes les questions que pose le jeu sont étroites (« le vaisseau de joueur le plus proche », « les personnages dans l'explosion »), et y répondre en parcourant tout fait grandir leur coût avec le combat lui-même : trois cents balles en vol rendent la recherche de quatre vaisseaux cent fois plus chère, précisément quand elle ne doit pas l'être. Les listes sont deux simples champs plutôt qu'un dictionnaire indexé par type, parce qu'une station est un vaisseau et que presque tous les appelants veulent dire « n'importe quelle coque, stations comprises ».

Tick 跟著歸屬走

需要自己每個 tick 邏輯的物件（消化輸入的駕駛中船艦、執行行為的 NPC），實作單一的 WorldTick(dt) 方法。它被呼叫，是因為物件在地圖上，而在它離開的那一刻就停止。這取代了一個靜態的「世界 tick」事件：每個物件都訂閱它，而且理應手動取消訂閱。這套紀律漏了兩次：NPC 船艦在地圖卸載後仍讓死掉的處理常式活著，持續 tick 著沒人看得見的物件。

地圖從一份副本 tick 它的物件：在鎖內把可 tick 的物件複製到一個可重複使用的緩衝區，然後在鎖外 tick，因為物件的 tick 被允許做任何事，包括新增或移除物件。緩衝區未使用的尾端每個 tick 都會被清空，讓地圖不會透過一個過時的參考讓死掉的船體繼續存活。

型別清單存在的理由，只有在戰鬥中才會顯現。ID 表包含一切：船體、角色，以及每一顆子彈、飛彈與碎片。遊戲提出的問題幾乎都很窄（「最近的玩家船艦」、「爆炸範圍內的角色」），而透過掃描全部來回答，會讓成本隨著戰鬥本身增長：三百顆飛行中的子彈，會讓找四艘船的成本變成一百倍，而且偏偏在最不能這樣的時候。這些清單是兩個普通的欄位，而不是以型別為鍵的字典，因為太空站就是一艘船，而幾乎每個呼叫端指的都是「任何船體，包括太空站」。

Network ids: two lifetimes, two regimes

Every object needs an id that the client can use as a key. The naive answer, one global counter, collides with the encoding of chapter 1.3: ids are variable-length integers, two bytes up to 16,382 and four bytes after, with no three-byte size. Bullets live about a second and hundreds are fired per second, so on a global counter their ids crossed 16,383 within minutes, and every bullet id in every snapshot cost four bytes.

Measured

About 140 bytes of bullet ids per snapshot, 7 % of the whole packet, spent numbering objects the client forgets two seconds later.

So ids follow two regimes. Durable objects (hulls, characters, stations, missiles, debris) draw from a monotonic 64-bit counter and are never reused: on a server that runs for days, a 32-bit counter would eventually overflow. Bullets rent ids from a reserved band, 8,192 to 16,382, where every id fits in two bytes, and return them when they die. The durable counter jumps over the band, so a bullet and a ship can never share a number, now or in ten hours.

Identifiants réseau : deux durées de vie, deux régimes

Chaque objet a besoin d'un identifiant que le client peut utiliser comme clé. La réponse naïve, un compteur global, se heurte à l'encodage du chapitre 1.3 : les identifiants sont des entiers de taille variable, deux octets jusqu'à 16 382 et quatre au-delà, sans taille de trois octets. Les balles vivent environ une seconde et il en part des centaines par seconde : sur un compteur global, leurs identifiants dépassaient 16 383 en quelques minutes, et chaque identifiant de balle de chaque snapshot coûtait quatre octets.

Mesuré

Environ 140 octets d'identifiants de balles par snapshot, 7 % du paquet entier, dépensés à numéroter des objets que le client oublie deux secondes plus tard.

Les identifiants suivent donc deux régimes. Les objets durables (coques, personnages, stations, missiles, débris) puisent dans un compteur monotone de 64 bits et ne sont jamais réutilisés : sur un serveur qui tourne des jours, un compteur de 32 bits finirait par déborder. Les balles louent leurs identifiants dans une bande réservée, de 8 192 à 16 382, où chaque identifiant tient sur deux octets, et les rendent à leur mort. Le compteur durable saute par-dessus la bande : une balle et un vaisseau ne peuvent jamais porter le même numéro, ni maintenant ni dans dix heures.

網路 ID：兩種生命週期，兩種制度

每個物件都需要一個用戶端能拿來當鍵的 ID。天真的答案——一個全域計數器——會與第 1.3 章的編碼衝突：ID 是可變長度整數，16,382 以內兩個位元組，之後四個位元組，沒有三位元組的長度。子彈只活約一秒，而每秒發射數百顆，所以在全域計數器上，它們的 ID 幾分鐘內就超過了 16,383，之後每份快照中的每個子彈 ID 都要花四個位元組。

實測

每份快照約有 140 位元組的子彈 ID，佔整個封包的 7 %，花在為用戶端兩秒後就會忘記的物件編號上。

所以 ID 遵循兩種制度。持久的物件（船體、角色、太空站、飛彈、碎片）從一個單調遞增的 64 位元計數器取號，永不重複使用：在一台連續運作好幾天的伺服器上，32 位元的計數器總有一天會溢位。子彈則從一段保留區段 8,192 到 16,382 租用 ID，這裡的每個 ID 都放得進兩個位元組，並在子彈死亡時歸還。持久計數器會跳過這個區段，所以子彈與船艦永遠不可能共用同一個號碼，不論是現在還是十個小時後。

GameServer/Domain/MetaObjectId.cs · simplified
public const ulong TransientFirst = 8192, TransientLast = 16382;   // last two-byte id
private const long QuarantineMs = 10_000;

public static ulong Next()                                         // durable ids
{
    while (true)
    {
        var n = Interlocked.Increment(ref _next);
        if (n < TransientFirst || n > TransientLast) return n;
        Interlocked.CompareExchange(ref _next, TransientLast, n);  // push past the band, retry
    }
}

public static ulong RentTransient()                                // bullets
{
    lock (_gate)
    {
        if (_quarantine.Count > 0 && _quarantine.Peek().FreeAtMs <= Environment.TickCount64)
            return _quarantine.Dequeue().Id;  // oldest id out of quarantine
        if (_nextTransientFresh <= TransientLast) return _nextTransientFresh++;
    }
    return Next();                                                 // band exhausted: still correct
}

public static void ReleaseTransient(ulong id)
{
    if (id < TransientFirst || id > TransientLast) return;
    lock (_gate) _quarantine.Enqueue((id, Environment.TickCount64 + QuarantineMs));
}

The quarantine is what makes recycling safe. The client keeps a bullet under its id until the bullet expires on its side, about two seconds plus an impact grace. An id handed out again sooner would teleport the old bullet onto the new one. Ten seconds is five times that lifetime, and the sizing holds: about 300 live bullets plus 250 spawns per second times 10 seconds is roughly 2,800 ids in circulation, for 8,191 in the band. If a burst ever exhausts the band anyway, bullets fall back on the durable counter: larger ids, still correct.

Rule

Reuse an identifier only after everyone who could still hold it has forgotten it, and size the delay from their memory, not yours.

The server forgets a bullet the tick it dies. The client does not, and it is the client's memory that decides when the number is free.

La quarantaine est ce qui rend le recyclage sûr. Le client garde une balle sous son identifiant jusqu'à ce qu'elle expire de son côté, environ deux secondes plus une grâce d'impact. Un identifiant redonné plus tôt téléporterait la vieille balle sur la nouvelle. Dix secondes, c'est cinq fois cette durée de vie, et le dimensionnement tient : environ 300 balles vivantes plus 250 apparitions par seconde fois 10 secondes, c'est à peu près 2 800 identifiants en circulation, pour 8 191 dans la bande. Si une salve épuise quand même la bande, les balles se rabattent sur le compteur durable : des identifiants plus gros, toujours justes.

Règle

Ne réutiliser un identifiant qu'une fois que tous ceux qui pourraient encore le tenir l'ont oublié, et dimensionner le délai sur leur mémoire, pas sur la sienne.

Le serveur oublie une balle au tick où elle meurt. Le client, non, et c'est la mémoire du client qui décide quand le numéro est libre.

隔離期讓回收變得安全。用戶端會以子彈的 ID 保留它，直到子彈在用戶端那邊到期，大約兩秒再加上一段命中寬限。一個太早被再次發出的 ID，會把舊的子彈瞬移到新的子彈上。十秒是那段生命週期的五倍，而容量也足夠：約 300 顆存活子彈，加上每秒 250 次產生乘以 10 秒，流通中的 ID 大約 2,800 個，而區段有 8,191 個。如果某次突發仍然用光了區段，子彈會退回持久計數器：ID 比較大，但仍然正確。

規則

只有在每個可能還持有某個識別碼的人都忘了它之後，才能重複使用它，而延遲的長短要依他們的記憶而定，不是你的。

伺服器在子彈死亡的那個 tick 就忘了它。用戶端不會，而決定這個號碼何時空出來的，是用戶端的記憶。

Players and NPCs speak the same language

A player's ship is driven by a few intention fields that the network thread writes: move this way, aim there, trigger held. An NPC ship is driven by the same kind of fields, written by its behaviours instead. In both cases the ship's own tick applies the intentions through the same physics, so a heavy NPC is slow for the same reasons as a heavy player, and an under-powered sentry visibly stutters under the same power budget players live with. Behaviours desire; the actor applies.

That split has a second rule: mechanism upkeep stays on the actor, never in a behaviour. Weapon cooldowns tick in the ship's own update whether or not anything is trying to fire. If they lived in the firing behaviour, detaching that behaviour in the middle of a fight would freeze every hardpoint mid-cooldown forever. The same split is what lets a disconnected player's lingering hull (chapter 2.3) become an inert wreck: its intentions are cleared, and its mechanisms keep running.

Joueurs et PNJ parlent la même langue

Le vaisseau d'un joueur est piloté par quelques champs d'intention que le thread réseau écrit : aller par là, viser là-bas, gâchette tenue. Un vaisseau PNJ est piloté par le même genre de champs, écrits par ses comportements. Dans les deux cas, le tick du vaisseau applique ces intentions par la même physique : un PNJ lourd est lent pour les mêmes raisons qu'un joueur lourd, et une tourelle sous-alimentée hoquette visiblement sous le même budget d'énergie que celui des joueurs. Les comportements désirent ; l'acteur applique.

Ce partage a une seconde règle : l'entretien des mécanismes reste sur l'acteur, jamais dans un comportement. Les temps de recharge des armes s'écoulent dans la mise à jour du vaisseau, que quelque chose essaie de tirer ou non. S'ils vivaient dans le comportement de tir, détacher ce comportement en plein combat figerait chaque point d'emport au milieu de sa recharge, pour toujours. Le même partage est ce qui permet à la coque rémanente d'un joueur déconnecté (chapitre 2.3) de devenir une épave inerte : ses intentions sont vidées, et ses mécanismes continuent de tourner.

玩家與 NPC 說同一種語言

玩家的船艦由網路執行緒寫入的幾個意圖欄位驅動：往這邊移動、瞄準那裡、扳機按住。NPC 的船艦由同一類欄位驅動，只是改由它的行為寫入。兩種情況下，都是船艦自己的 tick 透過同一套物理來套用這些意圖，所以一艘沉重的 NPC 船會因為和沉重的玩家船相同的理由而緩慢，而一座電力不足的哨兵，會在與玩家同樣的電力預算下明顯地卡頓。行為負責渴望；行動者負責套用。

這種拆分還有第二條規則：機制的維護留在行動者身上，絕不放在行為裡。武器冷卻會在船艦自己的更新中 tick，不論有沒有東西想開火。如果它們放在開火行為中，在戰鬥中途卸下這個行為，就會讓每個武器掛點永遠凍結在冷卻中途。同樣的拆分，也讓斷線玩家的殘留船體（第 2.3 章）能變成一具無動作的殘骸：它的意圖被清除，而它的機制繼續運作。

Behaviour by composition

What an NPC does is not decided by its class but by the behaviours attached to it at spawn. "A sentry that sweeps and fires" and "a ship that aims at the nearest target and fires" are the same NPC class with different parts, not two subclasses.

Le comportement par composition

Ce que fait un PNJ n'est pas décidé par sa classe mais par les comportements qu'on lui attache à l'apparition. « Une sentinelle qui balaie et tire » et « un vaisseau qui vise la cible la plus proche et tire » sont la même classe de PNJ avec des pièces différentes, pas deux sous-classes.

以組合構成行為

NPC 做什麼，不是由它的類別決定，而是由產生時附加在它身上的行為決定。「一座會掃視並開火的哨兵」和「一艘瞄準最近目標並開火的船」是同一個 NPC 類別配上不同的零件，而不是兩個子類別。

public interface IBehavior<in TActor>  // contravariant: a behaviour written for
{                                        // Character works on every NpcCharacter
    void Tick(TActor actor, double dt);  // actor passed in, never captured
}

public sealed class BehaviorSet<TActor>
{
    private readonly List<IBehavior<TActor>> _behaviors = new();

    public BehaviorSet<TActor> Add(IBehavior<TActor> b) { _behaviors.Add(b); return this; }

    public void Tick(TActor actor, double dt)
    {
        for (var i = 0; i < _behaviors.Count; i++)  // by index: a behaviour may add or remove
            _behaviors[i].Tick(actor, dt);          // another; additions run next tick
    }
}

// At a spawn site: order is meaningful, aim before fire.
sentry.Behaviors
    .Add(new ShipAimAtNearestBehavior(range))
    .Add(new ShipContinuousFireBehavior());

Three small decisions make this work well:

  • Contravariance. The interface is IBehavior<in TActor>. A behaviour written against the loosest type it needs (anything that can aim) drops into the set of any more specific actor with no adapter and no cast. Write each behaviour against the smallest type it needs and it stays reusable by construction.
  • The actor is a parameter. Behaviours do not capture their actor, so they hold no back-reference that would keep a despawned NPC alive, and a single stateless behaviour instance could be shared.
  • Order instead of a scheduler. Behaviours run in insertion order, with no priorities and no arbitration. That covers everything in the game today; inventing a scheduler before a case needs one would be guessing at requirements. The set is its own small type precisely so that arbitration has an obvious place to grow later, without touching any actor.

Trois petites décisions font que ça marche bien :

  • La contravariance. L'interface est IBehavior<in TActor>. Un comportement écrit pour le type le plus large dont il a besoin (tout ce qui peut viser) se glisse dans l'ensemble de n'importe quel acteur plus précis, sans adaptateur ni conversion. Écrire chaque comportement contre le plus petit type dont il a besoin, et il reste réutilisable par construction.
  • L'acteur est un paramètre. Les comportements ne capturent pas leur acteur : ils ne tiennent aucune référence arrière qui garderait en vie un PNJ disparu, et une même instance sans état pourrait être partagée.
  • L'ordre plutôt qu'un ordonnanceur. Les comportements tournent dans l'ordre d'insertion, sans priorités ni arbitrage. Cela couvre tout ce qu'il y a dans le jeu aujourd'hui ; inventer un ordonnanceur avant qu'un cas en ait besoin, ce serait deviner des besoins. L'ensemble est son propre petit type justement pour que l'arbitrage ait un endroit évident où grandir plus tard, sans toucher aucun acteur.

有三個小決定讓這運作得很好：

  • 反變性。介面是 IBehavior<in TActor>。一個針對它所需最寬鬆型別（任何能瞄準的東西）寫成的行為，可以直接放進任何更具體的行動者的行為集合中，不需要轉接器，也不需要轉型。讓每個行為都針對它所需的最小型別來寫，它在結構上就保持可重複使用。
  • 行動者是參數。行為不擷取它們的行動者，所以不持有任何會讓已消失的 NPC 繼續存活的反向參考，而單一的無狀態行為實例也可以被共用。
  • 用順序取代排程器。行為依加入的順序執行，沒有優先權，也沒有仲裁。這涵蓋了目前遊戲中的一切；在有案例需要之前就發明一個排程器，等於是在猜需求。行為集合本身就是一個小型別，正是為了讓仲裁日後有個明顯可以成長的地方，而不必動到任何行動者。

Pools, and the double release

Bullets and missiles are pooled per map: the C# object graph is reused across shots instead of allocated for each one. The pool is per map because a bullet's simulation slot lives in that map's bullet array, which sweeps against that map's physics world; an instance pooled in one map can never be handed out in another.

Pools come with their own classic bug: releasing the same instance twice. A bullet can run out of range and take a hit in the same tick, and both paths scheduled its return to the pool. Returned twice, the instance would later be handed out twice, and two logically distinct future shots would share one object. A "pending despawn" flag, set by whichever path gets there first, makes the second attempt a no-op.

Rule

Make every release idempotent before you pool anything.

A double free in a pool is not a crash; it is two live objects sharing one identity, discovered much later somewhere else.

Les réserves, et la double restitution

Les balles et les missiles sont gérés en réserve par carte : le graphe d'objets C# est réutilisé d'un tir à l'autre au lieu d'être alloué à chaque fois. La réserve est par carte parce que la case de simulation d'une balle vit dans le tableau de balles de cette carte, qui balaie le monde physique de cette carte ; une instance mise en réserve dans une carte ne peut jamais être distribuée dans une autre.

Les réserves viennent avec leur bug classique : restituer deux fois la même instance. Une balle peut arriver en bout de portée et toucher au même tick, et les deux chemins planifiaient son retour en réserve. Rendue deux fois, l'instance serait plus tard distribuée deux fois, et deux tirs futurs, logiquement distincts, partageraient un seul objet. Un drapeau « retrait en attente », posé par le premier chemin qui arrive, fait de la seconde tentative une opération nulle.

Règle

Rendre chaque restitution idempotente avant de mettre quoi que ce soit en réserve.

Une double libération dans une réserve n'est pas un plantage ; ce sont deux objets vivants qui partagent une identité, découverts bien plus tard ailleurs.

物件池，以及重複釋放

子彈與飛彈以地圖為單位放在物件池中：C# 物件圖在每次射擊之間重複使用，而不是每次都配置。物件池以地圖為單位，因為子彈的模擬格子位於那張地圖的子彈陣列中，掃掠的對象是那張地圖的物理世界；在一張地圖的池中的實例，永遠不可能被發給另一張地圖。

物件池附帶著它自己的經典 bug：同一個實例被釋放兩次。一顆子彈可能在同一個 tick 中既超出射程、又被命中，兩條路徑都排定了把它還回池中。被歸還兩次的實例，之後會被發出兩次，兩次邏輯上不同的未來射擊就會共用同一個物件。一個「待消失」旗標，由先到的那條路徑設定，讓第二次嘗試變成什麼都不做。

規則

在把任何東西放進物件池之前，先讓每一次釋放都具有冪等性。

物件池中的重複釋放不會當機；它會讓兩個存活的物件共用同一個身分，然後在很久之後、在別的地方被發現。

Data read by several threads: swap, do not mutate

A hull's list of hex parts is read from several threads: the tick rebuilds it after construction work, the network thread reads it while answering inventory and interaction requests, the snapshot builder reads it too. It used to be rebuilt in place, clear then refill, so any reader enumerating it during that window hit "collection was modified". It needed a player to press a key at the exact moment a build was applied: rare, load-dependent, impossible to reproduce on demand.

The list is now never mutated: a new list is built and swapped in with one reference assignment. A reader holding the old list keeps a complete, coherent one and simply sees the layout from a moment ago. One tick stale beats one exception. The comment next to it also says what this does not allow: the ship's computed stats come from a cache without that guarantee, so only the part list itself is safe to read off-thread.

Des données lues par plusieurs threads : échanger, pas modifier

La liste des pièces hexagonales d'une coque est lue depuis plusieurs threads : le tick la reconstruit après des travaux de construction, le thread réseau la lit en répondant aux demandes d'inventaire et d'interaction, et le constructeur de snapshots la lit aussi. Elle était autrefois reconstruite sur place, vidée puis remplie : tout lecteur qui la parcourait pendant cette fenêtre tombait sur « collection was modified ». Il fallait qu'un joueur appuie sur une touche à l'instant précis où une construction s'appliquait : rare, dépendant de la charge, impossible à reproduire à la demande.

La liste n'est maintenant jamais modifiée : une nouvelle liste est construite puis échangée par une seule affectation de référence. Un lecteur qui tient l'ancienne garde une liste complète et cohérente, et voit simplement la disposition d'il y a un instant. Un tick de retard vaut mieux qu'une exception. Le commentaire à côté dit aussi ce que ça ne permet pas : les statistiques calculées du vaisseau viennent d'un cache sans cette garantie, donc seule la liste des pièces se lit sans risque hors du tick.

被多條執行緒讀取的資料：交換，不要修改

船體的六角零件清單會被好幾條執行緒讀取：tick 在建造工作之後重建它，網路執行緒在回應庫存與互動請求時讀取它，快照建構器也會讀取它。它過去是就地重建的，先清空再重新填入，所以任何在那段期間列舉它的讀取端，都會碰到「collection was modified」。這需要玩家剛好在一次建造被套用的那一刻按下按鍵：罕見、取決於負載、無法隨時重現。

現在這份清單從不被修改：建立一份新清單，再用一次參考指派換上去。持有舊清單的讀取端保有一份完整、一致的清單，只是看到的是片刻之前的配置。慢一個 tick 勝過一次例外。旁邊的註解也說明了這不允許什麼：船艦計算出的數值來自一個沒有這種保證的快取，所以只有零件清單本身可以在其他執行緒上安全讀取。

Key takeaways

  • Give every object one way in and one way out of a map, deferred to the tick, and announce departures from the single exit.
  • Let ticking follow map membership instead of manual subscriptions, and keep typed lists for the narrow questions.
  • Choose id regimes from lifetimes and encoding: a never-reused counter for durable objects, a recycled two-byte band with a quarantine for bullets.
  • Drive players and NPCs through the same intention fields, keep mechanism upkeep on the actor, and compose behaviours.
  • Make pool releases idempotent, and swap shared lists instead of mutating them.

À retenir

  • Donner à chaque objet une seule entrée et une seule sortie de carte, différées vers le tick, et annoncer les départs depuis la sortie unique.
  • Faire suivre le tick à l'appartenance à la carte plutôt qu'à des abonnements manuels, et garder des listes typées pour les questions étroites.
  • Choisir les régimes d'identifiants selon les durées de vie et l'encodage : un compteur jamais réutilisé pour les objets durables, une bande recyclée sur deux octets avec quarantaine pour les balles.
  • Piloter joueurs et PNJ par les mêmes champs d'intention, garder l'entretien des mécanismes sur l'acteur, et composer les comportements.
  • Rendre les restitutions en réserve idempotentes, et échanger les listes partagées au lieu de les modifier.

重點整理

  • 給每個物件一條進入、一條離開地圖的路，延後到 tick 執行，並從唯一的出口宣告離開。
  • 讓 tick 跟著地圖歸屬走，而不是手動訂閱，並為那些窄問題保留型別清單。
  • 依生命週期與編碼選擇 ID 制度：持久物件用永不重複使用的計數器，子彈用帶隔離期、可回收的兩位元組區段。
  • 以相同的意圖欄位驅動玩家與 NPC，把機制的維護留在行動者身上，並組合行為。
  • 讓物件池的釋放具有冪等性，並交換共用的清單，而不是修改它們。

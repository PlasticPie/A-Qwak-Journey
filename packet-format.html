A binary protocol of your ownUn protocole binaire à soi

Framing, positional payloads, and the discipline that keeps a hand-written serializer honest.Les trames, les charges utiles positionnelles, et la discipline qui garde un sérialiseur écrit à la main honnête.

Why write the format by hand

JSON is readable and self-describing, and far too large for 25 updates a second per player: every field name travels with every value. Schema-based binary formats such as Protocol Buffers, FlatBuffers or MessagePack are compact and handle adding fields gracefully, and they are a perfectly good choice for a game. MoonQwak writes its packets by hand instead, for three reasons:

  • Control over every byte. The hottest messages use tricks a general serializer does not offer: a flag byte that says which blocks follow, quantized numbers, a bullet sent in two different formats depending on what the receiver already knows (Part 4).
  • No allocation on the hot path. The snapshot for one player is serialized into a reused buffer, 25 times a second, without creating garbage for the collector. That is easier to guarantee in code you wrote.
  • The same C# on both ends. The packet classes live in a library compiled for both the server and the Unity client, so there is no generated code to keep in sync with anything.

The price is real. A hand-written format has no schema and no field names on the wire, so nothing but discipline makes the writer and the reader agree. Chapter 1.6 is the other half of this one: the tests and the version gate that turned that discipline into something checked.

Pourquoi écrire le format à la main

JSON est lisible et auto-descriptif, et bien trop gros pour 25 mises à jour par seconde et par joueur : chaque nom de champ voyage avec chaque valeur. Les formats binaires à schéma comme Protocol Buffers, FlatBuffers ou MessagePack sont compacts et gèrent bien l'ajout de champs, et ce sont de très bons choix pour un jeu. MoonQwak écrit pourtant ses paquets à la main, pour trois raisons :

  • La maîtrise de chaque octet. Les messages les plus chauds utilisent des astuces qu'un sérialiseur générique n'offre pas : un octet de drapeaux qui dit quels blocs suivent, des nombres quantifiés, une balle envoyée sous deux formats différents selon ce que le destinataire sait déjà (partie 4).
  • Aucune allocation sur le chemin chaud. Le snapshot d'un joueur est sérialisé dans un tampon réutilisé, 25 fois par seconde, sans créer de déchets pour le ramasse-miettes. C'est plus facile à garantir dans du code qu'on a écrit.
  • Le même C# des deux côtés. Les classes de paquets vivent dans une bibliothèque compilée à la fois pour le serveur et pour le client Unity : aucun code généré à garder synchronisé avec quoi que ce soit.

Le prix est réel. Un format écrit à la main n'a ni schéma ni noms de champs sur le fil : rien d'autre que la discipline ne garantit que l'écrivain et le lecteur sont d'accord. Le chapitre 1.6 est l'autre moitié de celui-ci : les tests et la porte de version qui ont transformé cette discipline en quelque chose de vérifié.

The length field is not redundant with the transport: the transport delivers a whole datagram, but the parser still checks that the declared payload fits in what arrived before reading anything. A frame that claims more bytes than it carries is rejected as a whole instead of being half-parsed.

Le champ de longueur n'est pas redondant avec le transport : le transport livre un datagramme entier, mais le parseur vérifie quand même que la charge utile annoncée tient dans ce qui est arrivé avant de lire quoi que ce soit. Une trame qui annonce plus d'octets qu'elle n'en porte est refusée en bloc au lieu d'être parsée à moitié.

Positional payloads

Inside the payload, fields are written in a fixed order with no names and no tags. A login is a string, a string, then a number. A snapshot is a tick number, a flag byte, an optional block for the player's own ship, then a count followed by that many objects. The reader must read exactly what the writer wrote, in the same order, with the same sizes. If it reads one byte too few or too many, every field after that point is garbage, and nothing in the bytes says so.

This is the smallest possible encoding and the most fragile one. Three rules keep it workable:

  1. Append, never insert. A new field goes at the end of a packet. A reader built later can then detect that an older writer did not send it, by checking whether any bytes remain.
  2. Presence is explicit. An optional block is announced by a bit in a flag byte written before it, or by a count. The parser never guesses.
  3. Absence has a meaning, or it has a count of zero. Only read "is there anything left?" when "not sent" must mean something different from "zero". Otherwise always write the field; a field that is always written cannot be forgotten by the reader.

Des charges utiles positionnelles

Dans la charge utile, les champs sont écrits dans un ordre fixe, sans noms ni étiquettes. Un login, c'est une chaîne, une chaîne, puis un nombre. Un snapshot, c'est un numéro de tick, un octet de drapeaux, un bloc optionnel pour le vaisseau du joueur, puis un compte suivi d'autant d'objets. Le lecteur doit lire exactement ce que l'écrivain a écrit, dans le même ordre, avec les mêmes tailles. S'il lit un octet de trop ou de moins, chaque champ suivant est du bruit, et rien dans les octets ne le signale.

C'est l'encodage le plus petit possible, et le plus fragile. Trois règles le rendent vivable :

  1. Ajouter, jamais insérer. Un nouveau champ va à la fin du paquet. Un lecteur plus récent peut alors détecter qu'un écrivain plus ancien ne l'a pas envoyé, en regardant s'il reste des octets.
  2. La présence est explicite. Un bloc optionnel est annoncé par un bit dans un octet de drapeaux écrit avant lui, ou par un compte. Le parseur ne devine jamais.
  3. L'absence a un sens, ou elle a un compte de zéro. Ne regarder « reste-t-il quelque chose ? » que quand « non envoyé » doit vouloir dire autre chose que « zéro ». Sinon, toujours écrire le champ : un champ toujours écrit ne peut pas être oublié par le lecteur.
Packet/Packets/Auth/Login.cs · an appended field, read defensively
// The default value is a compile-time constant, inlined at each call site:
// every binary sends the protocol number it was built with, without anyone thinking about it.
public Login(string username, string password, int protocol = ProtocolVersion.Current) { ... }

protected override void Build()
{
    WriteString(Username);
    WriteString(Password);
    WriteVarInt(Protocol);  // appended later: always written at the end
}

protected override bool ParsePayload()
{
    Username = ReadString();
    Password = ReadString();
    // A client built before this field existed does not send it. Without this guard the read
    // would throw on an exhausted stream and the old client would see a login screen that never
    // answers. Reading 0 instead gets it refused, with a reason it can display.
    Protocol = Remaining > 0 ? (int)ReadVarInt() : 0;
    return true;
}

One class, two directions

Every packet type is a class deriving from BasePacket, with a Build() method that writes the payload and a ParsePayload() method that reads it. The base class owns the stream, the header and the primitives (fixed-size integers, strings, varints, quantized numbers, angles). A packet instance is either being written or being read, never both: asking a parsed packet to serialize itself throws.

That last rule looks like a detail and shaped a habit. When the game server relays a message it received from the gateway to a client, it cannot forward the object it parsed: it builds a new one from the parsed fields. A "forward" would have worked by accident with some packet types and thrown with others.

Une classe, deux sens

Chaque type de paquet est une classe dérivée de BasePacket, avec une méthode Build() qui écrit la charge utile et une méthode ParsePayload() qui la lit. La classe de base possède le flux, l'en-tête et les primitives (entiers de taille fixe, chaînes, varints, nombres quantifiés, angles). Une instance de paquet est soit en écriture, soit en lecture, jamais les deux : demander à un paquet parsé de se sérialiser lève une exception.

Cette dernière règle a l'air d'un détail et a façonné une habitude. Quand le serveur de jeu relaie à un client un message reçu de la gateway, il ne peut pas transmettre l'objet parsé : il en construit un neuf à partir des champs lus. Un simple « transfert » aurait marché par hasard avec certains types de paquets et levé une exception avec d'autres.

Packet/BasePacket.cs · framing, shared by every send path
private void FrameIntoStream()
{
    var ms = GetMemoryStream();
    ms.SetLength(0);                   // reset BEFORE Build: the instance may be reused
    Build();                           // subclass writes its payload

    var payloadLen = (int)ms.Length;
    var payload = ArrayPool<byte>.Shared.Rent(payloadLen);  // rented, not allocated
    ms.Position = 0;
    ms.Read(payload, 0, payloadLen);

    ms.SetLength(0);
    Write((byte)Version);              // header
    Write(Type);
    Write(RSV);
    WriteUVarInt((ulong)payloadLen);
    ms.Write(payload, 0, payloadLen);  // then the payload
    ArrayPool<byte>.Shared.Return(payload);
}

Pitfall I hit

The reset at the top of that method was once only at the bottom. A debug broadcaster sent the same packet object to several connected tools in a loop, so the second Build() appended its payload after the complete frame of the first call. The tools displayed "billions of connected peers" and negative byte counts. The fix was one line; finding it took an afternoon, because the numbers looked like a counter overflow, not like a framing bug.

Piège rencontré

La remise à zéro en tête de cette méthode n'était autrefois qu'à la fin. Un diffuseur de debug envoyait le même objet paquet à plusieurs outils connectés dans une boucle : le second Build() ajoutait sa charge utile après la trame complète du premier appel. Les outils affichaient « des milliards de pairs connectés » et des compteurs d'octets négatifs. La correction tenait en une ligne ; la trouver a pris un après-midi, parce que les chiffres ressemblaient à un débordement de compteur, pas à un bug de trame.

From a type id to a handler

The receiver reads the type field and asks a ParserFactory for a fresh instance of the matching class, then lets it parse. A Dispatcher maps each type to one or more handlers. Registering a handler for a type registers the parser at the same time, so there is no way to handle a packet you cannot parse, or to parse one nobody handles without the client saying so in its log.

A few packets need a session token in front of their payload. Rather than asking each of them to remember, an AuthenticatedPacket base class writes and reads the token itself, then calls the subclass for the rest. Its Build and ParsePayload are sealed: a subclass cannot forget the token because it never had the chance to write it.

D'un identifiant de type à un gestionnaire

Le récepteur lit le champ de type et demande à une ParserFactory une instance neuve de la classe correspondante, puis la laisse parser. Un Dispatcher associe chaque type à un ou plusieurs gestionnaires. Enregistrer un gestionnaire pour un type enregistre le parseur en même temps : impossible de gérer un paquet qu'on ne sait pas parser, ou d'en parser un que personne ne gère sans que le client le dise dans son journal.

Quelques paquets doivent porter un jeton de session devant leur charge utile. Plutôt que de demander à chacun de s'en souvenir, une classe de base AuthenticatedPacket écrit et lit le jeton elle-même, puis appelle la sous-classe pour le reste. Ses Build et ParsePayload sont scellées : une sous-classe ne peut pas oublier le jeton, elle n'a jamais eu l'occasion de l'écrire.

Network/Dispatcher.cs · one call registers parsing and handling
public bool Register<T>(ushort id, Handler handler) where T : IPacket, new()
{
    ParserFactory.Register<T>(id);   // how to build an instance of this type
    return Register(id, handler);     // what to do with it
}

// usage, on the game server
server.Dispatcher.Register<PlayerInput>((ushort)Type.PlayerInput,
    (peerId, packet, source) =>
        sessions.GetConnectedPlayer(peerId)?.HandleInput((PlayerInput)packet) ?? false);

Two styles of packet

Not every message deserves the same care about bytes. MoonQwak ended up with two deliberately different styles.

Gameplay stream

Snapshots, inputs, bullets. Sent many times a second to many players.

  • Compact: varints, quantization, flag bytes.
  • May be delta or conditional.
  • Tuned by measurement.

Social and economy state

Market, mail, trade, guild roster. Sent when a screen opens or something changes.

  • Always the full state; the client replaces its copy, never accumulates.
  • Durations ("expires in 3,600 s"), never dates, so no clocks to synchronize.
  • Codes, never sentences (see 1.6).

A market screen opens a few times per session and weighs a few kilobytes. Making it idempotent (the same message applied twice gives the same result) is worth far more than the bytes a delta would save, because no race can leave a ghost order on screen, and resynchronizing costs one packet.

Deux styles de paquets

Tous les messages ne méritent pas le même soin sur les octets. MoonQwak a fini avec deux styles volontairement différents.

Flux de jeu

Snapshots, entrées, balles. Envoyés de nombreuses fois par seconde à de nombreux joueurs.

  • Compacts : varints, quantification, octets de drapeaux.
  • Peuvent être en delta ou conditionnels.
  • Réglés à la mesure.

État social et économique

Marché, courrier, échange, liste de guilde. Envoyés à l'ouverture d'un écran ou quand quelque chose change.

  • Toujours l'état complet ; le client remplace sa copie, il n'accumule jamais.
  • Des durées (« expire dans 3 600 s »), jamais des dates : aucune horloge à synchroniser.
  • Des codes, jamais des phrases (voir 1.6).

Un écran de marché s'ouvre quelques fois par session et pèse quelques kilo-octets. Le rendre idempotent (le même message appliqué deux fois donne le même résultat) vaut bien plus que les octets qu'un delta économiserait : aucune course ne peut laisser un ordre fantôme à l'écran, et une resynchronisation coûte un paquet.

Shared codecs: one layout, two readers

For a long time, the body of a snapshot object was written by server domain classes (a ship, a bullet) and read by Unity classes (the client's ship, the client's bullet). Two files, in two projects, bound together only by a comment saying "exact mirror of the server's Marshal". Five wire bugs in one optimization session came from that gap, and none of them could be caught by a test, because no test project could reference both sides.

The fix was to move the layout of the hottest blocks into small codecs in the shared packet library. The server fills a plain struct from its ship and calls Write; the client calls Read and applies the struct. The codec knows nothing about ships. Adding a field adds it for both readers at once, or the client stops compiling.

Des codecs partagés : une disposition, deux lecteurs

Longtemps, le corps d'un objet de snapshot a été écrit par des classes de domaine du serveur (un vaisseau, une balle) et lu par des classes Unity (le vaisseau du client, la balle du client). Deux fichiers, dans deux projets, liés seulement par un commentaire « miroir exact du Marshal du serveur ». Cinq bugs de fil en une seule session d'optimisation sont venus de cet écart, et aucun ne pouvait être attrapé par un test, puisqu'aucun projet de test ne pouvait référencer les deux côtés.

La correction a été de déplacer la disposition des blocs les plus chauds dans de petits codecs de la bibliothèque de paquets partagée. Le serveur remplit une structure simple depuis son vaisseau et appelle Write ; le client appelle Read et applique la structure. Le codec ne sait rien d'un vaisseau. Ajouter un champ l'ajoute pour les deux lecteurs d'un coup, ou le client ne compile plus.

Packet/Wire/MovementWire.cs
public struct MovementFields { public double X, Y, Rotation, VelX, VelY, AngularVelocity; }

public static class MovementWire
{
    public static void Write(BasePacket p, in MovementFields f)
    {
        p.WriteQuantized(f.X, NetworkPrecision.Position);  // 2.5 cm steps
        p.WriteQuantized(f.Y, NetworkPrecision.Position);
        p.WriteAngle(f.Rotation);                             // 16-bit fraction of a turn
        p.WriteQuantized(f.VelX, NetworkPrecision.Velocity);  // 1 cm/s steps
        p.WriteQuantized(f.VelY, NetworkPrecision.Velocity);
        p.WriteQuantized(f.AngularVelocity, NetworkPrecision.AngularVelocity);
    }

    public static MovementFields Read(BasePacket p) => new MovementFields
    {
        X = p.ReadQuantized(NetworkPrecision.Position),
        Y = p.ReadQuantized(NetworkPrecision.Position),
        Rotation = p.ReadAngle(),
        VelX = p.ReadQuantized(NetworkPrecision.Velocity),
        VelY = p.ReadQuantized(NetworkPrecision.Velocity),
        AngularVelocity = p.ReadQuantized(NetworkPrecision.AngularVelocity),
    };
}

Pitfall I hit

The client once skipped the per-hex block of a ship it could not apply yet with a hard-coded bytesPerPart constant. The server later removed one field from that block. The constant became wrong, the reader desynchronized, and the client threw EndOfStreamException on ships in the middle of a rebuild. It now skips the block by parsing it with the same code as the normal path.

Rule

Knowledge of a wire format must exist in exactly one place: the writer/reader pair.

A constant that "knows" how many bytes a block takes, a second parser written for a special case, a comment that promises a mirror: each is a copy of the format that will not be updated with it.

Piège rencontré

Le client sautait autrefois le bloc par hex d'un vaisseau qu'il ne pouvait pas encore appliquer, avec une constante bytesPerPart écrite en dur. Le serveur a ensuite retiré un champ de ce bloc. La constante est devenue fausse, le lecteur s'est désynchronisé, et le client levait EndOfStreamException sur les vaisseaux en pleine reconstruction. Il saute maintenant ce bloc en le parsant avec le même code que le chemin normal.

Règle

La connaissance d'un format de fil doit exister à un seul endroit : la paire écrivain/lecteur.

Une constante qui « sait » combien d'octets fait un bloc, un second parseur écrit pour un cas particulier, un commentaire qui promet un miroir : chacun est une copie du format qui ne sera pas mise à jour avec lui.

Key takeaways

  • A small fixed header (version, type, reserved byte, payload length) in front of every message lets the receiver reject malformed frames before reading fields.
  • Positional payloads are the most compact and the most fragile encoding: append fields at the end, announce optional blocks explicitly.
  • Keep writing and reading of one packet in one class, and never reuse a parsed packet to send.
  • Use full-state, idempotent packets for anything that is not sent many times a second.
  • Put the layout of the hottest blocks in codecs shared by both ends, so that a format change cannot reach only one of them.

À retenir

  • Un petit en-tête fixe (version, type, octet réservé, longueur) devant chaque message permet au récepteur de refuser une trame malformée avant de lire les champs.
  • Les charges utiles positionnelles sont l'encodage le plus compact et le plus fragile : ajouter les champs à la fin, annoncer explicitement les blocs optionnels.
  • Garder l'écriture et la lecture d'un paquet dans une seule classe, et ne jamais réutiliser un paquet parsé pour envoyer.
  • Utiliser des paquets d'état complet et idempotents pour tout ce qui n'est pas envoyé plusieurs fois par seconde.
  • Mettre la disposition des blocs les plus chauds dans des codecs partagés par les deux bouts, pour qu'un changement de format ne puisse pas n'en atteindre qu'un.

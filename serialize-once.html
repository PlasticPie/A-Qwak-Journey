Turning O(players × objects) serialization into O(objects), and the data race it hid until 780 players.Passer d'une sérialisation en O(joueurs × objets) à O(objets), et la course de données qu'elle a cachée jusqu'à 780 joueurs.把 O(玩家 × 物件) 的序列化變成 O(物件)，以及它一直藏到 780 名玩家才現形的資料競爭。

The same bytes, written once per viewer

Snapshots are built per player, in a parallel loop, and for each visible object the builder used to call that object's serializer. But an object's bytes are the same for every player who sees it. A ship serializing itself walks its list of parts several times; a hundred players who all see each other made that walk a hundred times per ship per tick, to produce a hundred identical byte sequences.

The cost was only half the problem. Serializers carry small per-tick memos (for example "has this ship stopped moving since last tick?", chapter 4.4), and a hundred threads serializing the same ship all wrote to those memos at once. A real data race, invisible as long as there was one player per map, which was every test.

Les mêmes octets, écrits une fois par spectateur

Les snapshots sont construits par joueur, dans une boucle parallèle, et pour chaque objet visible le constructeur appelait le sérialiseur de cet objet. Or les octets d'un objet sont les mêmes pour tous les joueurs qui le voient. Un vaisseau qui se sérialise parcourt plusieurs fois sa liste de pièces ; cent joueurs qui se voient tous faisaient ce parcours cent fois par vaisseau et par tick, pour produire cent suites d'octets identiques.

Le coût n'était que la moitié du problème. Les sérialiseurs portent de petits mémos par tick (par exemple « ce vaisseau s'est-il arrêté depuis le tick dernier ? », chapitre 4.4), et cent threads qui sérialisent le même vaisseau écrivaient tous dans ces mémos en même temps. Une vraie course de données, invisible tant qu'il y avait un joueur par carte, c'est-à-dire dans tous les tests.

同樣的位元組，為每位觀察者各寫一次

快照是在一個平行迴圈中為每位玩家各自建構的，而對每個可見的物件，建構器過去都會呼叫那個物件的序列化器。但一個物件的位元組，對每位看到它的玩家來說都是一樣的。一艘船序列化自己時會走訪它的零件清單好幾次；一百位彼此看得見的玩家，就讓每艘船每個 tick 走訪一百次，只為了產生一百份完全相同的位元組序列。

成本只是問題的一半。序列化器帶著一些每個 tick 的小型備忘（例如「這艘船自上個 tick 以來停下來了嗎？」，第 4.4 章），而一百條同時序列化同一艘船的執行緒，全都在同一時間寫入這些備忘。這是真正的資料競爭，只要每張地圖只有一位玩家就看不見，而每一次測試都是這樣。

Prepare sequentially, copy in parallel

The answer fits in one ordering. After the world has finished changing for the tick (chapter 3.2, section 7), each map serializes the block of each of its hulls and characters once, on its own tick thread, sequentially. The parallel build that follows only copies those bytes into each player's packet. The race disappears because the writes and the reads no longer overlap in time, and the cost goes from O(players × visible objects) to O(objects on the map).

Préparer en séquence, copier en parallèle

La réponse tient en un ordre. Une fois que le monde a fini de changer pour le tick (chapitre 3.2, section 7), chaque carte sérialise le bloc de chacune de ses coques et de chacun de ses personnages une fois, sur son propre thread de tick, en séquence. La construction parallèle qui suit ne fait plus que recopier ces octets dans le paquet de chaque joueur. La course disparaît parce que les écritures et les lectures ne se recouvrent plus dans le temps, et le coût passe de O(joueurs × objets visibles) à O(objets de la carte).

循序準備，平行複製

答案就在一個順序裡。在世界於這個 tick 中不再改變之後（第 3.2 章，第 7 區段），每張地圖在自己的 tick 執行緒上，依序把每個船體與角色的區塊序列化一次。接下來的平行建構只負責把這些位元組複製到每位玩家的封包中。競爭條件消失了，因為寫入與讀取在時間上不再重疊，而成本也從 O(玩家 × 可見物件) 變成 O(地圖上的物件)。

WriteUVarInt((ulong)_others.Count);
foreach (var o in _others)
{
    WriteUVarInt(o.Id);
    Write(o.ObjectType);

    // The block already prepared for THIS tick, if any: copy it.
    if (o is ISnapshotBlockProvider provider)
    {
        if (provider.TryWriteSnapshotBlock(Tick, this)) { CachedBlockWrites++; continue; }
        UnpreparedBlocks++;  // expected to stay at zero
    }

    // Fallback: serialize directly. This runs in the PARALLEL loop, once per viewer,
    // so Marshal must be pure for every type that can reach it.
    ((IMarshalable)o).Marshal(this);
}

A block's validity is its tick number: a block prepared at tick N is used only by snapshots of tick N. There is no "dirty" flag to reset and no cache to invalidate each tick; last tick's blocks simply stop matching. The block is only explicitly invalidated when an object leaves a map or is recycled from a pool, so a reused object can never resurrect stale bytes.

Only hulls and characters use prepared blocks, deliberately. They are the ones that cost (a part list to walk) and the only ones with per-tick memos. A bullet, a piece of debris or an asteroid serializes in a few varints with no shared state; routing them through a cache would pay the copy and save nothing.

La validité d'un bloc est son numéro de tick : un bloc préparé au tick N ne sert qu'aux snapshots du tick N. Il n'y a aucun drapeau « sale » à remettre à zéro et aucun cache à invalider à chaque tick ; les blocs du tick précédent cessent simplement de correspondre. Un bloc n'est explicitement invalidé que quand un objet quitte une carte ou est recyclé depuis une réserve, pour qu'un objet réutilisé ne puisse jamais ressusciter des octets périmés.

Seuls les coques et les personnages utilisent des blocs préparés, délibérément. Ce sont eux qui coûtent (une liste de pièces à parcourir) et les seuls à porter des mémos par tick. Une balle, un débris ou un astéroïde se sérialise en quelques varints sans état partagé ; les faire passer par un cache paierait la recopie sans rien économiser.

區塊的有效性就是它的 tick 編號：在第 N 個 tick 準備的區塊，只會被第 N 個 tick 的快照使用。沒有需要重設的「髒」旗標，也沒有每個 tick 需要作廢的快取；上一個 tick 的區塊就只是不再相符而已。只有在物件離開地圖或從物件池中被回收時，區塊才會被明確作廢，所以被重複使用的物件永遠不可能讓過時的位元組復活。

只有船體與角色使用預先準備的區塊，這是刻意的。它們才是有成本的（要走訪零件清單），也是唯一帶有每個 tick 備忘的。子彈、碎片或小行星只要幾個 varint 就能序列化，而且沒有共用狀態；讓它們經過快取，只會付出複製的代價，什麼都省不到。

When preparing loses: an inequality, not a heuristic

The cache pays when the copies (V, the sum over players of the objects each one sees) exceed the preparations (P, all the hulls and characters of the map). With a single viewer, V is what that one player sees, so V ≤ P by definition: a player cannot see more objects than the map holds. Preparing is then a loss every time, and a bigger loss the larger the map is compared with the field of view. The first report that measured both sides said so plainly: 9 blocks prepared, 5 copied. Maps with fewer than two viewers therefore skip preparation and serialize directly.

Pitfall I hit

The first version of the counter reported the total number of objects per snapshot as "copies". But bullets, debris and asteroids never go through the cache. The report announced a gain four times larger than the real one. A flattering measurement is worse than none: it hides the day the cache stops paying. Copies are now counted inside the loop above, only when a prepared block is actually used.

Quand préparer perd : une inégalité, pas une heuristique

Le cache rapporte quand les recopies (V, la somme sur les joueurs des objets que chacun voit) dépassent les préparations (P, toutes les coques et tous les personnages de la carte). Avec un seul spectateur, V est ce que voit ce joueur, donc V ≤ P par définition : un joueur ne peut pas voir plus d'objets que la carte n'en contient. Préparer est alors perdant à tous les coups, et d'autant plus que la carte est grande par rapport au champ de vision. Le premier rapport qui a mesuré les deux côtés l'a dit en clair : 9 blocs préparés, 5 recopiés. Les cartes de moins de deux spectateurs sautent donc la préparation et sérialisent directement.

Piège rencontré

La première version du compteur rapportait le nombre total d'objets par snapshot comme des « recopies ». Or balles, débris et astéroïdes ne passent jamais par le cache. Le rapport annonçait un gain quatre fois supérieur au vrai. Une mesure qui flatte est pire qu'une mesure absente : elle cache le jour où le cache cesse de rapporter. Les recopies sont maintenant comptées dans la boucle ci-dessus, seulement quand un bloc préparé est réellement utilisé.

預先準備何時會虧：是不等式，不是經驗法則

當複製次數（V，所有玩家各自看到的物件數總和）超過準備次數（P，地圖上所有的船體與角色）時，快取才划算。只有一位觀察者時，V 就是那位玩家看到的物件數，所以依定義 V ≤ P：一位玩家不可能看到比地圖上更多的物件。這時預先準備每次都會虧，而且地圖相對於視野越大，虧得越多。第一份同時量測兩邊的報告說得很直白：準備了 9 個區塊，複製了 5 個。因此觀察者少於兩位的地圖會跳過預先準備，直接序列化。

我踩過的坑

計數器的第一版把每份快照的物件總數當成「複製次數」回報。但子彈、碎片與小行星從不經過快取。報告宣稱的收益是實際的四倍。一個奉承你的量測比沒有量測更糟：它會掩蓋快取不再划算的那一天。現在複製次數在上面的迴圈中計算，只在實際使用了預先準備的區塊時才計入。

The fallback path, direct serialization when no block was prepared for this tick, runs inside the parallel loop, once per viewer. And the ship's serializer began by recomputing its list of damaged hexes: clear a list, refill it, swap two references, bump a version number. Two viewers serializing the same unprepared ship at the same instant were enough. With forty players that is unlikely; with seven hundred it is a certainty every minute. The code had been there since the serialize-once change. The population was the revealer, not the cause.

But which objects reached the fallback, with preparation in place? Here is the gap. Preparation walks the map's own lists of hulls and characters. Snapshots read the published interest index, rebuilt earlier in the tick. Between the two runs the sequential "player deadlines" section, which removes objects from the map: a ship destroyed, a character who just sat down, a dead body picked up. Such an object is still in the index but has no block, so every one of its viewers falls back on serializing it, in parallel. It is probably also why a dead ship stayed on screen about two seconds before disappearing.

Measured

Three comments in the repository asserted the invariant that was being violated: "the damaged list is filled once per hull per tick, before the parallel phase"; "the viewer threshold is also the safety threshold"; "this separation in time, not a lock, is what makes the whole thing safe". All three were read as proof. None was checked by anything.

The fix was not a lock, which would have been paid on every object of every snapshot to cover a rare case. The serializer was made pure: it only reads what the last preparation left. The damaged-hex list is absolute (chapter 4.4), so a list one tick old is a truth one tick old that the next tick replaces entirely, never a cumulative inconsistency. Where the pure path cannot know whether the ship moved this tick, it answers "yes, send the position": sending an unnecessary position costs twelve bytes, not sending a needed one freezes a ship on screen. And the fallback is now counted, per snapshot, with zero as the expected value.

Rule

A comment that describes an invariant does not hold it.

If a property matters, enforce it in the code's shape (a pure function cannot mutate) or measure it (a counter that should be zero), and treat the comment as documentation of the enforcement, not as the enforcement.

Le chemin de repli, la sérialisation directe quand aucun bloc n'a été préparé pour ce tick, tourne dans la boucle parallèle, une fois par spectateur. Et le sérialiseur du vaisseau commençait par recalculer sa liste d'hex abîmés : vider une liste, la remplir, échanger deux références, incrémenter un numéro de version. Deux spectateurs sérialisant le même vaisseau non préparé au même instant suffisaient. À quarante joueurs c'est improbable ; à sept cents, c'est une certitude à chaque minute. Le code était là depuis la sérialisation-une-fois. La population était le révélateur, pas la cause.

Mais quels objets atteignaient le repli, la préparation étant en place ? Voici l'écart. La préparation parcourt les listes propres à la carte, coques et personnages. Les snapshots lisent l'index d'intérêt publié, reconstruit plus tôt dans le tick. Entre les deux passe la section séquentielle des « échéances joueurs », qui retire des objets de la carte : un vaisseau détruit, un personnage qui vient de s'asseoir, un corps relevé. Un tel objet est encore dans l'index mais n'a pas de bloc : chacun de ses spectateurs retombe sur sa sérialisation, en parallèle. C'est probablement aussi pourquoi un vaisseau mort restait environ deux secondes à l'écran avant de disparaître.

Mesuré

Trois commentaires du dépôt affirmaient l'invariant qui était violé : « la liste des abîmés est remplie une fois par coque et par tick, avant la phase parallèle » ; « le seuil de spectateurs est aussi celui de la sûreté » ; « c'est cette séparation dans le temps, pas un verrou, qui rend l'ensemble sûr ». Les trois se relisaient comme une preuve. Aucun n'était vérifié par quoi que ce soit.

La correction n'a pas été un verrou, qui se serait payé à chaque objet de chaque snapshot pour couvrir un cas rare. Le sérialiseur a été rendu pur : il ne fait que lire ce que la dernière préparation a laissé. La liste des hex abîmés est absolue (chapitre 4.4) : une liste d'un tick de retard est une vérité d'un tick de retard, que le tick suivant remplace en entier, jamais une incohérence cumulative. Là où le chemin pur ne peut pas savoir si le vaisseau a bougé à ce tick, il répond « oui, envoie la position » : envoyer une position inutile coûte douze octets, ne pas envoyer une position nécessaire fige un vaisseau à l'écran. Et le repli est maintenant compté, par snapshot, avec zéro comme valeur attendue.

Règle

Un commentaire qui décrit un invariant ne le tient pas.

Si une propriété compte, l'imposer par la forme du code (une fonction pure ne peut pas muter) ou la mesurer (un compteur qui devrait valoir zéro), et traiter le commentaire comme la documentation de ce mécanisme, pas comme le mécanisme.

後備路徑——當這個 tick 沒有準備區塊時的直接序列化——在平行迴圈中執行，每位觀察者一次。而船艦的序列化器一開始會重新計算它的受損六角格清單：清空一個清單、重新填入、交換兩個參考、遞增一個版本號。只要兩位觀察者在同一瞬間序列化同一艘沒被準備的船就夠了。四十位玩家時這不太可能發生；七百位時，每分鐘都必然發生。這段程式碼從「序列化一次」的變更起就一直在那裡。人口數是揭露者，而不是原因。

但在預先準備已經就位的情況下，哪些物件會走到後備路徑？缺口在這裡。預先準備走訪的是地圖自己的船體與角色清單。快照讀取的則是已發布的興趣索引，它在 tick 中更早就重建好了。在這兩者之間，執行的是循序的「玩家期限」區段，它會從地圖中移除物件：一艘被摧毀的船、一個剛坐下的角色、一具被撿起的屍體。這樣的物件仍然在索引中，卻沒有區塊，所以它的每一位觀察者都會退回去平行地序列化它。這大概也是為什麼一艘死掉的船會在畫面上停留約兩秒才消失。

實測

程式庫中有三則註解宣稱著那個正被違反的不變條件：「受損清單在平行階段之前，每個船體每個 tick 填入一次」；「觀察者門檻同時也是安全門檻」；「讓整件事安全的是時間上的分離，而不是鎖」。三則都被當成了證明。沒有一則被任何東西檢查過。

修正方式不是鎖，鎖的代價會落在每份快照的每個物件上，只為了涵蓋一個罕見的情況。序列化器被改成純函式：它只讀取上一次準備留下的東西。受損六角格清單是絕對的（第 4.4 章），所以舊了一個 tick 的清單，就是舊了一個 tick 的真相，下一個 tick 會把它完全取代，而絕不會是一種累積性的不一致。當純路徑無法知道船在這個 tick 是否移動過時，它會回答「是，送出位置」：送出一個不必要的位置只花十二個位元組，不送出一個需要的位置則會讓船凍結在畫面上。而後備路徑現在會被計數，每份快照一次，期望值是零。

規則

描述不變條件的註解，並不能守住它。

如果某個特性很重要，就用程式碼的形狀來強制它（純函式無法修改東西），或量測它（一個應該為零的計數器），並把註解當成強制機制的說明文件，而不是強制機制本身。

The bug nobody introduced

Two correct changes, each justified on its own, combined into a bug that only appeared when playing alone:

  1. "Only prepare when it can pay" added the two-viewer threshold, which returns before the preparation loop.
  2. "Make the fallback pure" (the 780-player fix) removed the fallback's right to recompute anything.

Together they removed both places where the damaged-hex list was built. With a single viewer, the list stayed empty. An empty list on the wire means "no damaged hex: restore this hull to full", so the server applied damage and then repaired the client's health bars 25 times a second. The symptom: "I shoot, the damage numbers appear, the health does not go down", only in solo. With two players, preparation kicked in and everything worked, which is exactly why nobody saw it in multiplayer tests.

The collection of per-tick state now runs unconditionally for every hull, before the threshold. The threshold went back to being what it should always have been: a cost decision, and nothing else.

Rule

Never let game state depend on a performance decision.

A cache may be skipped, a phase may be parallel or not, a threshold may change; what the game says about the world must be the same on every path. If a performance switch can change the outcome, the state is living in the wrong place.

Le bug que personne n'a introduit

Deux changements justes, chacun justifié de son côté, se sont combinés en un bug qui n'apparaissait qu'en jouant seul :

  1. « Ne préparer que quand ça peut rapporter » a ajouté le seuil de deux spectateurs, qui sort avant la boucle de préparation.
  2. « Rendre le repli pur » (la correction des 780 joueurs) a retiré au repli le droit de recalculer quoi que ce soit.

Ensemble, ils ont supprimé les deux seuls endroits où la liste des hex abîmés était construite. Avec un seul spectateur, la liste restait vide. Une liste vide sur le fil veut dire « aucun hex abîmé : remets cette coque à neuf » : le serveur appliquait les dégâts puis réparait les barres de vie du client 25 fois par seconde. Le symptôme : « je tire, les chiffres de dégâts s'affichent, la vie ne descend pas », seulement en solo. À deux joueurs, la préparation se déclenchait et tout marchait, ce qui explique exactement pourquoi personne ne l'a vu en test multijoueur.

La collecte de l'état par tick tourne maintenant sans condition pour chaque coque, avant le seuil. Le seuil est redevenu ce qu'il aurait toujours dû être : une décision de coût, et rien d'autre.

Règle

Ne jamais faire dépendre l'état du jeu d'une décision de performance.

Un cache peut être sauté, une phase peut être parallèle ou non, un seuil peut changer ; ce que le jeu dit du monde doit être le même sur tous les chemins. Si un interrupteur de performance peut changer le résultat, l'état vit au mauvais endroit.

沒有人引入的 bug

兩個各自都有充分理由的正確變更，組合成一個只在單人遊玩時才出現的 bug：

  1. 「只在划算時才預先準備」加入了兩位觀察者的門檻，會在準備迴圈之前就返回。
  2. 「讓後備路徑變成純函式」（780 名玩家的修正）拿掉了後備路徑重新計算任何東西的權利。

兩者合在一起，拿掉了建立受損六角格清單的兩個地方。只有一位觀察者時，清單一直是空的。線路上的空清單代表「沒有受損的六角格：把這個船體恢復到全滿」，所以伺服器施加了傷害，接著又每秒 25 次修好用戶端的生命條。症狀是：「我開火，傷害數字出現了，生命值卻沒有下降」，而且只在單人時發生。兩位玩家時，預先準備就會啟動，一切正常，這正是為什麼在多人測試中沒有人看到它。

現在每個 tick 狀態的收集會在門檻之前，無條件地為每個船體執行。門檻回到了它本來就該有的樣子：一個成本決策，僅此而已。

規則

絕不讓遊戲狀態依賴於一個效能決策。

快取可以被跳過、一個階段可以平行或不平行、門檻可以改變；遊戲對世界的描述，在每條路徑上都必須相同。如果一個效能開關能改變結果，狀態就放錯地方了。

Key takeaways

  • An object's bytes are the same for all its viewers: serialize once per tick, then copy.
  • Prepare sequentially after all mutation, and make the parallel phase read-only; date blocks by tick instead of invalidating them.
  • Cache only what is expensive and stateful, and decide when to prepare from the inequality copies > preparations.
  • Make every fallback that runs in parallel pure, and count how often it runs.
  • Keep game state independent of performance switches, and do not trust comments to hold invariants.

À retenir

  • Les octets d'un objet sont les mêmes pour tous ses spectateurs : sérialiser une fois par tick, puis recopier.
  • Préparer en séquence après toutes les mutations, et rendre la phase parallèle en lecture seule ; dater les blocs par tick au lieu de les invalider.
  • Ne mettre en cache que ce qui est coûteux et porte un état, et décider quand préparer à partir de l'inégalité recopies > préparations.
  • Rendre pur tout repli qui tourne en parallèle, et compter combien de fois il tourne.
  • Garder l'état du jeu indépendant des interrupteurs de performance, et ne pas compter sur des commentaires pour tenir des invariants.

重點整理

  • 一個物件的位元組對它所有的觀察者都相同：每個 tick 序列化一次，然後複製。
  • 在所有修改之後循序準備，讓平行階段只讀；以 tick 為區塊標上日期，而不是逐一作廢。
  • 只快取昂貴且帶狀態的東西，並根據「複製次數 > 準備次數」這個不等式決定何時準備。
  • 讓每一條平行執行的後備路徑都是純函式，並計算它執行的次數。
  • 讓遊戲狀態獨立於效能開關，也不要指望註解能守住不變條件。

Why a front door at all

The first version of any online game has one server that does everything. As soon as the world is split across several game servers, a question appears that none of them can answer alone: which server should this player talk to? Answering it requires knowing every server, every map they host, and every player online. That knowledge belongs in one place, and in MoonQwak that place is the gateway.

The gateway is deliberately boring. It simulates nothing and holds no physics. It owns accounts and characters (in the database), sessions and presence (in memory), the social features that span maps, the decision of which server hosts which map, and the number of servers each world needs. Because it does not simulate, it can stay up while game servers start, crash and retire around it.

Pourquoi une porte d'entrée

La première version de tout jeu en ligne a un serveur qui fait tout. Dès que le monde est réparti sur plusieurs serveurs de jeu, une question apparaît à laquelle aucun d'eux ne peut répondre seul : à quel serveur ce joueur doit-il parler ? Y répondre demande de connaître chaque serveur, chaque carte qu'il héberge et chaque joueur en ligne. Cette connaissance doit vivre à un seul endroit, et dans MoonQwak cet endroit est la gateway.

La gateway est volontairement ennuyeuse. Elle ne simule rien et ne porte aucune physique. Elle possède les comptes et les personnages (en base), les sessions et la présence (en mémoire), les fonctions sociales qui traversent les cartes, la décision de quel serveur héberge quelle carte, et le nombre de serveurs dont chaque monde a besoin. Comme elle ne simule pas, elle peut rester debout pendant que les serveurs de jeu démarrent, plantent et se retirent autour d'elle.

為什麼需要一扇大門

任何線上遊戲的第一版，都是一台伺服器包辦一切。一旦世界被拆到好幾台遊戲伺服器上，就會出現一個沒有任何一台能獨自回答的問題：這位玩家應該和哪台伺服器溝通？要回答它，就得知道每一台伺服器、它們託管的每一張地圖，以及每一位在線的玩家。這份知識應該放在同一個地方，而在 MoonQwak 中，那個地方就是閘道。

閘道刻意設計得很無聊。它不模擬任何東西，也沒有物理。它擁有帳號與角色（在資料庫中）、連線階段與上線狀態（在記憶體中）、跨越地圖的社交功能、哪台伺服器託管哪張地圖的決定，以及每個世界需要幾台伺服器。正因為它不做模擬，所以能在周圍的遊戲伺服器啟動、當機、退役時持續運作。

Trade-off

A single gateway is a single point of failure, and it holds live state that is lost when it restarts: every session, every group, the map-to-server table. Game servers reconnect and re-authenticate on their own, but players must log in again. The right fix is a resynchronization (servers re-announcing the sessions they carry) rather than persisting groups and sessions; it has not been built or tested yet, and it is on the open problems list.

Compromis

Une gateway unique est un point de défaillance unique, et elle tient un état vivant perdu à son redémarrage : chaque session, chaque groupe, la table cartes-serveurs. Les serveurs de jeu se reconnectent et se réauthentifient seuls, mais les joueurs doivent se reconnecter. La bonne correction est une resynchronisation (les serveurs réannonçant les sessions qu'ils portent) plutôt que de persister groupes et sessions ; elle n'est ni écrite ni testée, et figure dans les problèmes ouverts.

取捨

單一閘道就是單一故障點，而且它持有重新啟動時會遺失的即時狀態：每個連線階段、每個隊伍、地圖對伺服器的對照表。遊戲伺服器會自行重新連線並重新認證，但玩家必須重新登入。正確的修正方式是重新同步（由伺服器重新宣告它們所承載的連線階段），而不是把隊伍與連線階段持久化；這還沒有實作也沒有測試，列在待解問題清單上。

Two doors, two audiences

The gateway opens two listeners on two ports: one for players, one for game servers. Each listener registers only the handlers its audience may call. A player cannot send a map-assignment result, because the client port does not know that packet; a game server cannot send a login. There is no if (sender is a server) check to forget, because the question never arises.

Deux portes, deux publics

La gateway ouvre deux écoutes sur deux ports : un pour les joueurs, un pour les serveurs de jeu. Chaque écoute n'enregistre que les gestionnaires que son public a le droit d'appeler. Un joueur ne peut pas envoyer un résultat d'assignation de carte, parce que le port client ne connaît pas ce paquet ; un serveur de jeu ne peut pas envoyer un login. Il n'y a pas de test if (l'expéditeur est un serveur) à oublier, parce que la question ne se pose jamais.

Sur le port client, l'authentification découle du type du paquet. Les paquets qui exigent une session dérivent d'AuthenticatedPacket, et l'utilitaire d'enregistrement vérifie automatiquement le jeton pour exactement ces types, avant le gestionnaire :

兩扇門，兩群對象

閘道在兩個埠上開啟兩個監聽器：一個給玩家，一個給遊戲伺服器。每個監聽器只註冊它的對象可以呼叫的處理常式。玩家無法送出地圖指派結果，因為用戶端的埠根本不認得那個封包；遊戲伺服器也無法送出登入請求。沒有任何 if (sender is a server) 的檢查會被遺忘，因為這個問題根本不會出現。

在用戶端的埠上，認證由封包類型推導而來。需要連線階段的封包衍生自 AuthenticatedPacket，而註冊輔助函式會在處理常式執行之前，自動為恰好這些類型檢查權杖：

Gateway/ClientGateway.cs
private void Register<T>(ushort type, Func<int, T, Server, bool> handler) where T : BasePacket, new()
{
    // Decided once, from the type: a new authenticated packet is protected the day it is added.
    bool needsAuth = typeof(AuthenticatedPacket).IsAssignableFrom(typeof(T));

    _server.Dispatcher.Register<T>(type, (peerId, packet, source) =>
    {
        var server = (Server)source;
        if (needsAuth && packet is AuthenticatedPacket auth
            && _sessions.Validate(peerId, auth.SessionToken) == null)  // token must belong to THIS connection
        {
            server.Send(peerId, new ErrorResult(Code.LoginRequired));
            return false;
        }
        return handler(peerId, (T)packet, server);
    });
}

Note the second argument of Validate: a token is accepted only from the connection that logged in. A token copied to another connection is useless there.

Remarquez le second argument de Validate : un jeton n'est accepté que depuis la connexion qui s'est authentifiée. Un jeton copié sur une autre connexion n'y sert à rien.

注意 Validate 的第二個參數：權杖只有從登入的那條連線送來時才會被接受。被複製到另一條連線的權杖，在那裡毫無用處。

How a game server proves who it is

Game servers connect to the gateway like any other peer, over the same encrypted transport. Then they must prove they are part of the fleet, because a registered server is trusted with a lot: it is told which maps to host and receives players.

Each machine that may run game servers has an RSA key pair. The private key stays on the machine; the public key is a file on the gateway, named after the machine. When a server starts, it announces its identity, address, port and a timestamp, and signs that announcement with the machine's private key. The gateway looks up the public key by machine name and verifies the signature. A wrong or missing key means the server is refused.

Comment un serveur de jeu prouve qui il est

Les serveurs de jeu se connectent à la gateway comme n'importe quel pair, sur le même transport chiffré. Ensuite, ils doivent prouver qu'ils font partie du parc, parce qu'un serveur enregistré reçoit beaucoup de confiance : on lui dit quelles cartes héberger et on lui envoie des joueurs.

Chaque machine autorisée à faire tourner des serveurs de jeu a une paire de clés RSA. La clé privée reste sur la machine ; la clé publique est un fichier sur la gateway, nommé d'après la machine. Au démarrage, un serveur annonce son identité, son adresse, son port et un horodatage, et signe cette annonce avec la clé privée de la machine. La gateway retrouve la clé publique par le nom de machine et vérifie la signature. Une clé fausse ou absente, et le serveur est refusé.

遊戲伺服器如何證明自己的身分

遊戲伺服器像其他端點一樣，透過同樣的加密傳輸連上閘道。接著它們必須證明自己是叢集的一員，因為已註冊的伺服器會被賦予很多信任：它會被告知要託管哪些地圖，並接收玩家。

每台可以執行遊戲伺服器的機器都有一組 RSA 金鑰對。私密金鑰留在機器上；公開金鑰則是閘道上一個以機器名稱命名的檔案。伺服器啟動時，會宣告自己的身分、位址、埠與時間戳記，並用機器的私密金鑰為這份宣告簽章。閘道依機器名稱查出公開金鑰並驗證簽章。金鑰錯誤或缺少，伺服器就會被拒絕。

Gateway/GameServerGateway.cs · the GameServerAuth handler, simplified
// Servers are started on demand as "MACHINE#index": the key belongs to the MACHINE.
var hash = auth.ServerId.IndexOf('#');
var machine = hash > 0 ? auth.ServerId.Substring(0, hash) : auth.ServerId;

if (!_publicKeys.TryGetValue(machine, out var rsa))
    return Refuse(peerId, $"no public key for machine '{machine}'");

var signed = Encoding.UTF8.GetBytes(auth.ServerId + auth.ServerIp + auth.ServerPort + auth.Timestamp);
if (!rsa.VerifyData(signed, auth.Signature, HashAlgorithmName.SHA256, RSASignaturePadding.Pkcs1))
    return Refuse(peerId, "signature verification failed");

_gameServers[peerId] = new GameServerInfo { ServerId = auth.ServerId, Ip = auth.ServerIp,
                                            Port = auth.ServerPort, WorldId = auth.WorldId };
server.Send(peerId, new GameServerAuthResult(Code.Success));
RetryPendingAssigns();  // maps that were waiting for a host get a second chance now

The key belongs to the machine, not to the server process, and that was forced by the fleet design. Game servers are now started on demand by a node agent (chapter 7.3), so a server's identity does not exist until it is started: there was never going to be a way to hand out one key per server. The invariant that mattered survives: a row in a database table is not enough to join the fleet. Only possession of the machine's private key is.

The last line of the handler matters for scaling: when a new server announces itself, the gateway immediately replays every map that was waiting for a host. Chapter 7.1 explains that waiting room.

La clé appartient à la machine, pas au processus serveur, et c'est la conception du parc qui l'a imposé. Les serveurs de jeu sont désormais lancés à la demande par un agent de machine (chapitre 7.3) : l'identité d'un serveur n'existe pas avant son lancement, il n'aurait jamais été possible de distribuer une clé par serveur. L'invariant qui comptait survit : une ligne dans une table ne suffit pas pour entrer dans le parc. Seule la possession de la clé privée de la machine le permet.

La dernière ligne du gestionnaire compte pour la montée en charge : quand un nouveau serveur s'annonce, la gateway rejoue immédiatement chaque carte qui attendait un hôte. Le chapitre 7.1 explique cette salle d'attente.

金鑰屬於機器，而不屬於伺服器程序，這是叢集設計所逼出來的。遊戲伺服器現在是由節點代理程式按需啟動的（第 7.3 章），所以伺服器的身分在它啟動之前並不存在：本來就不可能為每台伺服器發一把金鑰。真正重要的不變條件仍然保留：資料庫表中的一列資料不足以加入叢集。只有持有機器的私密金鑰才行。

處理常式的最後一行對擴展很重要：當一台新伺服器宣告自己時，閘道會立刻重新處理每一張正在等待主機的地圖。第 7.1 章會解釋這個候位區。

Why the social layer lives here

A guild's members are spread over many maps, served by as many processes. A private message goes from a player on one server to a player on another. A group must know when its members go offline, not when they merely change map. None of this can be decided by a game server, which only sees its own maps. So the gateway is the authority for everything social: presence, chat routing, groups, friends, guilds.

The game server becomes a relay. A player's guild command reaches their game server, which forwards it to the gateway; the gateway decides, and the answer travels back down to every member concerned, through whichever server each one is on. The game server keeps authority only over the few gestures that need the world, such as checking that a player is standing at the right place before founding something.

Three habits keep this layer simple:

  • Indexes, never scans, on the message path. Presence is indexed by character id and by name when a session is created. Routing a whisper is a dictionary lookup, not a loop over everyone online.
  • Full state, idempotent. A guild state packet always carries the whole roster, and "guild id 0" means "no guild". Absence is a state, not a silence, so the client can reset its copy from any single message.
  • Rebuild, never forward. A relayed packet is parsed on the game server and a new one is built for the client. A parsed packet is in read mode, and asking it to serialize again throws (chapter 1.2).

Pourquoi le social vit ici

Les membres d'une guilde sont répartis sur de nombreuses cartes, servies par autant de processus. Un message privé part d'un joueur sur un serveur vers un joueur sur un autre. Un groupe doit savoir quand ses membres se déconnectent, pas quand ils changent simplement de carte. Rien de tout ça ne peut être décidé par un serveur de jeu, qui ne voit que ses cartes. La gateway est donc l'autorité pour tout le social : présence, routage du chat, groupes, amis, guildes.

Le serveur de jeu devient un relais. La commande de guilde d'un joueur arrive sur son serveur, qui la transmet à la gateway ; la gateway décide, et la réponse redescend vers chaque membre concerné, par le serveur sur lequel se trouve chacun. Le serveur de jeu ne garde l'autorité que sur les rares gestes qui ont besoin du monde, comme vérifier qu'un joueur se tient au bon endroit avant de fonder quelque chose.

Trois habitudes gardent cette couche simple :

  • Des index, jamais de parcours, sur le chemin d'un message. La présence est indexée par identifiant de personnage et par nom à la création de la session. Router un message privé, c'est une recherche dans un dictionnaire, pas une boucle sur tous les connectés.
  • L'état complet, idempotent. Un paquet d'état de guilde porte toujours toute la liste des membres, et « guilde 0 » veut dire « pas de guilde ». L'absence est un état, pas un silence : le client peut réinitialiser sa copie à partir de n'importe quel message.
  • Reconstruire, jamais transférer. Un paquet relayé est parsé sur le serveur de jeu et un nouveau est construit pour le client. Un paquet parsé est en mode lecture, et lui demander de se resérialiser lève une exception (chapitre 1.2).

為什麼社交層放在這裡

一個公會的成員分散在許多地圖上，由同樣多的程序服務。一則私訊從一台伺服器上的玩家送到另一台伺服器上的玩家。一個隊伍必須知道成員何時下線，而不是只是換了地圖。這些都不能由遊戲伺服器決定，因為它只看得到自己的地圖。所以閘道是一切社交事務的權威：上線狀態、聊天路由、隊伍、好友、公會。

遊戲伺服器變成了中繼站。玩家的公會指令到達他所在的遊戲伺服器，由它轉送給閘道；閘道做出決定，答覆再經由每位相關成員各自所在的伺服器，傳回給每一位成員。遊戲伺服器只對少數需要世界資訊的動作保有權威，例如在創立某樣東西之前，檢查玩家是否站在正確的位置。

有三個習慣讓這一層保持簡單：

  • 訊息路徑上只用索引，從不掃描。上線狀態在連線階段建立時，就依角色 ID 與名稱建立索引。路由一則密語是一次字典查詢，而不是在所有在線者之間跑迴圈。
  • 完整狀態，具冪等性。公會狀態封包永遠攜帶完整的名冊，而「公會 ID 0」代表「沒有公會」。缺席是一種狀態，而不是沉默，所以用戶端可以從任何一則訊息重設自己的副本。
  • 重新建立，絕不轉送。被中繼的封包在遊戲伺服器上解析，再為用戶端建立一個新的。解析過的封包處於讀取模式，要求它再序列化一次會拋出例外（第 1.2 章）。

Rule

The authority for a feature is the process that can see all of it.

A guild spans servers, so only the gateway can decide about it. A docking bay is in one map, so only that map's server can. When the data a decision needs is spread over several processes, move the decision, not the data.

Règle

L'autorité sur une fonctionnalité est le processus qui peut la voir en entier.

Une guilde s'étend sur plusieurs serveurs, donc seule la gateway peut en décider. Une baie d'amarrage est dans une carte, donc seul le serveur de cette carte le peut. Quand les données dont une décision a besoin sont réparties sur plusieurs processus, déplacer la décision, pas les données.

規則

一項功能的權威，是能看見它全貌的那個程序。

公會跨越多台伺服器，所以只有閘道能為它做決定。停靠艙位於單一地圖中，所以只有那張地圖的伺服器能做決定。當一項決定所需的資料分散在好幾個程序中時，移動的是決定，而不是資料。

A slow console is an outage

Pitfall I hit

The gateway wrote about fifteen log lines for every player who connected, synchronously, from its network thread: the same thread that answers the game servers' session checks and relays map transitions. With five hundred bots arriving, that was seven thousand kernel calls on the critical path of authentication, each holding a process-wide lock. A console that scrolls, a large scrollback, or someone selecting text with the mouse in the console window (which pauses writes until the next click on Windows), and authentication stopped for everyone.

The fix, shared by all server processes: standard output is replaced at the very start of Main by a writer that queues the line and returns. A low-priority thread writes to the real console. The queue is bounded, keeps the order, counts what it had to drop and says so, and is drained when the process exits so the last lines before a crash are not lost. Noisy per-player prefixes can be muted by configuration. Chapter 10.1 gives the details.

Une console lente est une panne

Piège rencontré

La gateway écrivait une quinzaine de lignes de journal pour chaque joueur qui se connectait, en synchrone, depuis son thread réseau : le même thread qui répond aux vérifications de session des serveurs de jeu et relaie les transitions de carte. Avec cinq cents robots qui arrivaient, ça faisait sept mille appels noyau sur le chemin critique de l'authentification, chacun tenant un verrou global au processus. Une console qui défile, un gros historique, ou quelqu'un qui sélectionne du texte à la souris dans la fenêtre (ce qui suspend les écritures jusqu'au clic suivant sous Windows), et l'authentification s'arrêtait pour tout le monde.

La correction, partagée par tous les processus serveur : la sortie standard est remplacée dès le début de Main par un writer qui met la ligne en file et rend la main. Un thread de faible priorité écrit sur la vraie console. La file est bornée, garde l'ordre, compte ce qu'elle a dû jeter et le dit, et se vide à l'arrêt du processus pour ne pas perdre les dernières lignes avant un plantage. Les préfixes bavards par joueur peuvent être rendus muets par configuration. Le chapitre 10.1 donne les détails.

緩慢的主控台就是一次停機

我踩過的坑

閘道會為每一位連線的玩家寫大約十五行日誌，而且是從它的網路執行緒同步寫入：正是這條執行緒負責回應遊戲伺服器的連線階段檢查，並中繼地圖切換。五百個機器人同時抵達時，就是在認證的關鍵路徑上進行七千次核心呼叫，每一次都持有一個程序層級的鎖。只要主控台在捲動、捲動緩衝區很大，或有人在主控台視窗中用滑鼠選取文字（在 Windows 上這會暫停寫入，直到下一次點擊），所有人的認證就都停住了。

所有伺服器程序共用的修正：在 Main 一開始，就把標準輸出換成一個把那一行排入佇列後立即返回的寫入器。一條低優先權的執行緒負責寫到真正的主控台。佇列有上限、保持順序、計算它不得不丟棄的數量並說出來，而且在程序結束時會被清空，所以當機前的最後幾行不會遺失。吵雜的每位玩家前綴可以透過設定關閉。第 10.1 章有詳細說明。

Key takeaways

  • A gateway exists to answer "where should this player go?", which no single game server can.
  • Separate listeners for players and servers make whole classes of permission checks unnecessary.
  • Derive authentication from the packet type, and bind session tokens to the connection that logged in.
  • Servers join the fleet by signing their announcement with their machine's private key.
  • The authority for a feature is the process that sees all of it; for social features that is the gateway.

À retenir

  • Une gateway existe pour répondre à « où doit aller ce joueur ? », ce qu'aucun serveur de jeu ne peut faire seul.
  • Des écoutes séparées pour les joueurs et les serveurs rendent inutiles des catégories entières de vérifications de droits.
  • Déduire l'authentification du type du paquet, et lier les jetons de session à la connexion qui s'est authentifiée.
  • Les serveurs entrent dans le parc en signant leur annonce avec la clé privée de leur machine.
  • L'autorité sur une fonctionnalité est le processus qui la voit en entier ; pour le social, c'est la gateway.

重點整理

  • 閘道的存在，是為了回答「這位玩家該去哪裡？」，這是任何一台遊戲伺服器都無法單獨回答的。
  • 為玩家與伺服器分別設置監聽器，讓一整類的權限檢查變得不必要。
  • 由封包類型推導認證，並把連線階段權杖綁定在登入的那條連線上。
  • 伺服器以所在機器的私密金鑰為宣告簽章，藉此加入叢集。
  • 一項功能的權威，是能看見它全貌的那個程序；對社交功能來說，那就是閘道。

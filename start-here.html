What these notes are

MoonQwak is a top-down space game whose ships are built out of hexagonal parts, and an ongoing project built by one developer, self-taught in MMO architecture, to find out how far one person can go. Behind the game sits a server architecture inspired by what large online games are known to use: a gateway, many game servers, a fleet of machines that sizes itself, a database used as a journal, and a launcher that patches the client. These notes describe how that architecture was built, the problems it ran into, and the decisions that came out of them. They are shared for educational purposes: my choices, not the way it must be done (see About this project).

It is not a recipe. Most chapters describe one problem, the options I considered, what I chose, and what the measurements said afterwards. Several of the choices were wrong the first time, and those stories are kept in, because the wrong turn is usually where the lesson is. When a number appears, it comes from a real measurement on this project, usually a load test with hundreds of bot clients. Those tests ran on a single development machine, so read the absolute figures as orders of magnitude and the before/after ratios as the real information.

The game itself barely appears. Ships, bullets and maps show up in the examples because they are what the server moves around, but every chapter is about architecture: how bytes travel, how a world advances in time, what each player is told, how data stays consistent, and how the whole thing runs on more than one machine.

Three ideas that shaped everything

1. The server decides, on a fixed clock

An MMO server is authoritative. The client sends intentions (keys held, where the mouse points, "I want to dock") and the server decides what actually happens. The world advances in fixed steps called ticks, 25 per second here, and every decision happens inside one of them. Almost every chapter is a consequence of this: the tick has a time budget (40 ms), nothing inside it may wait for anything slow, and what players see is a copy of the server's state sent after each tick.

2. Shapes versus constants

An optimization is either a constant or a shape. A constant is a function that is twice too slow, an allocation that could be avoided: you fix it locally when a measurement shows it hurts, and waiting costs nothing. A shape is O(players × objects) work, a global lock on a parallel path, a collection that mixes three hundred bullets with four ships. Shapes get built into the architecture, other code starts depending on them, and changing them later costs ten times more. "It's cheap today" is a fine argument for a constant and a bad one for a shape: with three objects on screen, nothing is expensive.

3. Measure before you believe, including your instruments

The most expensive lessons in this project came from reading a number that did not measure what its label said: a "tick duration" that was really the interval between ticks, a "pre-step" timer that included three other phases, a profiler that only fired on abnormal ticks. Chapter 10.1 is entirely about this. The short version: build the instrument before the optimization, and check that two numbers measure the same thing before you look for the difference between them.

Trois idées qui ont tout façonné

1. Le serveur décide, sur une horloge fixe

Un serveur de MMO fait autorité. Le client envoie des intentions (touches enfoncées, direction de la souris, « je veux m'amarrer ») et le serveur décide de ce qui se passe réellement. Le monde avance par pas fixes appelés ticks, 25 par seconde ici, et chaque décision se prend à l'intérieur de l'un d'eux. Presque chaque chapitre en découle : le tick a un budget de temps (40 ms), rien à l'intérieur n'a le droit d'attendre quoi que ce soit de lent, et ce que voient les joueurs est une copie de l'état du serveur envoyée après chaque tick.

2. Les formes contre les constantes

Une optimisation est soit une constante, soit une forme. Une constante, c'est une fonction deux fois trop lente, une allocation évitable : on la corrige localement quand une mesure montre qu'elle fait mal, et attendre ne coûte rien. Une forme, c'est un travail en O(joueurs × objets), un verrou global sur un chemin parallèle, une collection qui mélange trois cents balles et quatre vaisseaux. Les formes se coulent dans l'architecture, du code finit par en dépendre, et les changer plus tard coûte dix fois plus. « Ce n'est pas cher aujourd'hui » est un bon argument pour une constante et un mauvais pour une forme : avec trois objets à l'écran, rien n'est cher.

3. Mesurer avant de croire, y compris ses instruments

Les leçons les plus chères de ce projet sont venues de chiffres qui ne mesuraient pas ce que disait leur étiquette : une « durée de tick » qui était en fait l'intervalle entre deux ticks, un chronomètre « pre-step » qui englobait trois autres phases, un profileur qui ne se déclenchait que sur les ticks anormaux. Le chapitre 10.1 ne parle que de ça. En bref : construire l'instrument avant l'optimisation, et vérifier que deux nombres mesurent la même chose avant de chercher l'écart entre eux.

Rule

Fix constants when a measurement says they hurt. Fix shapes before anything depends on them.

An O(n²) loop or a global lock on a parallel path is invisible with three test objects and fatal with four hundred. Waiting for proof is fine for a slow function, not for a structure other code will be built on.

Règle

Corriger les constantes quand une mesure dit qu'elles font mal. Corriger les formes avant que quoi que ce soit n'en dépende.

Une boucle en O(n²) ou un verrou global sur un chemin parallèle est invisible avec trois objets de test et fatal avec quatre cents. Attendre une preuve convient à une fonction lente, pas à une structure sur laquelle on va bâtir.

The build order

If I started again, this is the order I would follow. Each stage ends with a concrete test. Moving on before that test passes is how a project ends up with a gateway before it has a working tick loop, or with six hundred players and no way to see where the time goes.

  1. A connection and a message. Pick a transport, frame typed packets, and dispatch them to handlers. Done when: two processes exchange typed messages, and a malformed packet costs one dropped packet instead of a crashed server. 1.1, 1.2, 1.5.
  2. Protect the protocol. Write round-trip tests for every packet, and a version number checked at login. This comes early on purpose: a field added on one side only is the most expensive bug in a hand-written protocol, and it gets more expensive with every packet you add. Done when: adding a packet without a test fails the build. 1.6.
  3. Identity. A gateway that registers, logs in and issues tokens, and game servers that prove who they are to the gateway. Done when: a client logs in, picks a character, and enters a game server with a token issued by the gateway. 2.1, 2.2.
  4. One authoritative world. A fixed-rate tick, one map, inputs in, snapshots out. Done when: two clients see each other move, the server decides everything, and the tick rate you configured is the rate you get. 3.1, 3.2, 4.2.
  5. Make it feel right. Interpolate remote objects, predict your own movement, reconcile with the server. Done when: remote ships look smooth at 25 snapshots a second and your own character responds instantly at 150 ms of round trip. 5.2, 5.3.
  6. Instruments and bots. A monitor that shows where each millisecond of the tick goes, and a load test that runs real clients. Earlier than feels necessary: every stage after this one is a performance question. Done when: you can start 100 bots and read the cost of each tick phase. 10.1, 10.3.
  7. Tell each player only what matters. Area of interest, serialization shared between viewers, deltas, a per-player budget. Done when: doubling the number of players on a map does not quadruple the bandwidth. Part 4.
  8. Durable, and never duplicated. Decide what lives in RAM and when it is written, and make every transfer of goods between players atomic. Done when: killing the server at any moment loses at most a minute of progress and never duplicates an item. Part 6.
  9. Many maps, then many servers. Load maps on demand, move players between processes, then let the fleet size itself. Done when: a player can cross from a map hosted on one process to a map hosted on another, and a new server appears when the existing ones are full. Parts 2.3 and 7.
  10. Ship it. An updater that downloads only what changed, and a launcher that can replace itself. Done when: a friend with a stale install gets the new build in one click. Part 8.

L'ordre de construction

Si je recommençais, voici l'ordre que je suivrais. Chaque étape se termine par un test concret. Passer à la suite avant que ce test ne passe, c'est comme ça qu'un projet se retrouve avec une gateway avant d'avoir une boucle de tick qui marche, ou avec six cents joueurs et aucun moyen de voir où passe le temps.

  1. Une connexion et un message. Choisir un transport, encadrer des paquets typés, les distribuer à des gestionnaires. Fini quand : deux processus échangent des messages typés, et un paquet malformé coûte un paquet perdu au lieu d'un serveur planté. 1.1, 1.2, 1.5.
  2. Protéger le protocole. Écrire des tests aller-retour pour chaque paquet, et un numéro de version vérifié au login. C'est tôt exprès : un champ ajouté d'un seul côté est le bug le plus cher d'un protocole écrit à la main, et il coûte plus cher à chaque paquet ajouté. Fini quand : ajouter un paquet sans test casse le build. 1.6.
  3. L'identité. Une gateway qui inscrit, connecte et délivre des jetons, et des serveurs de jeu qui prouvent leur identité à la gateway. Fini quand : un client se connecte, choisit un personnage et entre sur un serveur de jeu avec un jeton délivré par la gateway. 2.1, 2.2.
  4. Un monde autoritaire. Un tick à cadence fixe, une carte, des entrées qui arrivent, des snapshots qui partent. Fini quand : deux clients se voient bouger, le serveur décide de tout, et la cadence configurée est la cadence obtenue. 3.1, 3.2, 4.2.
  5. Rendre le jeu agréable. Interpoler les objets distants, prédire son propre mouvement, se réconcilier avec le serveur. Fini quand : les vaisseaux distants sont fluides à 25 snapshots par seconde et votre personnage répond instantanément avec 150 ms d'aller-retour. 5.2, 5.3.
  6. Instruments et robots. Un moniteur qui montre où passe chaque milliseconde du tick, et un banc de charge qui lance de vrais clients. Plus tôt que ça ne semble nécessaire : chaque étape suivante est une question de performance. Fini quand : vous lancez 100 robots et lisez le coût de chaque phase du tick. 10.1, 10.3.
  7. Ne dire à chaque joueur que ce qui compte. Zone d'intérêt, sérialisation partagée entre spectateurs, deltas, budget par joueur. Fini quand : doubler le nombre de joueurs sur une carte ne quadruple pas la bande passante. Partie 4.
  8. Durable, et jamais dupliqué. Décider de ce qui vit en RAM et quand c'est écrit, et rendre atomique chaque transfert de biens entre joueurs. Fini quand : tuer le serveur à n'importe quel moment perd au plus une minute de progression et ne duplique jamais un objet. Partie 6.
  9. Plusieurs cartes, puis plusieurs serveurs. Charger les cartes à la demande, déplacer les joueurs entre processus, puis laisser le parc se dimensionner. Fini quand : un joueur passe d'une carte hébergée par un processus à une carte hébergée par un autre, et un nouveau serveur apparaît quand les autres sont pleins. Parties 2.3 et 7.
  10. Livrer. Un système de mise à jour qui ne télécharge que ce qui a changé, et un launcher capable de se remplacer lui-même. Fini quand : un ami avec une vieille installation reçoit le nouveau build en un clic. Partie 8.

What to postpone

An MMO invites you to solve problems you do not have yet. These are the ones I deliberately left for later, and I would leave them for later again:

  • Splitting one map across several servers. Every map in MoonQwak lives in exactly one process. The limit this creates (how many players fit on one map) was measured at several hundred, and players spread over many maps anyway. Seamless world partitioning is a large project of its own, and it makes everything else harder.
  • Microservices. The architecture has a handful of processes, each with a clear owner for its data. More processes means more messages that can be lost, reordered or duplicated.
  • A custom physics engine. Box2D, driven carefully, handled 600 ships on one map. The problems were in how it was fed, not in the engine.
  • Clever compression before measuring. Two optimizations in this project were aimed at the wrong target because nobody had measured what the bytes were made of. A trace that breaks a snapshot down by object type came later than it should have.
  • A second database, a cache cluster, a message bus. One MySQL instance, used as a journal and never on the hot path, was enough. Chapter 6.1 explains the rule that makes that possible.

Ce qu'il faut repousser

Un MMO pousse à résoudre des problèmes qu'on n'a pas encore. Voici ceux que j'ai volontairement laissés pour plus tard, et que je laisserais encore pour plus tard :

  • Découper une carte sur plusieurs serveurs. Chaque carte de MoonQwak vit dans exactement un processus. La limite que ça crée (combien de joueurs tiennent sur une carte) a été mesurée à plusieurs centaines, et les joueurs se répartissent de toute façon sur beaucoup de cartes. Le partitionnement continu du monde est un gros projet à lui seul, et il complique tout le reste.
  • Les microservices. L'architecture compte une poignée de processus, chacun propriétaire clair de ses données. Plus de processus, c'est plus de messages qui peuvent se perdre, arriver dans le désordre ou en double.
  • Un moteur physique maison. Box2D, bien alimenté, a tenu 600 vaisseaux sur une carte. Les problèmes venaient de la façon de le nourrir, pas du moteur.
  • Une compression astucieuse avant de mesurer. Deux optimisations de ce projet visaient la mauvaise cible parce que personne n'avait mesuré de quoi étaient faits les octets. Une trace qui décompose un snapshot par type d'objet est arrivée plus tard qu'elle n'aurait dû.
  • Une seconde base, un cluster de cache, un bus de messages. Une seule instance MySQL, utilisée comme journal et jamais sur le chemin chaud, a suffi. Le chapitre 6.1 explique la règle qui le permet.

Key takeaways

  • Build in the order that lets you test each stage: connection, protocol tests, identity, one world, feel, instruments, interest, durability, scale, shipping.
  • Put protocol tests and instruments early. Both get more expensive to add with every feature built before them.
  • Treat structural costs (shapes) differently from local slowness (constants).
  • Postpone map partitioning, microservices and speculative compression until a measurement asks for them.

À retenir

  • Construire dans l'ordre qui permet de tester chaque étape : connexion, tests du protocole, identité, un monde, ressenti, instruments, intérêt, durabilité, échelle, livraison.
  • Mettre les tests du protocole et les instruments tôt. Les deux coûtent plus cher à ajouter à chaque fonctionnalité bâtie avant eux.
  • Traiter les coûts structurels (les formes) autrement que les lenteurs locales (les constantes).
  • Repousser le partitionnement des cartes, les microservices et la compression spéculative jusqu'à ce qu'une mesure les réclame.
